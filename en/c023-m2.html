JavaScript, TypeScript and message types

Your goalRead a TypeScript message contract, check received values and justify when a reservation can be displayed as confirmed.

Before you start
c021-m5 : origin, authentication and authorization · c018-m5 : contract tests and test doubles · c023-m1 : HTML, CSS, DOM and events

✿01 See the idea

You reserve the Atlas of Islands at the library. The screen receives a notice saying “waiting, position 4”. It can report that waiting status; it cannot yet say “reservation confirmed”. An envelope arriving and a book being reserved are different facts.

Imagine cards whose headings determine their contents: a waiting card carries a position, a confirmation carries a reference and a refusal carries a reason. The heading prevents you from looking for a reference on a card that gives only a position. You must also check whether the card received actually follows this pattern.

JavaScript is the language that executes the instructions: read the values, choose a branch, then change the text in the DOM, the representation of the page you have already met. TypeScript adds features including type descriptions and checks before execution. Here, a type describes the allowed shapes of values. Type annotations are erased during the transformation into JavaScript; they do not become an automatic check of messages from the server.

The scene and all its numbers are fictional. We follow only the request named “resa-lilas”, with no further sends, cancellations or concurrent messages. In this exercise contract, the server is assumed to be authorized and the kind “confirme” attests to a recorded reservation. This assumption gives the confirmation its meaning; it does not prove that the book has been handed to the reader.

The rule to remember

Describe the variants before execution; validate the received value during execution; display only what the valid variant and its contract attest to.

✿02 Follow an example

Worked example

From received notices to a justified confirmation

The library sends notices A, B and C in that order for “resa-lilas”. A reports waiting at position 4; B reports confirmation with a numeric reference 17; C reports confirmation with the text reference “LILAS”. Let us replay their checks and count received, accepted and confirming notices separately.

  1. Write the allowed shapes

    An object groups properties, each with a name and a value. The name genre serves as a tag; demande identifies the target reservation. In TypeScript, string means text and number means a number. The keyword type names a description. The symbol | means “one of these shapes”: this is a union. Read the following declaration as a structural contract:

    TypeScript declaration: type Retour = { genre: "attente"; demande: string; position: number } | { genre: "confirme"; demande: string; reference: string } | { genre: "refuse"; demande: string; raison: string };

    Each quoted genre value is an exact allowed text value, not a word to interpret freely. This shared field that distinguishes the shapes is called a discriminant. Braces delimit the properties of an object, and colons associate a name with its type.

    A variable retour of type Retour can have one of these shapes. In the branch where retour.genre === "attente", the TypeScript checker can narrow it to the shape that has position. The === operator tests equality without type conversion. Accessing retour.reference directly in this branch is an error detectable before execution. This assumes that TypeScript checking is active and that types have not been bypassed.

  2. Specify what the declaration does not check

    In this library contract, a position is an integer rank, from 1 to 20, counted in places in the queue; it is not a duration. A reference and a reason are text values that are non-empty after removing whitespace at both ends. The request identifier has no physical unit. The counters that follow are expressed in notices. The number type alone requires neither an integer rank nor a bound, and string even allows empty text.

    After JSON decoding, we first treat the value as unknown, meaning that it is still unknown. Before reading its properties, the check requires a non-null object that is not an array. It then requires a known genre and a text demande equal to "resa-lilas". Finally, it checks the fields specific to the variant. Extra properties are ignored in this exercise.

    For a position extracted from the object, the JavaScript test is: typeof position === "number" && Number.isInteger(position) && position > 0 && position <= 20. typeof examines the type of the value; Number.isInteger requires an integer; && requires all tests to succeed and stops at the first failure. For an extracted reference, the check is: typeof reference === "string" && reference.trim().length > 0. trim removes whitespace at both ends and length counts the remaining text units; here, only their presence matters. The same text test applies to raison.

    The check returns a value recognized as Retour or an explicit failure. Reporting a confirmation requires both a successful check and the genre "confirme". A failure must be reported as an unreadable notice, without inventing either a reservation refusal or a confirmation. The full design of a screen and its updates will come in later units.

  3. Process waiting notice A

    Decoded value A: { "genre": "attente", "demande": "resa-lilas", "position": 4 }. The kind is recognized, the request matches and 4 is a positive integer less than or equal to 20. A is accepted.

    The waiting branch allows the screen to display “Waiting, position 4”. It carries no confirmation reference. Contribution to the count of confirming notices: 0 notices. The shape check succeeded, but the contract still describes waiting.

  4. Reject the shape of B without inventing a reservation outcome

    Decoded value B: { "genre": "confirme", "demande": "resa-lilas", "reference": 17 }. The reference is a number, whereas this variant requires text. B fails the check even though its tag is known and its request matches.

    After A and B, we have 1 + 1 = 2 notices received, 1 notice accepted and 0 confirming notices. The screen can report the unreadable notice and retain the previous information, presenting it as the last valid information. It cannot conclude that the reservation was refused: it is the message that the check rejects.

  5. Recognize confirmation C

    Decoded value C: { "genre": "confirme", "demande": "resa-lilas", "reference": "LILAS" }. The reference is now non-empty text; the request and kind are appropriate. C is accepted in the confirmation branch.

    The exercise contract gives this kind the meaning “reservation recorded”. The screen can therefore display “Reservation confirmed, reference LILAS”. Contribution: 1 confirming notice. This result relies on the contract and on the source being assumed trustworthy; checking properties does not make a dishonest server truthful.

  6. Calculate the totals, then check them another way

    To count arrivals, add all notices, regardless of their validity: 2 + 1 = 3 notices received. To count those that pass the check, add only A and C: 1 + 1 = 2 notices accepted. The difference 3 − 2 = 1 notices gives the number rejected for their shape.

    Of the accepted notices, only C confirms: 1 notice. To check this without repeating the additions, mark A “accepted, waiting”, B “rejected, numeric reference” and C “accepted, confirmation”. The accepted and rejected categories cover the trace exactly: 2 + 1 = 3 notices, the total received. The confirmation count, 1, is less than the accepted notice count, 2: these counts answer different questions.

    These totals count the fictional trace. They measure neither the reliability of a real library nor an improvement achieved through TypeScript.

Explain it in your own words

Hide the notices. Reconstruct the roles of JavaScript and TypeScript and the boundary check. Explain why A passes without confirming, why B does not prove that a reservation was refused and why C allows a more precise display.

✿03 Common mistakes

  • “I wrote Retour, so everything the server sends conforms to this type.”

    An annotation or an assertion with as does not check any received value. Start again from unknown, check the object, then the kind and its fields. B has a known kind and remains malformed because of its numeric reference.

    Revisit the check of the reference in B

  • “If the message is accepted, I can display a confirmation.”

    A is a fully valid waiting notice. Validation allows you to read its variant; the kind and the meaning of the contract then determine the display. Count received, accepted and confirming notices separately.

    Revisit the totals and their categories

  • “I can make position, reference and reason optional fields on the same object.”

    That shape can accept a confirmation with no reference, because nothing then connects the kind to the required field. Instead, describe each variant with its required fields, then join the variants with |. Such a union describes the structure; bounds and non-empty text still need to be checked.

    Reread the cards and the fields specific to each

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What executes the instructions, and what happens to the TypeScript description?

JavaScript executes the tests, branches and text changes. TypeScript checks types, among other things, before execution; annotations are erased during the transformation into JavaScript. Validation of received messages must be explicitly executed.

Recall 2Why connect a kind to its fields in a union?

Each variant requires its own properties. In the attente branch, the discriminant genre allows the checker to narrow the value to the shape with position. A confirmation requires reference, and a refusal requires raison. Making every field optional does not describe these connections.

Recall 3Why use unknown followed by validation instead of brut as Retour?

unknown marks a value that still needs checking. as neither tests nor converts anything. The check that executes must recognize the object, the kind and the required fields, their constraints and then the target request, before using the value as a reservation result.

Recall 4Why is a valid notice not enough to display “reservation confirmed”?

A waiting notice can be valid. You also need the confirme variant, a valid reference and the right request. The meaning of this confirmation depends on the contract and a source assumed to be trustworthy; it does not attest to the physical handover of the book.
