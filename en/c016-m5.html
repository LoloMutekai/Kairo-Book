Documentation

✿01 See the idea

You give a friend a small program that counts the places remaining in a workshop. Your friend sees the name places_restantes but hesitates: should the inputs be the free places or the people already registered? Is the result displayed? Does calling the function reserve anything? A descriptive name still leaves these questions open.

Documenting means giving readers the information they need to act correctly. Here, the contract specifies what the inputs mean, their units, the expected conditions and what is returned. It also states any effects: calculating availability and recording a registration are different actions.

Our function receives capacite and inscrits. Its working body is simply return capacite - inscrits: it subtracts registrations from capacity and returns the result. It does not change any register, display anything or check the values received. The documentation must match this limited behavior.

The workshop and all its quantities are fictional. It has 12 places; 8 people are registered, each taking 1 place. We are documenting only this counter, without building a booking application.

The rule to remember

Write what someone needs to know to call the function and interpret its return value; check every promise against the code and an example.

✿02 Follow an example

Worked example

Provide usable documentation for the workshop counter

The call places_restantes(12, 8) uses the order capacite, inscrits. Let us build its documentation from the calculation, then check that the text also describes its limits.

  1. Name the quantities and the accepted domain

    C denotes capacite, the total number of places in the workshop. i denotes inscrits, the number of places already occupied by registrations. r denotes the number returned, meaning the remaining places. These quantities are integer counts, expressed in places; each registered person takes 1 place.

    A precondition is a requirement to meet before the call. We expect a nonnegative capacity and registrations between 0 and that capacity. The data must refer to the same workshop at the same time. The person making the call supplies them: the function does not consult a register on their behalf.

    0≤i≤C ; C et i entiers, en places

    C = 12 places and i = 8 occupied places satisfy this domain. A capacity of 0 is allowed if no places are occupied. The precondition describes the intended use; it adds no checking instruction to the program.

  2. Calculate the return value with the correct unit

    We subtract the places already occupied from the total because each is no longer available. We are calculating neither a proportion nor the number of people to register: the return value is a count of places still free.

    r=C−i=12−8=4 places

    The call therefore returns 4. The word “returns” means that this number goes back to the calling code. To show it on screen, another part of the program would need to display it. Registering someone would require another operation.

  3. Check the example by recombining the quantities

    The occupied and remaining places must add up to the capacity. Adding here checks the result through an operation different from the initial subtraction.

    i+r=8+4=12 places

    The recovered total is indeed 12 places, and the return value lies between 0 and C. We can also count the places numbered strictly above 8 and less than or equal to 12: 4 remain. This example checks a case; by itself, it does not prove that all possible calls are correct.

  4. Make the boundaries of the contract clear

    Full workshop: i = C, so 12 − 12 = 0 remaining places. The result can be 0; writing “always strictly positive” would be false. Empty workshop: i = 0, so 12 − 0 = 12 available places. These cases give concrete meaning to the inclusive bounds.

    If i is 12 + 2 = 14, the precondition is no longer met. The body described still performs 12 − 14 = -2. It does not reject this excess. This arithmetic result is not a valid availability count: the data were inconsistent with the workshop.

    The documentation must therefore state the expected domain and the absence of validation. Writing “raises an error if the workshop capacity is exceeded” would invent a behavior. Adding this check would change the program and should be addressed separately with its tests.

  5. Write the text to accompany the function

    Here is complete documentation for this small contract. The following paragraphs form its content; they explain how to use the function rather than repeating every symbol in the calculation.

    Purpose — Calculate the number of places still available in a workshop from the supplied counts.

    Inputs — capacite is the total number of places; inscrits is the number of places occupied by registrations. Supply integer counts for the same workshop at the same time, with 0 ≤ inscrits ≤ capacite.

    Return value and effects — Returns the integer capacite − inscrits, in places, between 0 and capacite inclusive when the preconditions are met. Displays nothing, changes no register and reserves no places.

    Limit — The function checks neither the type nor the bounds of the inputs. Their validity must be checked before the call; no rejection of inconsistent inputs is promised.

    Example — places_restantes(12, 8) returns 4. With inscrits equal to capacite, the return value is 0.

  6. Place the information and keep it consistent

    In Python, a docstring is a string literal placed as the first item in the function body, just after its def line. It is commonly enclosed in triple double quotes. The text proposed above can go there; Python help can then present it with the function. Comments starting with # are not docstrings.

    The project introduction file, often named README, instead explains how to run the small program and where to find its counter. The function docstring carries the detailed contract. Local comments explain, if needed, reasons that the operation does not make obvious. We do not need comments saying only “subtract inscrits” above an already readable subtraction.

    Finally, the text of an example does not automatically run a test. Keep a test that compares the return value with 4 for the example data and a full workshop case that expects 0. If the signature or behavior changes, reread the contract and rerun the relevant tests. Old documentation can remain easy to read while describing the wrong program.

✿03 Common mistakes

  • “The function name and an example are enough.”

    The example shows a particular call. Add the meaning and unit of the inputs, the expected domain, the return value and the effects. The full workshop case reveals a limit that a single ordinary example does not show.

    Reread the contract and its boundaries

  • “If the documentation forbids exceeding capacity, the program refuses it.”

    A precondition is a written requirement. This counter contains only the subtraction; with 14 registrations for 12 places, it returns -2. A check requires an instruction that is executed, followed by suitable tests.

    Compare the written condition with the calculation path

  • “Documenting means describing every line of code.”

    Explain what readers cannot decide by looking at the − sign: which values to supply, what they count and what the call changes. Place the contract near the function and the explanation of how to run the program in the project introduction file; avoid copying the same contract into several places.

Exercise 2 · Application and checking

Distinguish a new call from a registration

The program calls the counter with 12 places and 8 registrations, then makes exactly the same call again. What does it return each time? A registration is then recorded elsewhere: inscrits becomes 9. Calculate the new return value and its difference from the previous one. Write the example to add to the documentation.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

The counter records nothing: the same inputs have not changed between the initial calls.

Hint 2

For the new state, subtract 9 from 12, then compare the return values.

Compare with the solution

Each call with the initial inputs returns 12 − 8 = 4 places. The calculation alone takes no seat. It would therefore be wrong to reduce the result on the second identical call.

After the registration performed by another operation, the supplied registration count becomes 8 + 1 = 9. The return value becomes 12 − 9 = 3 places. It has decreased by 4 − 3 = 1 place, which corresponds to the added registration.

The documentation example can say: “places_restantes(12, 9) returns 3, without recording a registration.” The inverse check gives 9 + 3 = 12 places.

Check your reasoning

  • Keep 4 for calls whose inputs remain identical.
  • Obtain 3 places for the new state and explain the change of 1 place.
  • Write an example consistent with the contract without attributing the registration to the counter.

Exercise 3 · Diagnosis and independent writing

Correct misleading promises

The code remains the simple subtraction. New documentation announces: “Reserves a place, displays the free places, always returns a strictly positive integer and refuses registrations that exceed capacity.” Refute these promises, using the full workshop case and then the excess of 2 registrations. Write corrected documentation without changing the code.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Separate the stated effects from the number returned. Then examine the boundary inscrits = capacite.

Hint 2

Subtraction remains possible when the data fall outside the intended domain; this does not make them valid.

Compare with the solution

The body contains no recording or display operation: the booking and display promises do not match the code. In the full workshop case, 12 − 12 = 0; the return value is therefore not always strictly positive, even for an allowed input.

With 14 registrations for 12 places, the body calculates -2 instead of refusing the excess. This case falls outside the contract; it refutes the validation promise but must not become an example of permitted availability.

Possible corrected documentation: “Calculates the remaining places from capacite and inscrits, integer counts of places for the same workshop at the same time. Precondition: 0 ≤ inscrits ≤ capacite. Returns capacite − inscrits, between 0 and capacite inclusive under this condition. Displays nothing, reserves nothing and changes no register. Does not check the inputs. Example: places_restantes(12, 8) returns 4.”

The correction here concerns the text. If the project must reject inconsistent inputs, that behavior must be defined, implemented and tested; writing it in the documentation does not make it happen.

Check your reasoning

  • Justify the 0 value for the full workshop case and the result -2 for the excess.
  • Remove the effects and rejection that do not exist.
  • Produce a complete contract whose guarantee depends on valid inputs.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What should readers learn from function documentation?

Its purpose, the meaning and expected type of the inputs, their units and preconditions, the meaning of the return value, the effects and the limits. A checked example illustrates this contract without replacing it.

Recall 2Why is writing a precondition not enough to refuse an invalid input?

The precondition describes what the person making the call must supply. Rejection requires a check that is executed. Our counter only performs a subtraction and does not validate the inputs.

Recall 3Where should the function contract and the explanation of how to run the project go?

The contract belongs near the function, in its docstring: a string literal placed first in its body, commonly between triple double quotes. Instructions for running the project belong in the project introduction file. Local comments explain particular reasons.

Recall 4Why does calling places_restantes not take a place?

The body only returns capacite − inscrits. It changes no register; as long as the inputs remain identical, the return value remains identical. A registration must be performed separately.

Recall 5What is the difference between a written example and a test, and what should you do if the code changes?

The written example gives an input and an expected return value; its presence does not execute it. A test actually compares a result with the expected result. After a change, reread the contract and check its examples and boundaries with the relevant tests.
