Level 1 · C019·M1

Processes and address spaces

Your goalDistinguish a program from its processes, track their private values, and explain why an address must be accompanied by its address space.

Before you start
c016-m5 : documentation · c007-m5 : execution traces · c012-m5 : counterexamples

✿01 See the idea

You are preparing drafts of label sheets. A small program keeps a counter n: the number of labels planned in the current draft. You run this same program in processes A and B. Each starts with 12 labels. You add 3 in A: should the counter in B change?

Think of the program as an instruction sheet, and each process as a workstation that follows it with its own draft. A program is a set of instructions stored, for example, in a file. A process is an execution of a program managed by the operating system: it has an execution state, including its current position in the instructions, and an address space. The system assigns it a process identifier, often abbreviated PID, that distinguishes it from other processes currently alive on the same system.

An address space is the set of addresses that this process can use, together with the rules governing their use. A virtual address is a number interpreted in that space; it does not directly specify a location in physical memory modules. Here, the counter is private: a write by A changes only the draft in A. A and B can exist at the same time without executing their instructions at exactly the same instant.

The entire scenario and its numbers are fictional. We choose independent launches, each initializing n to 12, with no communication between them and no shared memory configured. The isolation of the counters is an explicit assumption of this example. The private data of separate processes do not become shared just because the program or variable name is the same.

The rule to remember

Before reading or changing a value, name the process and the address in its space. The same program, name, and address number are not enough to identify shared data.

✿02 Follow an example

Worked example

Track each draft to its final value

Initially, A and B each have n = 12 labels. A adds 3 labels, then B removes 5. Our fictional machine stores each integer counter in a private block of 4 bytes starting at virtual address 128. We track the values and the space occupied by the counters alone.

  1. Define what is read and what is counted

    A and B denote the processes. dspqjk russqi hczbmy afbpus kzijhx oqxirb szqezo hezxlt xhyaje gyuiih pbauxj aqclmi jnbsfw kz A byte is a unit of storage. The size s = 4 bytes is imposed by our fictional machine; it is not the size of a Python integer.

    M_P(a) denotes the integer value decoded from the block of s bytes starting at a in process P. This notation reads the entire block, not just the byte at a. Here, it gives a number of labels. The pair (P, a) specifies where we read; the value read is a separate piece of information.

    At initialization: M_A(a) = M_B(a) = 12 labels. Equal values do not demonstrate that the blocks are shared. We assume that the operations can be represented in the chosen blocks and that readings take place after each change is complete.

  2. Add in the intended process

    The addition applies to draft A. We read its value, add the requested quantity, then write the result back to its block. The prime symbol below denotes the value after this step.

    nA′=nA+3=12+3=15 étiquettes

    A now contains 15 labels. B has received no operation: 12 + 0 = 12 labels. Writing in A has not changed the private block of B.

  3. Subtract starting from the value in B

    The removal applies to B. We must therefore start from 12, the value in B after the previous step, rather than 15, which belongs to A.

    nB′=nB−5=12−5=7 étiquettes

    A has received no further operation: 15 + 0 = 15 labels. The final state is therefore A: 15 labels; B: 7 labels. Their difference is 15 − 7 = 8 labels.

  4. Locate the block and distinguish its address from its contents

    The block contains s consecutive bytes, with the first at a. The last address is therefore a + (s − 1), because the starting byte already counts as part of the block. The final offset is 4 − 1 = 3 bytes; the last address is 128 + 3 = 131.

    In each space, the block therefore runs from 128 to 131, including both endpoints. Reverse check: 131 − 128 + 1 = 4 bytes. The contents can change from 12 to 15 labels without changing the size or address of this fictional block.

    At the same number a = 128, M_A(a) ends up equal to 15 labels and M_B(a) equals 7 labels. The system interprets addresses within their spaces; equal numbers prove neither the same private data nor the same physical memory location.

  5. Count the space actually described by the model

    Each process has its private block of s bytes. The number of processes p is 2; it is a count, with no physical unit. The space S occupied by the counters alone is the product p × s.

    S=p×s=2×4=8 octets

    Check by addition: 4 + 4 = 8 bytes. The values 15 and 7 are not sizes: they count labels. S does not measure all the memory used by the processes. Instructions, other data, and management overhead are outside this small model; in particular, instruction pages can be physically shared.

  6. Check the operations and the isolation

    Return to the start using the inverse operations: 15 − 3 = 12 labels in A; 7 + 5 = 12 labels in B. The calculations recover the initial values separately.

    Then check the targets: the step affecting A left B at 12, and the step affecting B left A at 15. An arithmetically correct result in the wrong space would still be incorrect. If a real system showed the counters influencing each other, we would need to examine its communication and actual sharing before applying our assumptions to it.

Explain it in your own words

Hide the results and draw the blocks for A and B. Describe each read and each write. Why must we know the process to interpret the address, and why does the number of labels not tell us the size of the counter?

✿03 Common mistakes

  • “It is the same program: changing n in A also changes n in B.”

    The program supplies the instructions. The processes in our scenario keep separate private data. Track the changes with their target: after the addition in A, B stays at 12 labels. Any sharing would require an additional mechanism, which is absent from the assumptions of this scenario.

    Review the branches from the program to the processes

  • “The address 128 is identical: the values must be identical too.”

    The space in which the number is interpreted is missing. Read the pair (A, 128), then the pair (B, 128). Their private blocks contain 15 and 7 labels respectively at the end of the example.

    Revisit the location of the block and its value

  • “The counter changes to 15: it occupies 15 bytes.”

    15 counts the labels in the draft; 4 bytes is the fixed size of its representation. Keep the units on every line. In our fictional machine, the changes in the example retain this same size.

    Count the space again, keeping the units

The program still exists; the process has changed

Start again from the end of the example, without the addition in the previous exercise. A stays open. Hint 1

The scenario provides no saving or transmission of the counter in B. A new execution goes through initialization again.

Hint 2

Separate the moments: after B closes, only the counter in A remains in our model; after C launches, a new block is added.

Compare with the solution

The program file stores the instructions, including initialization. It is not the private block of process B. With no saving or transmission mechanism in the scenario, the new execution C therefore initializes its counter to 12 labels. A stays at 15 labels. The difference A minus C is 15 − 12 = 3 labels.

While B is closed and before C launches, the space occupied by the counters still associated with the processes in the scenario is 8 − 4 = 4 bytes. After C launches: 4 + 4 = 8 bytes. This block count does not measure the immediate physical release of memory by a real system.

The proposed statement confuses the stored program with the state of its previous execution. C is a new process; it does not automatically receive the identity or state of B. The system can reuse process numbers after processes end: an isolated PID is therefore not enough to identify an execution throughout an entire history.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Why does running the same program in A and B not create a single shared counter?

The program supplies the same instructions. Each process in the scenario initializes its own state in its address space. The counter blocks are private and no communication is specified.

Recall 2What is missing from the statement “read the counter at address 128”?

The process and its address space. In the final state of the example, the block starting at this address contains 15 labels in A and 7 in B. The virtual address alone does not identify a shared value.

Recall 3How can a counter of 15 labels fit in 4 bytes?

The number of labels is the value represented; bytes measure the space occupied by its representation. Our fictional machine imposes a block of 4 bytes for the values used. This choice does not describe the size of a Python integer.

Recall 4What checks should you perform after the addition in A and the removal in B?

Undo each operation to recover 12 labels, then check that each write changed only its target. A correct addition assigned to the wrong process is still an error.

Recall 5Why does the new process C not automatically recover the final counter value from B?

The stored program contains the initialization instructions. In this scenario with no saving or transmission, C executes them and starts with 12 labels. Keeping the program does not preserve the private state of the previous process.

Reconstruct the reasoning

Without looking at the diagrams, reconstruct this sequence with the counter: stored instructions → executions A and B → private blocks → process and address pair → write to its target → reverse check and check of the other block. Finally, explain why a new execution starts from initialization again in this scenario. Each time, distinguish the value in labels from the space in bytes.
