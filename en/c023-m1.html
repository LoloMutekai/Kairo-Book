Level 2 · C023·M1

HTML, CSS, the DOM and events

Your goalFollow a button activation through to the displayed text, distinguishing structure, presentation, the current document and the declaration of a fact.

Before you start
c021-m5 : origin, authentication and authorization · c018-m5 : contract tests and test doubles

✿01 See the idea

You are preparing a reading room. A card on the screen shows ‘Declared ready: 2 / 6’ and offers ‘Declare a chair ready’. Imagine an activation: should it repaint the button, replace the whole page or change the count? To understand the effect, follow what holds the text and what decides to change it.

HTML describes the elements and their meaning: a section groups the card's contents, a paragraph holds the count, and a button allows an activation. CSS supplies presentation rules, such as a border around the card. The DOM is the current document that the browser builds from the HTML: a tree of nodes, where an element can contain other elements or text.

An event is a signal received by the program. A button's click event can follow activation with a mouse or keyboard. A handler is the function called in response to this signal; here, it checks the limit, updates the count and then the text in the DOM. The browser can then present this new text. The button alone does not contain this counting rule.

The room, values and traces on this page are fictional. The card counts local declarations; it neither moves any chairs nor checks the room. We follow only the path from an activation to a display. Exchanges with a server and their success will require other evidence.

The rule to remember

Identify the HTML element, the CSS rule, the DOM node that changes and the handler that is called. Then check what the displayed text actually establishes.

✿02 Follow an example

Worked example

Replay the card after 2 activations

Initially, the card declares 2 chairs ready out of a target of 6. It receives 2 successive click events. For each event, the handler adds 1 chair if the target has not been reached, then rewrites the count. Let us identify the structure and the entire path to the final text.

  1. Build the HTML structure

    A tag names an element; an opening tag and its closing tag surround its content. A section can contain our card's paragraph and button. The fragment <section id="fiche" class="fiche"> opens this group; </section> closes it after its children.

    The paragraph is written as <p id="compte">Declared ready: 2 / 6</p>. The button is written as <button type="button" id="ajouter">Declare a chair ready</button>. The name p means paragraph; button denotes a native button. The type button specifies an ordinary button, with no form submission by default.

    An attribute is a piece of information in the opening tag. The id attribute gives a unique identifier within the document: compte and ajouter identify different elements here. The class attribute assigns membership in a reusable presentation group; several elements can share a class. Using the same name in id and class does not merge their roles.

  2. Give the card a presentation with CSS

    A CSS rule associates a selector, which identifies the targeted elements, with presentation properties. The .fiche selector targets elements of class fiche; #compte targets the element whose identifier is compte. The dot and the # sign express different criteria.

    To give the card a border, its border-style property can be set to solid, which requests a continuous line. Text color is set with color. These properties change the appearance; they do not move our count from 2 to 3. The word ‘ready’ remains written out: color alone does not say what is being counted.

  3. Find the live document

    Once it has read the HTML, the browser has objects representing these elements: this is the DOM. document refers to the current document. The getElementById method searches it for an element by its id; a method is an operation available on an object. Here, we find ajouter to listen to the button and compte to change its content.

    The textContent property allows a node's text content to be read or replaced. Writing the new count to the paragraph's textContent is enough for our card, where this paragraph contains only text. Replacing the content of an element with children in this way would also remove those children: the target must therefore be chosen precisely.

    The initial HTML file and the current DOM are distinct. Changing this paragraph in the DOM does not rewrite the source file. Without storage in place, reloading our card would rebuild the initial count. Neither a change in appearance nor calculating a number alone automatically rewrites this paragraph.

  4. Link the event to an explicit rule

    A listener is a registration that associates an event type with a handler on a target. The addEventListener operation performs this registration. Once the elements are available, our small program registers its handler for click on the ajouter button. The program's syntax will be studied in the next unit; here, we work through its mechanism in English.

    The handler reads the count, checks the target, updates the value and then writes ‘Declared ready: value / target’ into compte. The trace assumes a single registration, elements that are present, events processed successively, no errors and no other changes to the count. An activation sends nothing to a server in this example.

    Let N be the number of declared chairs before the event, C the target and N′ the number afterwards; the prime means ‘after’, rather than a derivative. These are integer counts in chairs, between 0 and C. δ is the amount added for this event: 1 chair if N < C, 0 chairs otherwise. The remainder r′ counts the chairs still to be declared after the event.

    N′=N+δ;r′=C−N′

  5. Process the first activation

    We read N = 2 chairs and C = 6 chairs. Since 2 < 6, the permitted addition is 1 chair. We add because this declaration joins the previous ones: 2 + 1 = 3 declared chairs.

    The handler keeps this new value and replaces the text of compte with ‘Declared ready: 3 / 6’. The remainder is 6 − 3 = 3 chairs. The subtraction removes the chairs already declared from the required total. If only the internal number changed, the screen could keep its old text.

  6. Process the next activation from the new value

    The new event starts from 3, rather than the initial HTML value of 2. The target remains 6, so the same addition is allowed. The count becomes 3 + 1 = 4 declared chairs. Starting again from the initial value each time would incorrectly keep the display at 3.

    r′=6−4=2 chaises

    The paragraph receives ‘Declared ready: 4 / 6’. The event did not choose this text by itself: the handler requested this write after the calculation.

  7. Check using the total and the trace

    Check the total: 4 declared chairs + 2 remaining chairs = 6 chairs, which is the target. The counts are integers and stay between 0 and 6. This check would detect a remainder calculated from the old value.

    Another approach, valid here because the trace does not reach the target: 2 events × 1 chair per event = 2 chairs added. Adding them to the starting count gives 2 + 2 = 4 chairs. This agrees with the successive calculation. At the limit, we would need to distinguish events received from declarations actually added.

    A final check of the path: the compte node must contain the final text. Finding the right number in the calculation does not guarantee that the handler wrote it in the right place. The result describes declarations; the room still needs to be observed to confirm the physical chairs.

✿03 Common mistakes

  • “If the button changes color, the count has been updated.”

    A color rule changes presentation. Identify the calculated value and the write to the compte paragraph separately; this text must contain the current value. In our card, the border and color do no counting.

    Revisit CSS, the DOM and writing the result

  • “The DOM is simply the HTML file, which stays the same.”

    The browser builds a modifiable document from the file. After the activations, its paragraph holds 4 while the source fragment keeps 2. Reconstruct the tree and distinguish its initial version from its current content.

    Review the tree and the event's path

  • “An activation always produces a single addition.”

    The addition depends on the handlers actually called and their rule. At the limit it is 0; with distinct handlers registered in duplicate, it can be repeated. Replay the exercise traces instead of counting only the gestures.

Exercise 3 · Diagnosing a local event registration

One gesture, duplicate handlers

The card starts again from 2 / 6. By mistake, 2 distinct functions have been registered for the same click event on ajouter. Each immediately reads and updates the same count according to our rule. For 1 event, calculate the expected result with a single registration and the result with this fault. Propose a repair to the registration and a check that would distinguish the two situations.

Assisted answer: try this exercise without help later.

Hint 1

The second handler reads the first handler's result; the target has not yet been reached.

Hint 2

Repairing the presentation removes no registrations. Look for the number of handler calls for a single event.

Compare with the solution

With a single registration, 2 + 1 = 3 chairs. With the fault described, 1 event × 2 handlers called per event = 2 calls. Here, each call adds 1 chair: 2 calls × 1 chair per call = 2 chairs added. The first gives 3, the next gives 4: 2 + 2 = 4 chairs. The difference is 4 − 3 = 1 chair.

Repair: register the handler only once for the current button. If the card is replaced and then reinstalled, remove the old registration with removeEventListener on the same target, with the same type, the same function and the same capture setting, then install the new one. Capture is an option that selects a phase of event propagation; our case keeps the default setting, whose details are not required here.

Proposed check: start again with the card at 2, send 1 click event and check for 1 call followed by 3 in the text of the compte node. Repeat after reinstalling the card. The fault would give 2 calls and 4 under the assumptions in the problem. Seeing a button on the screen is not enough.

The fault does assume distinct functions: registering exactly the same function again on the same target for the same type and capture setting does not automatically create a duplicate. Here, we count calls and follow their effect; we infer no general problem from an operation's name alone.

Check your reasoning

  • Produce the expected and faulty counts, with their difference in chairs.
  • Repair the registration rather than artificially subtracting a chair from the display.
  • Check the calls and the DOM content after a reinstallation.
  • Keep the assumption of distinct functions in the diagnosis.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What do HTML and CSS define in our card?

HTML defines the section, paragraph and button, with their meaning and initial content. CSS describes their presentation, such as the border; this presentation rule does not calculate the count.

Recall 2Why can the HTML file contain 2 and the DOM 4?

The browser built a modifiable document from the HTML. The handler replaced the text of the current paragraph; this change did not rewrite the initial file.

Recall 3What is the difference between #compte and .fiche in a CSS rule?

#compte selects the element with id compte, which is unique within the document. .fiche selects elements of class fiche; a class can be shared.

Recall 4What does the handler add to the click event?

The event signals an activation. The registered handler defines its consequence: read the count, check the target, update the value and write the text into the DOM. Without it, our counting is not defined by the button alone.

Recall 5What does the text ‘Declared ready: 6 / 6’ prove?

It indicates the count held by the card. Checking its correctness requires the event trace, the calls and the correct write to the DOM. Even verifying this path does not establish the physical arrangement of the chairs; that requires a separate observation.
