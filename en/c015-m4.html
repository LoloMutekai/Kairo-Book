Boundary cases

Your goalChoose inputs at the boundaries of a calculation contract and state their expected results before testing the program.

Before you start
c013-m5 : recursion · c014-m5 : invariants · c015-m1 : exceptions · c015-m2 : assertions · c015-m3 : unit tests

✿01 See the idea

A jug contains 500 mL of juice. A small program must state the portion for each guest. With 3 guests, sharing seems straightforward. But what should it return if nobody comes, if the table reaches its capacity, or if the jug is empty? These situations require us to specify the rule before calculating.

The table in our example seats at most 4 guests. A boundary case is an input at a boundary of the rule or just beside it: the last number accepted, the first rejected, or a 0 quantity. It does not have to be a huge or rare case. Equality with the capacity needs its own check.

The contract is the agreement on accepted inputs and the expected response. Here, a valid request produces a portion; an invalid request produces a rejection message, with no numerical result. A portion of 0 mL can be correct if the jug is empty; it cannot replace the rejection of a sharing request with no guests.

The scene, capacity, and volumes are fictional. We assume ideal sharing with no loss and containers large enough to hold the portions. We work with whole numbers of millilitres and guests; text inputs, imprecise readings, and rounding errors in machine arithmetic are outside the problem.

The rule to remember

Read the contract, identify where the response changes, then choose inputs on either side and exactly at the boundary. Write the expected result before looking at the program output.

✿02 Follow an example

Worked example

Prepare the juice-sharing tests

We keep the same jug and table. Let us build the expected results from the contract, then check the portions that can be calculated. No live service program is called.

  1. Define what the function promises

    V is the total volume in mL. n is the integer number of guests, a count with no physical unit. M is the integer capacity of the table, here 4 guests. q is the individual portion, in mL per guest, displayed in mL for each person’s container. The sign ≤ means “less than or equal to”; < means “strictly less than”.

    V≥0;1≤n≤M

    The inputs must first be integers and satisfy these conditions. Only then is q = V/n. Otherwise, the function must reject the request without performing the division. This choice of rejection is part of our contract; another application could define different behaviour, which would need to be stated and tested.

    The notation (V ; n) will denote a request, in that order. The relation n × q = V checks that the juice is conserved for an accepted request. It is not enough to check whether the request should have been accepted: that decision comes before the calculation.

  2. Establish an ordinary result and check it

    Take V = 500 mL and n = 3. The volume is positive and 1 ≤ 3 ≤ 4: the request is valid. We divide the volume by the number of equal portions because everyone receives the same quantity.

    q=5003 mL≈166.67 mL

    The symbol ≈ indicates a rounded value. The exact fraction is 500/3 mL. To check the total, we keep this fraction: 3 × (500/3) = 500 mL, the original contents. Adding the exact portions also gives this total. The displayed decimal number does not replace the fraction in this check.

    The expected test result is therefore: input (500 ; 3), response indicating acceptance, exact portion 500/3 mL. A test that only checks that the function does not stop would miss an incorrect portion.

  3. Check around the lower bound on the number of guests

    The counts n are integers: the step between neighbours is 1. Around the first accepted count, compare n = 0 and then n = 1. For (500 ; 0), we expect rejection before division. For (500 ; 1), the request is valid: 500 ÷ 1 = 500 mL, and 1 × 500 = 500 mL.

    Add a clearly invalid input: n = -1. A negative number of guests must be rejected. This check prevents replacing “n must be strictly positive” with “n must differ from 0”. A division being technically possible does not make the sharing comply with the contract.

  4. Take the neighbour, the bound, then the value beyond it

    The capacity is M = 4. Its lower neighbour is M − 1 = 3; its upper neighbour is M + 1 = 5. We have already calculated the portion for 3 guests. At the bound itself, “at most” still requires acceptance.

    q=5004=125 mL;4×125=500 mL

    For (500 ; 5), we expect rejection: this count exceeds M. The quotient would exist mathematically, but the contract does not allow it. The expected test result is therefore not a calculated portion.

    An incorrect version that accepts only n < M would behave correctly for 3 and correctly reject 5. It would fail at n = 4. The equality test provides information that the neighbours do not.

  5. Move the boundary check to the volume

    Fix n = 4 so that only V changes. The contract accepts V = 0: 0 ÷ 4 = 0 mL, with 4 × 0 = 0 mL. This is a valid sharing of a 0 quantity. For V = -1 mL, the expected response is rejection because a negative volume does not describe our jug.

    On the accepted side, the immediate neighbour is V = 1 mL. The portion is 1/4 mL, or 0.25 mL; the reconstructed total is 4 × (1/4) = 1 mL. The contract allows fractional portions even though the input volume is an integer.

    The step between neighbouring volumes here is 1 mL because we chose whole millilitres. This step would not be a universal rule for continuous readings. Boundary cases are chosen within the stated domain, with its units.

  6. Combine boundaries and interpret the verdict within its limits

    The request (0 ; 0) remains: an empty jug and no guests. It must be rejected: the valid volume does not cancel out the invalid count. The shortcut “as soon as V is 0, return 0” would give a false success here. The whole request must be validated before the shortcut or the calculation.

    Each prepared test therefore contains the input, the expected acceptance or rejection and, if accepted, the exact portion. Then compare the actual output with that expected result, rather than with a copy of the same condition inside the test. For the portions, the reconstructed total provides an additional check.

    These cases target the boundary confusions we have identified. Passing them does not prove the behaviour for all inputs or that the juice is actually served. It gives a specific reason to trust these tested behaviours; it is not a general proof of the program.

✿03 Common mistakes

  • “A case below and a case above are enough to check the boundary.”

    Add equality. Under our rule, n = 4 must be accepted; n < M would reject it while still giving the correct verdicts for 3 and 5. Reconstruct the expected result from “at most”.

    Revisit the bound and its neighbours

  • “If there is nothing to share, I always return 0.”

    Check n too. The request (0 ; 4) gives 0 mL, whereas (0 ; 0) is rejected. A 0 portion and rejection must remain distinguishable.

    Compare the roles of 0

  • “All these cases pass, so the function is proved correct.”

    State which behaviours were compared with which expected results. A finite set of tests can miss other inputs or a defect shared by the calculation and its check. The product n × q checks the accepted sharing, but not the decision to accept; revisit the contract too.

    Review the scope of the verdict

For (0 ; 0), the contract requires rejection because n < 1. Yet the shortcut returns 0 mL: it turns an invalid request into a result. This input is enough to disprove this version.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1How do you choose a boundary case rather than a random number?

Start from a condition in the contract. Choose the boundary where behaviour can change, then neighbours within the stated domain. For our integer count bounded by M: M − 1, M, M + 1.

Recall 2Why must you test exactly 4 guests?

“At most 4” includes equality. The cases 3 and 5 do not distinguish n ≤ M from n < M; the case n = 4 does.

Recall 3Why do a 0 volume and a 0 count give different responses?

V = 0 and n = 4 give a valid portion of 0 mL. n = 0 violates the contract and rules out division, whatever the volume. Rejection is not a 0 quotient.

Recall 4What must you write before running a test of our function?

The input (V ; n), the expected decision according to the contract, then the exact portion if the request is accepted. For that portion, also check n × q = V. Do not manufacture the expected result by copying the program condition.

Recall 5What can you conclude when these tests pass?

That the observed outputs match the expected results for these inputs. This proves neither correctness for all inputs nor that the juice is actually served. You must name the cases checked and the limits of this evidence.

Reconstruct the reasoning

Without rereading, reconstruct this sequence: state the domain and bounds; choose their neighbours and equality cases; distinguish rejection from a 0 portion; write the expected results from the contract; check exact portions using the total; combine boundaries when the order of checks can change the response. Then explain what these tests leave unresolved.

Identify a boundary in a bounded queue

What you understand
A boundary test starts with the meaning of the quantity being counted. The jug example uses the total number of guests requested; an event queue, a list of pending messages, may count its contents before an addition. The equality condition depends on this difference.
