Checkpoint and interruption

Your goalPrepare a consistent checkpoint, calculate the work that must be replayed after an interruption, and verify that resuming preserves the same trial.

✿01 See the idea

You are comparing a candidate method for ranking maintenance tickets with a reference method. The tickets are entirely fictional, the methods remain fixed, and no real ticket is sent. The candidate evaluation processes 12 batches in a fixed order. We focus only on resuming it: the score comparison was prepared in earlier units.

The screen shows 10 completed batches. Yet the last state that was saved and read back covers only 8 batches. If the process disappears now, the displayed counter disappears with it. Reliable resumption starts from the 8 saved batches, then repeats the next 2 batches before continuing.

A checkpoint is a state package that allows the same computation to continue. It combines what has been computed, how far the computation has progressed, and the identity of the trial. A line saying “save started” or a file with a recent name is insufficient to establish that this package is complete and readable.

Interrupting means stopping work according to an explicit rule. A request for a clean stop can arrive during a batch and then take effect at its end boundary. A failure can cut off the process in the middle of an operation. Prepare for these cases before relying on resumption. Saving does not give permission to restart a trial while its stop instruction remains in force.

The rule to remember

Start again from the last complete, compatible state that has been read back; resume after its last batch; check resumption against the same computation without interruption.

✿02 Follow an example

Worked example

A failure after 10 batches, a saved checkpoint after 8

The fictional trial contains N = 12 batches. An intermediate checkpoint is published after each group of b = 4 batches; those for batches 4 and 8 have been read back. The failure occurs just after batch a = 10, before the next one. Each batch takes exactly τ = 90 s per batch in our duration model; restoring takes r = 30 s. Writing, verification and waiting costs are excluded from this estimate.

  1. Define the state boundary

    A batch is a fixed portion of the fictional dataset. Sⱼ denotes the state after batch j: results associated with identifiers already processed, counts and sums used by the score. Dⱼ denotes the contents of batch j. F is the evaluation operation; θ denotes the fixed code, parameters and settings of the candidate. A complete transition is:

    Sj=F(Sj−1,Dj;θ)

    j is a batch index; S at index 0 is the empty initial state. The state index means “after”, never “next batch”. Processing is sequential, the batches and their order remain identical after resumption, and F is deterministic under the chosen conditions: the same state and inputs give the same result. Our evaluation produces no external effect.

    N, a and k count all batches, batches completed at the time of failure, and batches included in the last validated checkpoint, respectively. They satisfy 0 ≤ k ≤ a ≤ N. b counts the batches between periodic checkpoints. τ is a duration per batch, in seconds per batch; r is a duration, in seconds. The quantities L and R introduced below also count batches.

  2. Freeze state, position and identity together

    Package Ck contains k, Sk and I. I is the description that links the state to the trial: trial identifier, version of the code and its relevant environment, parameters, fingerprint of the ticket dataset, batch order and scoring rule. A fingerprint is a digest of the contents, useful for detecting a change; it does not demonstrate dataset quality.

    Ck=(k,Sk,I)

    Freeze the package at a boundary where the batch result is fully incorporated. Writing the counter after a batch and the sum before that batch would create an inconsistent state. In a variant using a pseudorandom generator, saving its current state and the position in the data would also be necessary; an initial seed alone does not describe its progress.

    First write a separate candidate package, read it back, check its contents and identity, then publish it through an atomic replacement: readers must select a whole package. The old checkpoint remains available until the new one is accepted. Resistance to a power failure also requires filesystem synchronization guarantees; the word “atomic” does not demonstrate it. Here, we assume that the last published checkpoint survives the process stopping.

  3. Calculate what the failure forces you to repeat

    The 2 accepted checkpoints are those for batches 4 and 8. Their last index is k = 2 × 4 = 8 batches. The last displayed index is a = 10; simply copying it does not make it k.

    L=a−k=10−8=2 lots

    L counts the completed work that must be replayed. Its duration is L × τ = 2 × 90 = 180 s, or 180 ÷ 60 = 3 min. The corresponding results are not added to those in the checkpoint: start again from Sk and recompute them.

    Assuming synchronous saving at each interval, no new batch starts until that save is published. Unsaved computation then remains at most b × τ = 360 s, or 6 min, including any batch already started. This bound excludes writing and does not describe a system that continues computing despite failed saves.

  4. Calculate what remains after restoration

    The first batch to run is k + 1 = 9, because Sk already contains results up to and including batch 8. The number R of batches to compute from the checkpoint is:

    R=N−k=12−8=4 lots

    Of these, 2 must be replayed and N − a = 2 have not yet been processed. Check with another decomposition: 2 + 2 = 4 batches. Resuming at batch 11 would skip the lost results; resuming at batch 8 would count that batch a second time.

    T is the estimated duration from the start of restoration to the end of computation, with the exclusions given in the problem. Add restoration only once and multiply the duration per batch by the number of remaining batches:

    T=r+Rτ=30+4×90=390 s

    The 360 s of computation and 30 s of restoration give 390 ÷ 60 = 6.5 min. The loss of 3 min is already included in this remaining computation: adding it again would count the replay twice. This number follows from the fictional durations and is not a measured performance.

  5. Handle a stop request without confusing it with a failure

    If the instruction allows stopping at the next boundary and the current batch has a bounded duration, start no further batch, finish the current one, then publish and read back the package for that boundary. After batch 10, an additional accepted checkpoint would give k = a = 10: L = 0 batches to replay.

    In this variant of the same scene, 2 batches would remain. Computing them would take 180 s; with restoration, 210 s, or 3.5 min. The cost of creating the new checkpoint is still excluded. This difference therefore cannot be presented as an overall gain.

    If the stop must be immediate, do not delay it to finish a batch or write a file. Any later resumption will start from the last checkpoint already accepted. If the candidate save is incomplete, keep the previous checkpoint and report what is lost. In all cases, resumption requires that the trial conditions and authorization remain valid.

  6. Check resumption against an uninterrupted reference run

    Before using this procedure, prepare an isolated trial on the same fictional tickets. Run the complete computation without interruption and save its expected final state. Then repeat the trial with interruption, writing, reading back and resumption; compare the ordered list of processed identifiers, results per ticket, counts and sums, and the final position N. An identical final average can hide a duplicate and an omission.

    The 8 batches in the checkpoint and the 4 resumed batches must cover the 12 expected batches without overlap. Also check the initial and final boundaries: from index 0, everything remains to be computed; from index N, no batch should be replayed. Introducing an interruption during writing and a package with a different identity lets you check that rejection remains visible to the checkpoint reader.

    With exact calculations and the stated determinism, expect the same final state. For approximate calculations, specify the comparison fields and tolerance in advance, then justify the tolerance. Equal rounded scores are insufficient. The duration calculation on this page does not constitute execution of this resumption check.

Explain it in your own words

Without rereading, explain why completed batches, saved batches and batches remaining after resumption have different counts. Then state aloud the package contents and the check that could refute a claim of correct resumption.

✿03 Common mistakes

  • “The counter shows 10, so I can resume after that batch.”

    The counter measures work completed before the failure; the accepted checkpoint preserves only 8 batches. Restore that checkpoint and resume at batch 9. Check the position and saved results together.

    Repeat the calculation of lost and remaining work

  • “The file has the right name, so I can use it.”

    Read the whole package back, and check its consistency and trial identity before publication. A truncated file or one linked to a different ticket order must be rejected. Keep the previous accepted checkpoint.

    Review the package publication diagram

  • “The final score is identical, so resumption is proved.”

    A score can hide omissions and duplicates. Compare identifiers, results and all relevant state with an uninterrupted reference run; declare tolerances. The milestone also distinguishes an implemented comparison from an executed comparison.

    Read the available evidence and its limitation

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What must a usable checkpoint combine?

A complete state, its exact position in the computation, and the identity of the inputs, code and settings that give it meaning. The package must have been read back and accepted.

Recall 2If Sₖ is the state after batch k, which batch should run next?

Batch k + 1, after a compatibility check. Repeating k would introduce a duplicate; following the last displayed counter could omit lost work.

Recall 3How do you distinguish lost work from work remaining after restoration?

With a completed batches, k saved batches and N planned batches: the loss is a − k; the remaining work is N − k. This includes replay and the N − a batches still unprocessed.

Recall 4How do a clean stop and an immediate stop differ for saving?

A clean stop can reach a boundary within a bounded time and publish a new state if the instruction allows it. An immediate stop must not wait for this operation; the last checkpoint already accepted provides the fallback.

Recall 5Why does an identical rounded score fail to prove correct resumption?

It can hide omissions, duplicates or different states. Compare identifiers, results and relevant state with a comparable uninterrupted run, using declared tolerances if needed.
