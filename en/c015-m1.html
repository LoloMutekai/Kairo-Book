Level 1 · C015·M1

Exceptions

Your goalFollow an exception from an interrupted calculation to the appropriate handler, without turning failure into a result.

Before you start
c013-m5 : recursion · c014-m5 : invariants

✿01 See the idea

At a workshop, a jug holds 750 mL of water to share equally among 3 people. The program prepares a share of 250 mL per person. But if the registration sheet lists 0 people, what should it display? It cannot obtain a share by continuing the same division.

An exception is a signal that interrupts the normal flow of an operation. In our Python program, division by 0 raises an exception of type ZeroDivisionError. The type names its category; an optional message gives more details about the circumstances. This signal is not a quantity of water.

A handler is the part of a program responsible for handling a type of exception. Here it can announce that the number of people needs correcting. It does not fill the cups, produce a share, or automatically repeat the division.

All numbers in this scenario are fictional. We are only preparing a quantity to announce: no water distribution is triggered. Functions and function calls are already familiar; we are adding the particular path that appears when a call fails.

The rule to remember

When an operation raises an exception, abandon its normal continuation, look for an active handler of the right type, and distinguish its response from a successful calculation.

✿02 Follow an example

Worked example

The same preparation, with a normal return or an interruption

The preparation calls part_par_personne(V, n), a function that performs the division V / n and returns its result. First follow V = 750 mL and n = 3 people, then the same preparation with n = 0. We assume the inputs are already numeric; reading the form is outside this scenario.

  1. Define what needs to be calculated

    V denotes the available volume, in millilitres. n is the number of people, an integer that counts people. q is the share, in millilitres per person. Sharing equally means finding a quantity q such that n × q gives V back. We allow fractional shares and ignore losses; we are not simulating a measuring device.

    q=Vn,n>0

    This sharing rule applies to a strictly positive number of people: n > 0, so at least 1 person. The first version of the function does not check this rule: it only attempts the division. An operation that Python can perform does not always give an acceptable preparation for the workshop.

  2. Define the protected section

    In the caller function, called preparation, a try block surrounds the call to part_par_personne(V, n), followed by the announcement of the share obtained. A block is a group of instructions; indentation in Python defines its boundaries. The word try marks the section in which we want to be able to handle an interruption.

    Immediately after this block, except ZeroDivisionError identifies the handler for this category. Its only action in this scenario is to display “Correct the number of people”. The announcement “End of attempt” is placed after the whole try/except statement, outside both blocks. The handler is active during the call: placing it after a call already executed without protection would not allow it to catch that call’s failure.

  3. Calculate the share when the number of people is valid

    With n = 3, dividing the volume by the number of people gives the quantity intended for each person. The word return, in the sharing function, sends this quantity back to the caller and ends this call normally.

    q=7503=250 mL par personne

    The caller receives the share and announces it. It skips the handler because nothing was raised, then announces the end of the attempt. Check the calculation: 3 people × 250 mL per person = 750 mL; we recover the entire initial volume.

  4. Identify the exact point of interruption

    Start again with the same supply, but with n = 0. The division is impossible: 0 people × a finite share would give 0 mL, never the 750 mL to be shared. There is therefore no new share that answers the question.

    In our Python function, evaluating V / n automatically raises ZeroDivisionError. The return does not return any quantity. The sharing function has no local handler: the signal propagates back to preparation, the function that called it. This is exception propagation.

    The assignment of the result in the caller does not complete. The share announcement, which comes next in the same try block, is skipped. An old value that might be stored elsewhere would not become the result of this call.

  5. Handle failure without pretending to succeed

    The raised type matches except ZeroDivisionError: its handler displays “Correct the number of people”. When it ends normally, execution moves past the whole try/except statement and announces “End of attempt”. It returns neither to the division nor to the skipped share announcement. Trying again would require a new call with a corrected input.

    If no matching handler is found here, the signal continues through the enclosing calls. An exception that remains unhandled all the way to the top interrupts this small script with an error traceback. The message in this traceback gives information about the failure; it is not a value to use for sharing.

    Check the path: with 3 people, the announcements are “share: 250 mL per person”, then “End of attempt”. With 0 people, they are “Correct the number of people”, then “End of attempt”. This last announcement only means that the attempt has ended; it does not prove that the calculation succeeded.

  6. Also reject values that division would accept

    An incorrect registration sheet may contain a negative integer. For n = -3, division alone would produce -250 mL per person without raising ZeroDivisionError. Yet a negative number of participants makes no sense in this scenario.

    Improve the same function: before the division, if n ≤ 0, it executes raise ValueError with the message “A strictly positive number of people is required”. The word raise explicitly raises a signal; here ValueError denotes a rejected input value. In this version, n = 0 also triggers ValueError before reaching the division.

    The caller must therefore handle ValueError to ask for a new number of people. A handler limited to ZeroDivisionError no longer matches this explicit rejection. Catching all errors indiscriminately could present another defect in the program as a simple input mistake.

    This validation does not correct the input: it rejects it. An exception does not undo actions already completed before it occurred. Our scenario avoids this difficulty by calculating before distributing any water; programming a rollback would be a separate task.

✿03 Common mistakes

  • “If the error is caught, the program resumes at the division.”

    The interrupted block is exited. After a handler that ends normally, execution continues after the whole try/except statement. In our scenario, only the end of the attempt follows; recalculating requires a new call with a corrected number of people.

    Trace the handling and announcements again

  • “I can return 0 mL to make the error disappear.”

    A 0 result would be a quantity announced as calculated. With 0 people, the share is undefined. Report the rejected number of people and do not announce any new share; hiding the signal does not resolve the division.

    Compare the two paths through the preparation

  • “If there is no exception, the input and the result must be correct.”

    With -3 participants, the numeric division works and returns -250 mL per person. The rule for this scenario must reject that number of people. After adding the explicit rejection, the handler must target ValueError, the type actually raised.

    Justify the rejection in the last exercise

Exercise 3 · Transfer · repair the reasoning

The sheet contains a negative number of people

The sheet gives n = -3. Someone proposes keeping division alone, since multiplying its result by n gives V back. Explain why this check is insufficient. Then add the explicit rejection before the division and specify which handler must ask for the number of people to be corrected. What then happens with n = 0?

Assisted answer: try this exercise without help later.

Hint 1

A calculation identity can remain true with values that make no sense in the scenario.

Hint 2

The rejection occurs before the division. The type given to raise, rather than the 0 value itself, determines which handler to look for.

Compare with the solution

Without validation, 750 / (-3) = -250 mL per person. The check (-3) × (-250) = 750 mL is algebraically correct, but it does not make a negative number of people possible. Our rule requires n > 0.

Before the division, the condition n ≤ 0 must explicitly raise ValueError with the message “A strictly positive number of people is required”. With n = -3, the function is interrupted before the quotient is calculated. The caller must have a ValueError handler to announce that the number of people needs correcting; except ZeroDivisionError alone is unsuitable.

With n = 0, the same condition is true: ValueError is again raised before the division. No new share is returned. Once a new valid number of people is supplied, a new call will be able to perform the sharing; the handler has not itself repaired the input.

  • Distinguish algebraic consistency from an acceptable number of people.
  • Place the rejection before the division and name ValueError.
  • Match the handler to the explicitly raised type, including when the number of people is 0.
  • Ask for a new input without assigning a share to the rejected calculation.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Why is a division exception not a share of water?

It is an interruption signal: the operation has not provided the requested quantity. The failure must be handled without inventing a new share, even a 0 share.

Recall 2Where does the signal go if part_par_personne has no local handler?

It leaves this call and looks for an appropriate active handler in the enclosing calls. In our scenario, preparation handles ZeroDivisionError around its sharing call. If it remains unhandled all the way to the top, this small script is interrupted.

Recall 3After the handler, does execution return to the skipped share announcement?

No. If the handler ends normally, execution continues after the whole try/except statement: here, the end of the attempt. Sharing again requires a new call. Actions already completed before the exception are not automatically undone.

Recall 4Why can explicitly rejecting 0 people raise ValueError rather than ZeroDivisionError?

The function first checks the rule requiring a strictly positive number of people and uses raise ValueError. It stops before the division: the signal is the one chosen for the rejection, and the handler must target that type.

Recall 5What else is needed for a successful division to guarantee an acceptable sharing?

A check of the scenario’s rules. A negative number of people can give a numeric quotient without an exception, even though sharing among a negative number of people is impossible.

What you understand
An interrupted call can lead its caller to return a fallback response. In our workshop, the message about a rejected number of people is not a calculated share; the distinction also applies when a program returns a value after handling an exception.
