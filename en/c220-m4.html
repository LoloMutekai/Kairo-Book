GPU

✿01 See the idea

A workshop checks deviations in the cuts of its panels. For each signed deviation x, in millimetres, it wants to store its square y, in square millimetres. A deviation to the left and a deviation of the same size to the right give the same square. Each panel can be processed without consulting the result for another panel.

The central processing unit, or CPU, controls the program. The graphics processing unit, or GPU, can make progress on many similar computations using different data. It is given a kernel: the small procedure to apply to each element. A GPU thread is a logical instance of this procedure, associated here with an array slot. This thread is not an independent operating system process.

The GPU groups and schedules these threads. Creating as many threads as panels does not mean having as many physical units active at the same instant. This work is suitable mainly because the threads follow the same rule and write to distinct slots. Reading neighbouring slots also makes it easier to read from memory.

The array still needs to be transferred to the GPU and the squares retrieved. Our scene assumes GPU memory separate from host memory, which is the memory the CPU uses. On a machine with shared or unified memory, data movement and its costs must be reconsidered. All deviations, transfer rates and times on this page are fictional; they support a computational model and do not describe the reader’s machine.

The rule to remember

First check that each thread produces the correct slot; then compare the full time needed to make the same result available in the same place.

✿02 Follow an example

Worked example

Square the deviations, then account for their transfer

The pattern (-3, -1, 2, 4) mm is repeated 1000 times: this defines the entire batch, with N = 4 × 1000 = 4000 values. The inputs are already on the host, and we want to retrieve the entire array of squares there, without calculating their sum. The buffers are already allocated and initialization is complete.

  1. Assign an output to each thread

    i is the integer index of a slot and has no unit; xᵢ denotes its deviation in mm and yᵢ its square in mm². N is the total number of elements. The thread with index i reads only xᵢ and writes only yᵢ. The input array remains unchanged during this computation.

    yi=xi2

    This operation runs only if 0 ≤ i < N. If the launch creates extra threads to fill its groups, those threads must neither read nor write outside the array. Distinct writes avoid contention over the same slot here. A shared sum would require another mechanism, which we do not introduce.

  2. Calculate and check the contents

    For the first pattern: (-3) × (-3) = 9; (-1) × (-1) = 1; 2 × 2 = 4; 4 × 4 = 16. All results are in mm².

    The expected array is therefore the pattern (9, 1, 4, 16) mm² repeated 1000 times, in the same positions as the inputs. It contains 4000 outputs, as required. The squares are nonnegative; the square of each negative input equals that of its absolute value. These checks complement the comparison with a CPU reference, element by element.

    We assume that the small values in this example are exactly representable in the chosen format. This does not promise numerical identity for all GPU computations: the general protocol for comparing rounding differences belongs to the next unit.

  3. State the cost model

    b = 4 bytes is the space occupied by an element, identical for input and output despite their different physical units. B = 8000 bytes/ms is the fictional effective transfer rate of each copy. rC = 500 values/ms is the rate of the complete reference CPU computation; rG = 2000 values/ms is the rate of the GPU kernel alone. These rates include the local memory accesses required for the computation.

    L = 1 ms is the fictional fixed launch cost. T_C and T_G are the total CPU and GPU durations, in ms. Since the GPU may be asynchronous, timing must wait for its completion and for the return copy to finish; the launch call returning is not enough.

    We assume constant rates for the sizes studied, sufficient memory, an available GPU and no overlap between stages. Allocations and initialization are excluded from this comparison of the two paths, which must be stated with any measurement. A compatible library and driver would be needed to run the kernel in practice.

    TC=NrC;TG=L+NbB+NrG+NbB

    In the formulas, rC and rG are the same rates as r with subscripts C and G. Each fraction of bytes divided by bytes/ms is a duration in ms. The central part N/rG refers only to the kernel.

  4. Count the bytes and copies

    The outbound copy carries the inputs: N × b = 4000 × 4 = 16000 bytes. The return copy carries as many outputs, and therefore as many bytes. The full path moves 16000 + 16000 = 32000 bytes.

    One copy takes 16000 / 8000 = 2 ms. The two directions take a total of 2 + 2 = 4 ms. The return copy must be counted because the requested result must be available on the host. If another task used it directly on the GPU, the path being compared would need to be redefined.

  5. Compare the full durations

    The CPU reference takes 4000 / 500 = 8 ms. The GPU kernel takes 4000 / 2000 = 2 ms. Outside the kernel, we incur 4 + 1 = 5 ms. The GPU therefore finishes in 2 + 1 + 2 + 2 = 7 ms.

    A=TCTG=87≈1.14

    A is the model’s speedup factor and has no unit. Here A exceeds 1, since the GPU path takes less time. The difference is 8 − 7 = 1 ms. Comparing only the CPU and the kernel would give 8 / 2 = 4, omitting the copies and the launch.

    Check using another expression: the variable GPU cost is N × (b/B + 1/rG + b/B). L is added to this. We obtain 7 ms again. This result follows from our fictional assumptions, with no claim of a real performance gain.

  6. Understand when batch size offsets the launch cost

    For a batch to be faster on the GPU, we need T_G < T_C. Grouping the terms proportional to N gives the inequality below. δ denotes the variable time saving per element, in ms/value, after accounting for both copies.

    δ=1rC−(2bB+1rG);Nδ>L

    If δ is positive, increasing N can offset L: we need N > L/δ. If δ is 0 or negative with positive L, increasing the batch size is never enough in this model. The decision exercise will ask you to calculate this threshold, then check it at equality.

    Real rates can vary with N. We would therefore need to measure the full path against a CPU reference that has already been carefully optimized, and check the resulting contents again before choosing. We stop at this decision about where to run the computation; we develop neither the complete architecture of a GPU nor the implementation of a computing library.

Explain it in your own words

Reconstruct the path of the batch and say where the input and output are at each stage. Why is a shorter kernel time not enough to choose the GPU? Also recall the reason for writing to distinct slots.

✿03 Common mistakes

  • “I can have all threads write to the first slot.”

    The writes would contend over a slot, while the other outputs would have no result. Assign slot i to thread i and check 0 ≤ i < N. Our goal is an array of squares; a sum would require a separate operation.

    Review the assignment of outputs at the start of the example

  • “The kernel finishes quickly, so the whole program has that speedup.”

    Trace the path through to the result being available on the host: outbound copy, launch, kernel, return copy. Wait for the work to actually finish before stopping the timer. In our model, the relevant ratio is 8/7, not 8/2.

    Review the diagram of the full path

  • “Increasing the batch size is enough to make the GPU win every time.”

    First calculate δ, including transfers. If each element costs the GPU as much time or more after the copies, a larger batch size cannot offset the fixed cost L. The threshold requires positive δ and rates assumed to be constant.

    Recall the condition and its check in the decision exercise

Exercise 1 · Application · contents and indexing

The first pattern reaches the correct slots

Work out the squares of the pattern (-3, -1, 2, 4) mm. However, a procedure writes every square to y[0]. Explain why the final array is incorrect, then give the writing rule and the condition for a valid index.

Assisted answer: try this exercise without help later.

Hint 1

The sign disappears when a value is squared. The element’s position must stay the same.

Hint 2

Ask yourself which thread fills each slot other than y[0].

Compare with the solution

The expected outputs are (9, 1, 4, 16) mm². For example, (-3) × (-3) = 9 mm². Each pattern in the batch must produce these outputs in this order.

With y[0] for all threads, several threads write to the same slot. No valid result for the entire array is guaranteed: these threads do not fill the other slots. You must not assume that the last element in the list will necessarily be written last.

Thread i must write yᵢ = xᵢ × xᵢ only when 0 ≤ i < N. The input is read-only, each output has its owner, and extra threads do not touch the array.

Check your reasoning

  • The squares are correct, nonnegative and in mm².
  • The logical order of the outputs is preserved, without imposing an execution order on the threads.
  • The fix assigns a distinct slot and bounds the index.

Exercise 2 · Application · full comparison

The same pattern in a smaller batch

Repeat the pattern only 100 times, giving N = 400 values. Keep b, B, rC, rG and L unchanged. Predict the choice, then calculate the copies, the kernel, both full durations and A. This extrapolation of rates is part of the fictional model.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Each copy carries N × b bytes; the launch still costs L.

Hint 2

A factor A below 1 means that the GPU path takes more time.

Compare with the solution

Each copy carries 400 × 4 = 1600 bytes. It takes 1600/8000 = 0.2 ms; the outbound and return copies take 0.4 ms. The kernel takes 400/2000 = 0.2 ms.

The cost outside the kernel is 0.4 + 1 = 1.4 ms. The GPU therefore takes 1.4 + 0.2 = 1.6 ms. The CPU takes 400/500 = 0.8 ms.

A = 0.8/1.6 = 0.5. The CPU finishes earlier in this model. Check: the variable terms have decreased in the same proportion as N, but L = 1 ms has not decreased. The kernel still takes less time than the CPU, which is still not enough to decide between the full paths.

Check your reasoning

  • Count both copies and keep L unchanged.
  • Give each duration in ms, then A with no unit.
  • Choose the CPU based on the full durations and state the assumptions.

Exercise 3 · Decision · justification and boundary case

At what batch size should you switch processors?

Using the parameters from the example, calculate δ, then L/δ. Give the strict condition on N and check it by calculating both durations exactly at the boundary. Finish by explaining what would change if δ were negative.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Calculate the CPU time for a value, then the time for its bytes to travel in both directions and the time for its GPU computation.

Hint 2

Nδ > L implies N > L/δ only if δ is positive. At equality, neither path is faster.

Compare with the solution

The CPU uses 1/500 = 0.0020 ms/value. Each value requires 4 + 4 = 8 bytes of transfers, giving 8/8000 = 0.0010 ms/value. The kernel adds 1/2000 = 0.0005 ms/value.

The variable GPU cost is therefore 0.0015 ms/value. The saving δ is 0.0020 − 0.0015 = 0.0005 ms/value, which is positive. L/δ = 1/0.0005 = 2000 values. The GPU is strictly faster for N > 2000 in this model, and only in this model.

At N = 2000, the CPU takes 2000/500 = 4 ms. The variable GPU cost is 2000 × 0.0015 = 3 ms; adding L gives 1 + 3 = 4 ms. The durations are equal, which checks the threshold.

If δ were negative, Nδ could not exceed positive L for a positive number of elements. Increasing the batch size would therefore give no GPU advantage under these assumptions. Changing the location of the data or the computation would create another path to model and verify.

Check your reasoning

  • Form δ from all variable costs and check its sign.
  • Obtain a threshold in values, with a strict inequality.
  • Check that the durations are equal at the boundary.
  • Limit the decision to the model and address the case of negative δ.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does a GPU thread do when calculating the squares?

Thread i runs the kernel for its slot: it reads xᵢ and writes yᵢ = xᵢ × xᵢ, only if 0 ≤ i < N. It is a logical instance, with no required correspondence to a physical core.

Recall 2Why can we process the panels without waiting for neighbouring results?

Each square depends only on its own input. The input array remains unchanged and each thread writes to a distinct slot. A shared output, such as a sum, would require an additional mechanism.

Recall 3Which costs must be counted to obtain the squares on the host?

In our sequential model: outbound copy Nb/B, launch L, kernel N/rG, return copy Nb/B. Timing must wait for the result to be complete. Allocations and initialization are explicitly excluded from this comparison.

Recall 4Why does a large batch not guarantee a GPU advantage?

Offsetting the launch cost requires a positive variable saving δ = 1/rC − (2b/B + 1/rG), then Nδ > L. If δ is 0 or negative with positive L, increasing N is not enough in this model.

Recall 5What evidence should you request before choosing the GPU on a real machine?

Compare the contents with the reference CPU result, then measure the same path through to the result being available in the same place, waiting for GPU completion and stating the measurement scope. The fictional rates and durations on this page prove no real performance.
