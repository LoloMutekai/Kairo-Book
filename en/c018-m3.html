Invariants and immutable states

Your goalState what makes a state valid, preserve that rule when making a reservation, and explain what a frozen object actually protects.

Before you start

✿01 See the idea

A small room has 12 seats. Its reservation record shows 5 reserved seats and 7 available seats. You keep this record to explain the situation to someone. A request for 4 seats arrives: should it rewrite the record you already hold?

Let us call the description of the room at a given moment its state: its capacity, the number of reserved seats and the number of available seats. An invariant is a rule required for every state the program accepts or makes visible. Here, the counts must be non-negative integers, and reserved + available must always equal the capacity.

An immutable state keeps its values after creation. To accept the request, we prepare a complete new record, then select it as the current state. The old record remains an accurate description of the previous situation. Immutable therefore does not mean that the room can no longer accept reservations: successive states can differ.

These data are fictional. We process requests one after another, with a fixed capacity. Each request specifies an integer number of seats; it is either accepted in full or refused. There are no cancellations or implicit partial reservations here.

The rule to remember

Validate the state when it is created, check the request, construct a complete new state and preserve the old one. Freezing an object is not enough to make its values consistent.

✿02 Follow an example

Worked example

Reserve seats without changing the old record

Starting with a capacity of 12 and 5 reserved seats, let us calculate the available seats, then process a request for 4 seats. We will also check why a request for 8 seats must be refused from the same starting state.

  1. Write the validity rule precisely

    Let S = (C, R, L) denote the ordered triple of capacity, reserved and available. C is a strictly positive integer; R and L are integers. All these quantities are measured in seats. I(S) denotes the condition “S is valid”; the symbol ∧ means that all the conditions must be true.

    I(S):0≤R∧0≤L∧R+L=C

    The integer domain and the requirement that C be strictly positive are part of the contract. The equality and non-negativity also imply that neither count exceeds C. Validation takes place as soon as a record is created, before it can be used. An invariant expresses what must remain true; it does not mean that R or L must remain constant.

  2. Construct and check the initial state

    The capacity and reservations are given. Since each seat is either reserved or available, subtract the reserved seats from the capacity: L = 12 − 5 = 7 seats. The initial state is S = (12, 5, 7).

    Check: 5 + 7 = 12 seats, equal to C. The counts are non-negative integers. S therefore satisfies I. This check must come before the first reservation: a correct transition does not automatically repair an inconsistent starting state.

  3. Check the request before acting

    q denotes the number of seats requested, in the same unit. The acceptance condition is: q is an integer and 0 ≤ q ≤ L. Here, q = 4 and L = 7; 0 ≤ 4 ≤ 7 is true. We can reserve the full number of seats.

    This condition on the input is a precondition of the operation. It complements the state invariant. If it fails, return an explicit refusal and keep S; do not publish a partially modified record.

  4. Calculate the complete new record

    The prime in S′, R′ and L′ means “after the request”. The capacity does not change. The reserved count increases by q; the available count decreases by exactly the same amount.

    S′=(C,R+q,L−q)

    R′ = 5 + 4 = 9 seats. L′ = 7 − 4 = 3 seats. Construct S′ = (12, 9, 3) from these values, then validate it. S remains (12, 5, 7). The name referring to the current state can then refer to S′; changing this reference does not modify the object S.

  5. Check the result and justify preservation

    Sum: 9 + 3 = 12 seats, matching the capacity. The new counts are integers and non-negative. Reverse check: 9 − 5 = 4 seats added to the reserved count; 7 − 3 = 4 seats removed from the available count. Both differences recover the requested amount.

    R′+L′=(R+q)+(L−q)=R+L=C

    The request is added and subtracted, so the sum is preserved. Also, q ≤ L ensures L′ ≥ 0 and q ≥ 0 ensures R′ ≥ 0. Given a valid initial state, the accepted transition therefore preserves the invariant for every permitted request, beyond just the chosen values.

  6. Understand the incomplete update

    If R is modified in the shared record before L is modified, someone may receive (12, 9, 7). The sum becomes 16 seats: it exceeds the capacity by 4 seats. The intermediate state violates the invariant even if a later instruction is intended to correct it.

    Our intermediate values serve only to prepare S′. We make the complete new record visible once it has been validated. The immutability of S prevents ordinary modification of it during this preparation. This property is not enough to handle simultaneous reservations: the reasoning here assumes successive requests.

  7. Refuse excess demand without fabricating a valid result

    Start again from S. The request for 8 seats exceeds the 7 available seats. Accepting it would give R′ = 5 + 8 = 13 and L′ = 7 − 8 = -1 seat. Yet the sum would be 13 + (-1) = 12 seats: equality alone is not enough, because L′ is negative.

    The correct result is a refusal with S unchanged. Silently replacing the negative available count with 0 would mean that adding the counts no longer recovers the capacity. Our contract requires refusal of the entire request, rather than an improvised repair of the numbers.

  8. Translate the idea into Python objects

    A class declared with @dataclass(frozen=True) prevents ordinary reassignment of its fields after construction. A validation check called at the end of construction can reject values that violate I by raising ValueError. Freezing protects the fields; validation protects their consistency. These are distinct mechanisms.

    In our triple, the integer counts are themselves immutable. If the record instead contains a list of group sizes, freezing the field does not freeze the list. Imagine a list containing 5: another reference to that same list can append 4 to it. The group total becomes 9 in the old record too; with its old available count of 7, we get the inconsistent total 16 again.

    Here, a reference is another name that lets us reach the same object; giving the list another name does not copy it. To keep the groups, constructing a tuple of integers (5,), then a new tuple (5, 4), avoids changing the old contents. A tuple cannot be extended in place. But a tuple containing a list would still have mutable contents: we must examine the objects it contains, as well as the container.

✿03 Common mistakes

  • “The object is frozen, so it must be valid.”

    Freezing prevents reassignment of its fields after construction; it does not check their meaning. A record containing 9 reserved and 7 available for a capacity of 12 can be frozen and inconsistent. Validate the state when it is created.

    Review the validity rule and construction

  • “To get a new state, I must change the old one.”

    Calculate the new values from the old record, then construct a separate record. The current reference can change while the old record keeps its values. Reassigning the current name does not mutate the old object.

    Compare records S and S′

  • “A frozen field automatically makes all its contents immutable.”

    The field can keep referring to the same list while that list is modified. In our case, replace it with a tuple of integers and create a new tuple for the next reservation. Check the elements too: a tuple of lists is not enough.

    Reread the passage on Python objects

A frozen but inconsistent record

A frozen record shows C = 12, R = 9 and L = 7, in seats. Does it satisfy I? A second record shows C = 12, R = 13, L = -1. Why is checking only the sum insufficient for identifying valid states?

Exercise 2 · Calculation and boundary case

Take exactly the remaining seats

Hint 1

The condition allows q = L. It does not require q to be strictly less than L.

Hint 2

A refused request leaves the starting state intact. All the variants start again from S′.

Compare with the solution

For q = 3 seats, the condition is satisfied. R becomes 9 + 3 = 12 seats; L becomes 3 − 3 = 0 seats. The sum is 12 seats: a full room remains valid.

From S′, requesting 4 seats exceeds the available count by 1 seat. The disallowed calculation would produce 13 reserved and -1 available. Return a refusal and the record (12, 9, 3), with no partial reservation.

The request for 0 seats is accepted under our contract: the values remain (12, 9, 3). We can return the existing object because no value has changed. Immutability does not require an unnecessary copy.

Exercise 3 · Diagnosis and repair

The old record changes despite freezing

A frozen record contains a list of group sizes [5] and an available count of 7 seats. Another name refers to that same list. The program appends 4 to the list to make a reservation and creates a new record with 3 available seats. What problem appears in the old record? Suggest a representation that keeps the groups without this fault, and state what still needs to be checked.

Hint 1

Reread the old list after the append: did freezing the field prevent modification of the object it refers to?

Hint 2

Compare the sum of the groups and the available count in each record. For the repair, choose elements that are themselves immutable.

Compare with the solution

The same list now contains [5, 4] in both records. The group total is 9 seats. The old record keeps 7 available seats; it therefore describes 16 seats for a capacity of 12. Its contents are no longer a snapshot of the starting situation.

Keep the tuple of integers (5,) in the old record and construct the tuple (5, 4) for the new one. The first keeps 5 reserved and 7 available; the second describes 9 reserved and 3 available. The counts in each record sum to the capacity.

You still need to validate the domain of the group sizes, check that their sum matches the reserved count and check the complete invariant. A tuple annotation does not perform this runtime validation on its own. A list inside a tuple would remain mutable.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What is an invariant, and what is its complete form for the room?

A rule required for every accepted or visible state. C is a positive integer; R and L are non-negative integers, in seats, with R + L = C. Checking only the total allows a negative available count through.

Recall 2How can we accept a request q without modifying the initial state?

From a valid state (C, R, L), check that q is an integer and 0 ≤ q ≤ L. Construct and validate (C, R + q, L − q), then select it as the current state. The request is added and subtracted: the sum remains C.

Recall 3Why refuse 8 seats from the initial state, even if the calculated total remains 12?

Only 7 seats remain. The calculation would give 13 reserved and -1 available: the state violates non-negativity. Return an explicit refusal and keep (12, 5, 7).

Recall 4Why are freezing and validation needed separately?

Freezing blocks ordinary reassignment of the fields after construction. Validation checks their values and relationships before accepting the object. A frozen object may have been constructed with inconsistent numbers.

Recall 5Why is a frozen record containing a list an unreliable snapshot?

The list remains mutable, including through another reference to it. For our groups, use separate tuples of integers; also check the elements they contain and the validity rules. Freezing the container does not recursively freeze its contents.
