Level 2 · C041·M5

Transactions and windows

Your goalRecord a transfer as a whole, then calculate a running stock level for each location while keeping every movement.

Before you start
c037-m5 : controlled cleaning · c017-m5 : reproduction protocol · c041-m1 : relational model · c041-m2 : keys · c041-m3 : SQL · c041-m4 : joins and aggregates

✿01 See the idea

A workshop prepares notebooks for its visitors. The storeroom holds 12 and the table holds 5. You move 4 from the storeroom to the table. The computer record needs an outgoing movement and an incoming movement. If only the outgoing movement remains recorded, some notebooks appear to have disappeared.

A transaction brings together writes that we want to commit together. Here, its atomicity means keeping the whole transfer after a commit, or keeping none of its writes after a rollback. An intermediate state can exist while the writing connection is working; it must not become the committed transfer.

Next, you want to read the log again and see the stock level reached at each movement. A window function adds a calculation to each row, using the rows defined by a rule. Unlike an aggregate with grouping, it keeps every movement here. The window is not a fixed period of time: in our case, it extends from the start of the log for the location to the current movement.

This scene and its quantities are fictional. We use SQLite, a relational database engine, with a single writer, integer changes with no missing values, and unique sequence numbers already assigned. The record describes reported movements; checking that the notebooks have actually changed location is a separate check.

The rule to remember

The transaction determines what is committed together; the window determines which rows contribute to the calculation for each movement kept in the result.

✿02 Follow an example

Worked example

Move the notebooks, then read each movement

The mouvements relation contains ordre, lieu and variation. The initial rows are (1, 1, 12) and (2, 2, 5). Record the transfer of 4 notebooks, then find the stock levels using a window sum.

  1. Define the log and the starting state

    ordre is an integer primary key that sets the sequence of events here, with no physical unit; it is not a time. lieu is a code with no unit: 1 denotes the storeroom, 2 the table. variation is an integer number of notebooks: positive for an incoming movement, negative for an outgoing movement. None of these columns contains a missing value.

    The initial rows represent the opening stock, starting from 0 notebooks recorded for each location. All the history needed is kept. We assume that these rows are already committed, that no one else is writing, and that the movement is allowed: 4 ≤ 12 notebooks.

    R denotes the initial stock in the storeroom, T the initial stock on the table, and d the quantity transferred; all are measured in notebooks. R′ and T′ denote the stock levels after the transfer. The prime symbol only indicates the next state. The initial check gives R + T = 12 + 5 = 17 notebooks.

  2. Set a common boundary for the writes

    On the same SQLite connection, running BEGIN; opens the explicit transaction. The next sequence numbers are 3 for the outgoing movement and 4 for the incoming movement. These sequence numbers are unique in our log.

    SQL statement: INSERT INTO mouvements (ordre, lieu, variation) VALUES (3, 1, -4);

    SQL statement: INSERT INTO mouvements (ordre, lieu, variation) VALUES (4, 2, 4);

    If the writes and checks succeed, running COMMIT; commits the whole set. If a write fails or a check rejects the transfer, stop the remaining steps and run ROLLBACK; to roll back the transaction that is still active. In SQLite, a constraint error on a statement does not necessarily roll back the previous statements: the program must handle the failure without proceeding to COMMIT.

    Without this explicit boundary, writes committed separately can leave only the outgoing movement recorded. Atomicity concerns changes in the database: it does not move the notebooks itself or guarantee that the values entered comply with the business rule.

  3. Calculate the stock levels and justify the check

    The outgoing movement is calculated as 0 − 4 = -4 notebooks. The storeroom loses this quantity and the table receives it. We add signed changes to the starting stock levels:

    R′=R−d=12−4=8 carnets
    T′=T+d=5+4=9 carnets

    The net change is -4 + 4 = 0 notebooks. The total after the transfer is 8 + 9 = 17 notebooks, the same as before. This conservation check comes from the scene: the transfer neither creates nor destroys notebooks. You must also check the locations, the signs and the absence of negative stock; the total alone would not detect a movement in the wrong direction.

  4. Choose the partition, order and frame

    After commit, the query for reading the log is:

    SQL statement: SELECT ordre, lieu, variation, SUM(variation) OVER (PARTITION BY lieu ORDER BY ordre ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumul FROM mouvements ORDER BY ordre;

    SUM(variation) adds the changes. Here, OVER turns this aggregate into a window function: each row keeps its columns and receives a cumul column. PARTITION BY lieu separates the locations; each running total starts with its own history.

    ORDER BY ordre inside OVER sets the progression of the calculation. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW specifies the frame: all rows in the partition from its first row up to and including the current row. The unique sequence numbers avoid ties that would need to be resolved. The final ORDER BY sorts the display; it does not replace the one used for the calculation.

    If C denotes the running total for the current location and v its current change, both measured in notebooks, the calculation amounts to progressing through each partition as follows:

    Caprès=Cavant+v

    At the start of each partition, C is 0 notebooks. This recurrence describes our cumulative sum, rather than every possible window function. Reading does not modify any recorded row.

  5. Work through every row of the result

    Sequence 1, storeroom: the frame contains only the opening movement. Running total = 0 + 12 = 12 notebooks.

    Sequence 2, table: its partition starts. Running total = 0 + 5 = 5 notebooks. The running total for the storeroom does not enter this calculation.

    Sequence 3, storeroom: its frame contains the opening movement and the outgoing movement. Running total = 12 + (-4) = 8 notebooks.

    Sequence 4, table: its frame contains the opening movement and the incoming movement. Running total = 5 + 4 = 9 notebooks.

    The result therefore keeps 4 rows. At sequence 3, the storeroom column shows a step in the log; it is not the overall committed outcome of the transfer. For the final stock levels, take the last running total for each location: 8 and 9 notebooks. Adding all the running totals would count several historical states.

  6. Check another way and decide where to filter

    SQL statement: SELECT lieu, SUM(variation) AS stock FROM mouvements GROUP BY lieu;

    This other query produces 2 rows, one per location: 8 and 9 notebooks. It finds the last running totals by summing all movements for each location, without working through the intermediate states. This check is independent of the progression of the window.

    A WHERE in the query that calculates the window filters before that calculation. Adding WHERE ordre > 2 would therefore remove the opening movements: the running totals would be -4 in the storeroom and 4 on the table. They would represent recent changes rather than complete stock levels.

    To display only these recent movements while keeping the stock from the full history, calculate the window in an inner query, then filter its result in an outer query:

    SQL statement: SELECT ordre, lieu, variation, cumul FROM (SELECT ordre, lieu, variation, SUM(variation) OVER (PARTITION BY lieu ORDER BY ordre ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumul FROM mouvements) AS historique WHERE ordre > 2 ORDER BY ordre;

    The parentheses after FROM delimit this inner query, named historique; the outer query reads its cumul column, already calculated from the full history. It displays 2 rows, with 8 and 9 notebooks. The position of the filter therefore changes the data used in the calculation, as well as how much appears on screen.

Explain it in your own words

Hide the queries. Explain what would prevent an outgoing movement from being committed on its own, then reconstruct the partition, order and frame needed for the running total. Why would a filter placed before the window lose the opening stock?

✿03 Common mistakes

  • “An error on the incoming movement always rolls back the entire outgoing movement.”

    A statement can fail while the transaction remains active with the previous write. Stop the remaining steps, check the failure and roll back with ROLLBACK. The boundary does not replace error handling.

    Review how the transaction starts and its possible outcomes

  • “OVER is enough: the sum will know which stock level I want.”

    You must define which rows contribute. Without PARTITION BY lieu, the running total would mix the storeroom and the table: at the outgoing movement, it would be 13 notebooks instead of 8. Also specify the order and the frame up to the current row.

    Find the separate running totals in the diagram

  • “WHERE only removes rows from the display, so the running total stays correct.”

    In the same SELECT, WHERE removes rows before the window. Filtering out the opening movements gives -4 and 4 here, rather than the stock levels. First calculate from the complete log in the inner query, then filter the result.

Exercise 2 · Diagnosis · write failure

A duplicate key in the middle of the transfer

Start again from the initial log. BEGIN succeeded, then the outgoing movement with sequence number 3 was inserted. The incoming movement mistakenly attempts the same sequence number 3: SQLite rejects this duplicate primary key, rolling back only that statement. What must the program do? What stock levels would remain after an incorrect COMMIT? And after the correct rollback?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Distinguish the rejected statement from the transaction that is still open.

Hint 2

With only the outgoing movement, the storeroom has already lost 4 notebooks within this transaction, while the table has received nothing.

Compare with the solution

The program must stop the remaining steps and run ROLLBACK on the connection whose transaction is still active. It must not report the transfer as committed or proceed to COMMIT.

An incorrect COMMIT after this rejection would keep the outgoing movement: 8 notebooks in the storeroom and 5 on the table, making 13 notebooks. Yet the total should be 17. The key error alone therefore does not guarantee a return to the starting state.

After the correct ROLLBACK, the outgoing movement is rolled back: back to 12 and 5 notebooks, total 17. The rejected attempt added no incoming movement. A retry must be prepared as a new complete transaction, after fixing the cause.

Check your reasoning

  • Name ROLLBACK and specify that it applies to the transaction that is still active.
  • Calculate the incorrect case 8 + 5 = 13 notebooks.
  • Recover the initial stock levels after rollback and reject a false success message.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What outcomes do you plan for the transfer writes?

COMMIT keeps the writes of the successful transaction; ROLLBACK rolls back those of the transaction that is still active. A statement error requires explicit handling and never justifies proceeding blindly to commit.

Recall 2Why use a window rather than GROUP BY to read the log again?

The window keeps every movement and adds its running total. Here, GROUP BY lieu reduces the movements to a single summary row per location.

Recall 3What do the partition, order and frame of our sum define?

PARTITION BY lieu separates the histories. ORDER BY ordre sets the progression within each history. ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW includes the rows from the start up to and including the current row.

Recall 4Why filter recent movements after calculating the stock level?

A WHERE in the same SELECT removes the opening movements before the window. An inner query calculates from the whole history; the outer query then filters the movements displayed.

Recall 5What does the conserved total establish, and what still needs checking?

It checks that no notebooks have been created or lost in the recorded numbers. You must still check the signs, the locations, the permitted stock levels and the actual movement; the transaction alone does not prove these facts.
