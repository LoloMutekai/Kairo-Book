Keys

Your goalChoose what identifies a row, check a reference between tables, and justify when a key must combine several columns.

Before you start
c037-m5 : controlled cleaning · c017-m5 : reproduction protocol · c041-m1 : relational model

✿01 See the idea

At the bicycle repair shop, Camille asks for an update on a repair job. But the register contains several clients named Camille. A name helps you speak to someone; it does not always let you find their row. So the shop assigns a client identifier, then copies that identifier onto the repair job records.

All people, identifiers, and records in this scene are fictional. The Clients table contains the rows (41, Camille), (42, Camille), and (43, Sana), in the columns id_client and nom. A row represents a client; a column describes the same attribute for all clients.

The Interventions table contains the columns id_intervention, id_client, and rang_local. Its rows are (701, 41, 1), (702, 41, 2), and (703, 42, 1). In the diagrams, “ticket” is short for id_intervention and “rank” is short for rang_local. Each repair job concerns exactly one registered client.

A primary key identifies the row in its own table. A foreign key references a key in a target table: here, id_client in Interventions refers to id_client in Clients. The same client can appear on several records. Repeating their reference does not create a new client.

The rule to remember

To identify, require a value that is present and unique; to reference, check that the value finds its target. Repetition can be forbidden in the primary key and perfectly normal in the foreign key.

✿02 Follow an example

Worked example

Check the keys in the shop register

Use exactly the rows in the diagrams. The shop forbids missing identifiers and identifiers reassigned to another row. It also assigns each repair job a rang_local that is present and never reused for the same client. Names can repeat and change. Let us check the keys and references before adding any new record.

  1. Set the rules before counting

    A candidate key is a minimal set of columns whose present values uniquely identify a row in every state allowed by the register’s rules. Minimal means that removing a column loses this guarantee. A primary key is the candidate key chosen as the table’s main reference. The other candidate keys remain possible identifiers.

    Here, Clients chooses id_client and Interventions chooses id_intervention. We assume these fields are present and unique, with compatible types for references. A missing cell, often written NULL in a database, represents missing information; it is neither an identifier nor the number 0. Every client link is mandatory in our scene.

    N denotes the number of rows in a table; D(K), the number of distinct values held in columns K; E(K), the number of repeated occurrences beyond the first. N, D, and E are counts of rows or values, with no physical unit. K denotes a column or a group of columns, rather than a number. We first check that K contains no missing cells.

  2. Rule out the name, even if it looks familiar

    Clients contains 2 rows for Camille and 1 row for Sana, giving N = 2 + 1 = 3 rows. Keeping each name only once leaves Camille and Sana: D(nom) = 1 + 1 = 2 distinct values. Subtraction measures what is lost by grouping people with the same name.

    E(K)=N−D(K)

    Thus E(nom) = 3 − 2 = 1 repeated occurrence. The name fails as a key. Direct check: the request “Camille” matches 2 rows, whereas a key must select at most 1. E does not count pairs of identical rows; it counts occurrences after the first.

  3. Validate the identifier and understand minimality

    The values 41, 42, and 43 are all present and different. D(id_client) = 3 values and E(id_client) = 3 − 3 = 0 repetitions. Independent check: comparing each identifier with all those that follow finds no equality.

    So id_client suffices to identify the observed rows. The assignment rule, which must be enforced during changes, guarantees future uniqueness. A sample without duplicates would not prove this guarantee. Adding nom to id_client does not make the key more minimal: removing nom still leaves a sufficient identifier. The group (id_client, nom) is an identifying superset, called a superkey, but is not a minimal candidate key.

    A numeric identifier is a label: adding 41 and 42 makes no sense as a way to find a client. Sorting the rows differently does not change their identity. Under our rules, correcting the spelling of the name preserves id_client.

  4. Check each reference in the right direction

    A foreign key is a constraint on source columns: every supplied value must match a key in the target table. The target can be a primary key or another key whose uniqueness is guaranteed. Here, Interventions.id_client references Clients.id_client and must also be present, since a client is mandatory for each repair job.

    For ticket 701, look for 41 in Clients: 1 row matches. For 702, look for 41 again: 1 row matches. For 703, look for 42: 1 row matches. The target key guarantees at most 1 match; the mandatory reference requires exactly 1.

    There are therefore 3 valid references for 3 repair jobs. Repeating 41 in Interventions is allowed: the target in Clients must be unique. Sana, identified by 43, can have no repair jobs. A foreign key does not require every client to be used.

  5. Count anomalies and check another way

    Let O be the number of orphaned repair jobs, meaning those whose mandatory reference has no target, and V the number of repair jobs whose target exists. Our references are all supplied and the target key is unique: each repair job belongs to exactly one of these groups. Hence O = N − V = 3 − 3 = 0 orphaned rows.

    Another check: the list of references is 41, 41, 42; each appears in the target list 41, 42, 43. The 2 distinct source values suffice to check existence, but the total V counts all 3 repair jobs, rather than just the distinct clients.

    N − D(id_client) in Interventions equals 3 − 2 = 1 repeated reference. This is not O: repeating an existing client need not create an orphan. Deleting a client that is still referenced without a defined way to handle this creates a reference problem. Our rules require rejecting this deletion while repair jobs still refer to the client.

  6. Recognize a composite key

    The rang_local is 1 for each client’s first repair job, then 2 for the next. The pairs (id_client, rang_local) are (41, 1), (41, 2), (42, 1). They give 3 distinct values for 3 rows. The stated rule forbids assigning the same rank to the same client again.

    This candidate key consists of 2 columns. Check its minimality: removing rang_local makes tickets 701 and 702 indistinguishable because they carry 41; removing id_client makes 701 and 703 indistinguishable because their rank is 1. The components fail individually; the complete pair suffices.

    Interventions thus has several candidate keys, including id_intervention and (id_client, rang_local), but chooses a single primary key. The primary key chosen here is id_intervention. The constraint on the pair must also remain guaranteed; adding the ticket number to it would no longer be minimal.

  7. Separate the finding from the guarantee

    Checking the current rows finds 0 repetitions of the client identifier, 0 orphaned repair jobs, and a minimal pair for identifying repair jobs locally. The data satisfy the stated rules. This does not prove that software will automatically block the next incorrect entry.

    The design must become constraints that are actually enforced: presence, uniqueness of keys, and existence of targets. We will learn how to write them in SQL in the next unit. For now, the expected outcome is to be able to decide, row by row, what must be accepted or rejected.

Explain it in your own words

Without looking at the tables, explain why Camille causes a problem in Clients, why repeating the reference to that client does not cause the same problem in Interventions, and why a rank only suffices when combined with the client.

✿03 Common mistakes

  • “I see no duplicates, so this column will always be a key.”

    Distinguish the observed rows from the rules for all allowed states. A check can refute a key with a counterexample; the absence of a counterexample today provides no guarantee for tomorrow. State the assignment rule, mandatory presence, and uniqueness that must be enforced.

    Revisit the identifier and its guarantee

  • “A foreign key must never repeat.”

    Tickets 701 and 702 concern the same client 41. Repetition is allowed in the source. Look for a single target in Clients for each repair job; distinguish the count of distinct clients from that of valid references.

    Compare the boxed columns in the diagrams

  • “If the pair is unique, each of its columns is unique.”

    Client 41 repeats and rank 1 repeats. Compare the complete pairs, then remove a column at a time to check minimality. A composite key does not promise uniqueness of its individual components.

Exercise 1 · Direct application

Find Camille after sorting

The Clients table is sorted by name, then displayed in reverse order. Client 42 has Camille corrected to Camila. Can their row be identified by its old position, by their name, or by id_client? Also recalculate the number of repeated occurrences of the name before the correction.

Hint 1

A position depends on the display; look for what our rules preserve when the name changes.

Hint 2

Before the correction, count the rows, then the names with each kept only once.

Compare with the solution

id_client = 42 continues to identify the same row. Sorting changes a position, rather than the identity; the name can change and was already nonunique. The old position and the old name are therefore unreliable keys for this register.

Before the correction: 3 rows and 2 distinct names, giving 3 − 2 = 1 repeated occurrence. After the correction, the names may all seem distinct in this extract; the rules still allow future clients with the same name.

Check your reasoning

  • Retain the client identifier despite sorting and the name change.
  • Justify the subtraction by explaining what the counts mean.
  • Do not treat a display with no shared names as a guarantee of uniqueness.

Exercise 2 · Diagnosis and repair

A new ticket, a missing client

The record (704, 44, 1) is proposed, in the order id_intervention, id_client, rang_local. No other client has been added. The ticket is new. Should the record be accepted? Calculate the number of orphans if it were accepted. The verified case file then indicates that it actually concerns client 42 and rank 2 for that client: check this repair.

Assisted answer: try this exercise without help later.

Hint 1

A new primary key does not guarantee the existence of the foreign key’s target.

Hint 2

Look for the stated client in Clients, then also check the client–rank pair proposed as a repair.

Compare with the solution

704 is none of the existing tickets: the ticket identity poses no obstacle. But 44 does not appear in Clients. The mandatory reference fails; the proposed record must be rejected. Do not create an extra fictional person just to pass the check.

If it were accepted, N would be 3 + 1 = 4 repair jobs and V would remain 3. We would have O = 4 − 3 = 1 orphaned repair job.

The repair is based on the verified case file: (704, 42, 2). Client 42 exists and the pair (42, 2) is still available. All references become valid: V = 3 + 1 = 4, so O = 4 − 4 = 0. Choosing an existing identifier at random would have hidden the assignment error without repairing it.

Check your reasoning

  • Check the ticket key and the client reference separately.
  • Find the orphan by counting repair jobs, without deriving a rate.
  • Base the correction on the case file and check the client–rank pair.

Exercise 3 · Independent justification

Identify without the global ticket number

Using the shop’s initial rows, we want to use the pair (id_client, rang_local) as the primary key in place of id_intervention. The rule remains: each rank is present and never reused for the same client. Justify the pair’s uniqueness and minimality. Then imagine a column nom_du_client that copies the name from Clients: would the group (id_client, rang_local, nom_du_client) be a minimal candidate key?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Write the pairs from the initial rows and find two rows that each component, taken alone, makes indistinguishable.

Hint 2

For the longer group, ask whether removing nom_du_client destroys identification.

Compare with the solution

The pairs (41, 1), (41, 2), and (42, 1) are all different: 3 pairs for 3 rows. The assignment rule guarantees that this uniqueness remains required when rows are added; both components must be present.

id_client alone makes tickets 701 and 702 indistinguishable. rang_local alone makes 701 and 703 indistinguishable. Removing either of the 2 columns therefore loses uniqueness: the pair is minimal. It can be chosen as the primary key, provided these rules are enforced.

Adding nom_du_client gives a group that still identifies rows, but is not minimal: the pair suffices without the name. This group is a superkey. A composite primary key remains a single primary key; its columns do not become separate primary keys.

Check your reasoning

  • Present the complete pairs and the rule that guarantees their uniqueness.
  • Give a specific counterexample for each column on its own.
  • Explain why adding the name fails the minimality requirement.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does a candidate key require beyond an extract with no duplicates?

Present values that identify each row in every allowed state, using a minimal set of columns. The rules must guarantee future uniqueness; a clean extract is not enough.

Recall 2How do candidate keys and primary keys differ?

A candidate key is a possible minimal identifier. The primary key is the one chosen as the table’s main reference; it can combine several columns.

Recall 3Why is repeating a client across several repair jobs allowed?

The foreign key requires a unique target to exist, rather than requiring each source reference to be unique. Several repair jobs can refer to the same client. Here, presence is also mandatory; other models may allow a missing reference.

Recall 4How can you prove that a composite key is minimal?

Check the uniqueness of the entire combination, then show that no column can be removed without losing the guarantee of identification. In our pair, the client repeats and the rank repeats, but their combination does not.

Recall 5What does a check with no orphaned repair jobs prove?

In the rows checked, every mandatory reference finds its target. This proves neither that the chosen client is the right person nor that a future error will be blocked by the software.
