Level 2 · C023·M5

Keyboard, contrast and unavailable states

Your goalDesign a way to save a record that can be reached with the keyboard, read and understood even when the action is unavailable.

Before you start
c021-m5 : origin, authentication and authorization · c018-m5 : contract tests and test doubles · c023-m1 : HTML, CSS, DOM and events · c023-m2 : JavaScript, TypeScript and message types · c023-m3 : React components and state · c023-m4 : live updates and errors

✿01 See the idea

You are preparing a workshop record titled “Repair the shelf”. The form contains the Title field, the Save button and the Help button. The mouse is set aside. You must be able to reach the control, identify where you are, activate it, then understand why it temporarily stops responding.

Focus is the current target of the keyboard. A visible outline marks it: it is neither the pointer position nor proof that the action is authorized. Tab moves forward between controls; Shift with Tab moves backward. On an available native HTML button, Enter or Space activates it. We keep these behaviors instead of turning decorative text into a fake button.

While saving, the button may remain visible without being able to accept another request. The state must then be announced, its reason explained and the action actually prevented. A pale color alone does not tell you whether the title is missing, an operation is waiting for its response or a failure has occurred. Useful text must remain readable.

The entire scene, its luminances and its traces are fictional. We are designing a simple form within a page, without a modal window. The drawings are static: they explain the contract but do not implement it. This unit concerns saving this record, rather than general accessibility certification.

The rule to remember

Make the control reachable, the focus identifiable and the reason for blocking explicit; check readability and the actual prevention of a new submission separately.

✿02 Follow an example

Worked example

Saving a record without losing your place

The mockup contains 1 field and 2 buttons, in the order Title, Save, Help. The title is present. For the calculation only, the background has a relative luminance of 0.95, the dark text 0.05 and the greyed text 0.35. The design criterion chosen here is a ratio of at least 5 for useful text. Let us work through keyboard navigation, contrast and then protection against repeated submission.

  1. Giving controls a name and behavior

    Title is an input with an associated visible label. Save is a button of type submit inside a form. Help is a button of type button: it displays a local explanation without submitting the record. These element names refer to native HTML controls, which provide their basic keyboard behavior.

    Place these elements in reading order and avoid using a positive tabindex to create a competing order. An outline appears on the control receiving keyboard focus, using the CSS pseudo-class focus-visible. Removing this outline without a replacement removes the marker we need.

    The message placed near Save describes the reason for its state. Its identifier is linked to the button through aria-describedby, which associates an accessible description with the control. This message stays visible: a tooltip shown only on mouse hover is not enough.

  2. Distinguishing a keyboard stop from an allowed action

    In our area, 1 field + 2 buttons give 3 Tab stops. We are counting controls, without a physical unit. From Title, Tab reaches Save; another press reaches Help. Shift with Tab returns to Save. Enter in the field can also submit the form: the check must therefore cover more than just the button click.

    The choice for this mockup: while waiting, Save remains focusable and carries aria-disabled with the value true, meaning “action unavailable”. This attribute communicates the state to assistive technologies; it does not remove focus or prevent activation by itself. There are still 3 stops, but the shared submission handler must reject the action.

    Another option is the HTML disabled attribute on the native button. It prevents user activation and removes the button from sequential navigation: here 3 − 1 = 2 stops. This choice can be suitable if the reason for blocking remains accessible elsewhere and if what happens to focus is checked when the button becomes disabled. Neither attribute replaces server-side authorization.

  3. Defining the quantities before calculating contrast

    A relative luminance L is a number without a unit here, from 0 for black to 1 for white, already obtained after converting colors to linear values. We are given background L = 19/20 = 0.95 and text L = 1/20 = 0.05. These are not red, green or blue channel values to insert directly into the formula.

    In the contrast ratio C, Lc denotes the lighter luminance of the compared surfaces and Ls the darker one. The constant a equals 1/20 = 0.05. All these numbers, as well as C, are without a unit. In particular, the constant avoids a 0 denominator for black. Here the background is the light surface.

    C=Lc+aLs+a

    Our criterion C ≥ 5 is an explicit choice for this exercise, rather than a statement of a universal regulatory threshold. The calculation assumes opaque text on a uniform background. An image, transparency or a different theme requires checking the colors actually produced by compositing.

  4. Calculating, then checking the greyed text

    Add the same constant to the luminances before dividing. The numerator equals 0.95 + 0.05 = 1.00; the dark-text denominator equals 0.05 + 0.05 = 0.10.

    C=1.000.10=10

    The ratio is therefore 10 to 1, above our criterion of 5. Check by multiplication: 10 × 0.10 = 1.00, the numerator. We do not subtract the luminances to obtain this ratio.

    With greyed text, Ls = 7/20 = 0.35. Its denominator equals 0.35 + 0.05 = 0.40; the ratio becomes 1.00 ÷ 0.40 = 5/2, or 2.50 to 1. It is below 5. For our mockup, we therefore keep a readable text color for the reason for blocking and write “Saving in progress”. We do not grey out all the useful information.

    This calculation concerns neither the pixels in the drawings above nor the actual colors of an application. It compares the supplied luminances. It does not validate the focus outline either: its contrast with neighboring surfaces must be checked separately.

  5. Closing the gate before starting the save

    Let V be the proposition “the title, after trimming spaces from its ends, is not empty” and B the proposition “a submission is already in progress”. A means “allow a new request to be sent”. These are logical values, without a unit. The symbol ∧ is read as “and”; ¬ is read as “not”.

    A=V∧¬B

    Initially V is true and B is false: the action is allowed. The submission handler, also called by Enter in the field, checks this rule. If it is false, the handler sends nothing. If it is true, the handler immediately locks the submission in progress before any asynchronous work, keeps the submitted title and starts saving.

    In React, a visual state update may wait for a render. To also block an activation arriving before that render, the check and the closing of the gate share a local lock that is changed immediately, for example a mutable reference. The displayed state then reflects this lock. A check performed only when rendering the button is not enough to describe this protection.

    While waiting, the field is read-only, with readOnly: the title remains available to read and focusable, but it is not changed while being sent. The control that had focus keeps it, including the field if the submission came from there. Save keeps its description and its outline when focused, while being marked unavailable. Help remains usable. A persistent message area, role status, placed outside the busy form, announces “Saving in progress” without taking focus. The aria-busy attribute can signal that the form is busy; it does not block an action by itself.

  6. Counting attempts and requests sent separately

    The fictional trace contains 2 successive submission attempts before any response. On the first, V is true and B false: the handler closes the gate and sends 1 request. On the next, B is already true: it sends 0 additional requests, even if the attempt comes from the keyboard.

    Total sent: 1 + 0 = 1 request. Local rejections: 2 − 1 = 1. Trace check: 1 request sent + 1 rejection = 2 submission attempts. This count describes our rule on this synthetic trace, without claiming a real success rate.

    Check the button path and the path for submission from the field separately. In both cases, the same handler guards the gate. Local protection for this form does not demonstrate that the server withstands another client, a page reload or a repeated request from outside this page.

  7. Returning to an understandable state

    In our trace, the first operation responds with a confirmed failure before any write. The lock is then released, the field becomes editable again and the title is kept. The message explains the failure and suggests trying again. A role alert area makes this error detectable by assistive technologies. Focus stays on the control used; it is not arbitrarily sent back to the top of the page.

    An explicitly confirmed success would allow “Record saved” to be announced. A missing response instead means “outcome unknown”: it does not allow a promise that nothing was saved. Before retrying in a way that could create a duplicate, a state check or a suitable server mechanism is needed, outside this unit.

    The final check of the contract includes several observations: navigating through and out of the area with the keyboard, seeing focus, understanding the name and the reason for blocking, rejecting a new submission while waiting and finding the input again after failure. The contrast calculation replaces none of these observations. Here we have prepared their criteria; no actual navigation through this mockup is claimed.

Explain it in your own words

Hide the steps. Explain where focus stays while waiting and why aria-disabled is not enough. Then redo the contrast calculation for the greyed text and explain what the count of requests sent proves. Distinguish a confirmed failure from a missing response.

✿03 Common mistakes

  • “The button is pale, so everyone understands that it is blocked.”

    A color gives neither the reason nor a way to resume. Keep a readable message associated with the button and an explicit state. With our fictional luminances, the greyed text reaches only 2.50 to 1, below the chosen criterion of 5.

    Revisit the calculation and the waiting message

  • “aria-disabled already blocks the keyboard just like disabled.”

    aria-disabled describes unavailability; the control can remain focusable and its events can reach the handler. The handler must reject the submission. disabled on a native button prevents user activation and removes it from Tab navigation. Choose the focus policy deliberately.

    Compare the stops and the submission gate

  • “The click works, so the form is accessible.”

    A click does not show Tab order, the outline, submission through Enter or whether the feedback is perceived. Repeat these paths separately and also check the outcome of saving. A color or an event received is not confirmation that the record was saved.

    Build the checks for the last exercise

Exercise 2 · Application · calculation and checking

How light can the text be?

The background keeps its luminance 0.95 and a equals 0.05. We want text darker than the background and a contrast C ≥ 5, according to the mockup criterion. Find the highest possible luminance for the text. Check the result using the full formula, then decide whether grey 0.35 is suitable.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

At the limit, the ratio equals exactly 5. Its numerator remains 1.00.

Hint 2

Find the denominator by division, then subtract the constant a to recover the text luminance.

Compare with the solution

The numerator equals 0.95 + 0.05 = 1.00. At the contrast limit, the denominator must equal 1.00 ÷ 5 = 0.20. This division reverses the product C × denominator = numerator.

The denominator also includes a. The text luminance is therefore at most 0.20 − 0.05 = 0.15, or exactly 3/20. The background does indeed remain the lighter surface.

C=0.95+0.050.15+0.05=5

Even lighter text increases the denominator and reduces the ratio. Grey 0.35 exceeds 0.15: it does not meet the chosen criterion. This result assumes the supplied luminances and a uniform background; it does not remove the need to examine an actual rendering.

Check your reasoning

  • Justify dividing by 5 and subtracting a.
  • Obtain 0.15 without a unit and recover C = 5 by substitution.
  • Explain the direction of the inequality and limit the conclusion to our criterion.

You then retry through Enter from the field, without changing the title; this new operation succeeds with confirmation. Give the numbers of submission attempts, requests sent and local rejections. Assisted answer: try this exercise without help later.

Hint 1

A local rejection does not produce an operation waiting for a response. The lock is released only after the confirmed outcome described here.

Hint 2

Separate what the handler receives, what it sends and what the response confirms.

Compare with the solution

The first part gives 1 request sent and 1 rejection for 2 submission attempts. After the confirmed failure, the lock is released. The new attempt is accepted: 1 + 1 = 2 requests sent in total, for 2 + 1 = 3 submission attempts. The rejection count remains 1. Check: 2 + 1 = 3.

The expected feedback is “Saving in progress”, then an explained failure with the title kept, then another wait, then “Record saved” after confirmation. The form becomes editable again after each completed operation. Activation from the field must go through the same check as activation from the button.

Prepare a navigation sequence in which Tab and Shift with Tab reach the controls in order, focus remains identifiable during state changes and it is possible to leave the area. Also check that Enter while waiting sends no additional request, then that Enter after the confirmed failure allows a retry. Check the visible messages and how assistive technology presents them; attributes in the code alone do not prove that they are perceived.

The synthetic count checks our scenario without proving actual persistence. If the first response had merely disappeared, the outcome would have had to remain unknown and the duplicate risk resolved before concluding that a retry was safe.

Check your reasoning

  • Distinguish 3 submission attempts, 2 requests sent and 1 rejection.
  • Keep the input and explain when the lock can be released.
  • Prepare separate observations of the keyboard, focus, message and outcome.
  • Do not turn a missing response into a confirmed failure.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1In the record, what does focus mean and what does it not prove?

It identifies the current target of the keyboard, made visible by an outline. A button can have focus while announcing an unavailable action; this does not prove that a submission is authorized.

Recall 2Why does aria-disabled replace neither disabled nor the submission gate?

aria-disabled describes the state and can leave the button in Tab navigation; it does not block its events. disabled on a native button prevents user activation and removes it from Tab navigation. In our focusable choice, the shared handler must reject the action as soon as the title is missing or a request is in progress.

Recall 3How do you calculate the contrast of our luminances, and what data do you need?

Take the lighter relative luminance Lc and the darker one Ls, already linearized, then C = (Lc + a)/(Ls + a), with a = 0.05. C is without a unit. For our background 0.95 and our text color 0.05, C = 10. A raw color channel does not replace a luminance.

Recall 4Why close the gate before asynchronous work and check the whole form?

An additional activation can arrive before the next render, and Enter in the field can submit without a button click. A lock changed immediately and shared by the submission handler prevents a new local request from being sent while waiting. This lock does not provide a general server guarantee.

Recall 5What evidence should be kept separate before claiming that the record works accessibly?

Separate the contrast calculation, actual keyboard navigation, focus identification, understanding and presentation of messages, rejection of a new submission and confirmation of the write. Reading code or receiving an assisted answer demonstrates neither these effects nor an acquired skill.
