Header and section table

Your goalFollow a header to a table entry, then check the portion of the file that it describes, without executing the file.

Before you start

✿01 See the idea

You receive a logbook of readings stored in a file. Where are the key and the readings? Searching randomly through the bytes would be like leafing through a logbook without a contents list. Its header acts as a cover page: it tells you where the list of parts begins. This list is the section table.

Here, a section is a portion of the file. A table entry is its record: it contains an identifier, a starting position and a size. The record for the readings describes their location; it does not contain the readings themselves. You must therefore distinguish the position of the record from the position of the section. These records and the header are metadata: information that describes the content.

In our logbook, the header occupies 8 bytes and specifies 2 entries of 6 bytes starting at position 8. The key starts at 20 and the readings at 28. These positions count bytes from the start of the file, whose first position is 0.

The logbook, its numbers and its format are fictional. We define a small set of rules for learning to follow a table, independently of real formats. We will read only its structure. Real files may have other fields, tables placed elsewhere and sections with no stored bytes.

The rule to remember

First read the format rules and the header; check the bounds of the entire table; locate its entries; check the bounds of each described section separately.

✿02 Follow an example

Worked example

Find the readings without opening their content

The actual available length of the logbook is L = 40 bytes. Its header contains, in order, the bytes 82, 86, 2, 0, 8, 0, 6, 0. All numeric byte values are written in base ten. Let us check where the table and the sections it specifies are located.

  1. Establish the format rules before decoding

    H = 8 bytes is the required size of the header, which starts at 0. The expected signature is the byte pair 82, 86, in that order. A signature is a recognition marker defined by the format, not a guarantee of integrity. We require L ≥ H before reading any fields; here 40 ≥ 8.

    After this pair come 3 unsigned integers of 2 bytes each: they represent nonnegative integers. They use little-endian order, meaning the least significant byte comes first. N counts the entries, T gives the absolute offset of the table in bytes, and E gives the number of bytes per entry. They start at positions 2, 4 and 6, respectively. The format requires E = 6 bytes: identifier, section start and section size, each occupying 2 bytes.

    In this format only, the table immediately follows the header; sections with strictly positive sizes follow the table in entry order, with no gaps or overlaps, and fill the rest of the file. Identifier 1 means key and 2 means readings. These rules come from our chosen convention; they cannot be inferred by looking at the bytes.

  2. Read the header fields

    For an integer v encoded in 2 bytes, b is the least significant byte and h the most significant byte. Each is an integer from 0 to 255. The value of v is b + 256 × h; its unit depends on the field. For N, it is a count of entries; for T and E, it is a count of bytes.

    v=b+256×h

    The signature matches. The following pairs give N = 2 + 256 × 0 = 2 entries; T = 8 + 256 × 0 = 8 bytes; E = 6 + 256 × 0 = 6 bytes per entry. T = H and the stride E matches the format rules. The fields are consistent; the presence of the table still needs checking.

  3. Check the bounds of the entire table before reading an entry

    B denotes the length of the table in bytes. U denotes its exclusive end boundary, measured from the start of the file. N has no physical unit; N × E counts the bytes occupied by all the entries. We then add T to position this length within the file.

    B=N×E;U=T+B≤L

    B = 2 × 6 = 12 bytes. U = 8 + 12 = 20 bytes. The table occupies [8, 20): the round bracket on the right excludes the end. Since 20 ≤ 40, it fits entirely within the file. All these bytes must be available, not just the start of the table.

  4. Find the records, then decode what they specify

    i is the index of an entry, with no unit, counted from 0. It satisfies 0 ≤ i < N. A with subscript i is the starting position of this entry, in bytes from the start of the file. The product i × E skips i complete records; adding T reaches the correct position.

    Ai=T+iE

    The first record, with index 0, starts at 8. Its bytes are 1, 0, 20, 0, 8, 0. The same decoding gives identifier 1, start 20, size 8 bytes: this is the key.

    The last record has index N − 1 = 1. The skip is 1 × 6 = 6 bytes; its position is 8 + 6 = 14. It ends at 14 + 6 = 20, exactly the exclusive end of the table. Its bytes are 2, 0, 28, 0, 12, 0: identifier 2, start 28, size 12 bytes.

  5. Check the bounds of each section separately

    For the section under consideration, o is its absolute starting offset, s its size, and f its exclusive end boundary; o, s and f are expressed in bytes. To check that it is present, we require 0 ≤ o ≤ L and 0 < s ≤ L − o. Here this is equivalent to checking f = o + s ≤ L with a positive size. The table may be present while a section it specifies is missing.

    f=o+s≤L

    Key: 20 + 8 = 28. Its interval is [20, 28); the last included byte is at 28 − 1 = 27. Readings: 28 + 12 = 40. Their interval is [28, 40); the last included byte is at 40 − 1 = 39. Each end is less than or equal to L = 40.

  6. Check the specified layout

    Now let us check the rules specific to the logbook: the table starts at H = 8 and ends at 20, exactly at the start 20 of the key. The key ends at 28, exactly at the start 28 of the readings. Their end 40 is the file boundary 40. The portions meet without sharing a byte.

    An independent check adds the lengths: sections, 8 + 12 = 20 bytes; metadata, 8 + 12 = 20 bytes; together, 20 + 20 = 40 bytes. This gives L again. This total would not be enough to detect overlapping sections: the boundaries checked just before are also necessary.

  7. Check the last section using the remaining space

    Start from the end of the file instead of adding a start and a size. After offset 28, there are 40 − 28 = 12 bytes left. This is exactly the size 12 specified for the readings. This check reaches the same conclusion through subtraction.

    Equality f = L is allowed: the end is excluded. The byte at position 40 does not exist in this file; the byte at position 39 does. Confusing a boundary with the last byte would wrongly reject this complete section.

  8. State the result precisely

    The specified structure follows our convention: readable header, complete table, located entries, present sections and consistent layout. To reach the readings, we follow the record at 14, then its offset 28; we do not treat the record as the content.

    We have not interpreted the bytes of the readings. The bounds therefore guarantee neither the accuracy of the readings nor the safety of another file. Another convention might allow gaps or overlaps; we would need to read it before applying the rules of this logbook.

✿03 Common mistakes

  • “The last entry is the last section.”

    The record for the readings starts at 14 in the table. Its start field specifies 28. Name each object before calculating: the position of the record, then the position of the bytes it describes.

    Reread the diagram of the records

  • “I add the start of the table to the start of the section.”

    The offsets in our format are all measured from the start of the file. Adding 8 to 28 would give 36, then an end at 48, outside the file. A relative offset would require different format rules; it cannot be assumed.

    Review the definition of absolute offsets

  • “A recognized signature and a readable table are enough.”

    Each entry may specify bytes that are missing. Check the section ends separately, then the layout required by the format. In the last exercise, the header remains readable while one of the checks fails.

    Diagnose the logbook variants

Compare with the solution

Last index: 2 − 1 = 1. Position: 8 + 1 × 6 = 14 bytes. Exclusive end: 14 + 6 = 20. Last included byte: 20 − 1 = 19.

These positions delimit the record. You still need to read its start field, whose value is 28, to find the readings. The index is a count with no physical unit; the position is an offset in bytes.

Check your reasoning

  • The index is 1 and the position is 14, obtained using stride E.
  • The exclusive end 20 is distinguished from the last byte 19.
  • The position of a record is distinguished from the field it contains.

Exercise 2 · Application and justification

The section reaches the exact end

The record for the readings specifies a start at 28 and a size of 12 bytes. The file is 40 bytes long. Someone rejects this section because its end reaches the length of the file. Answer with its interval, then check by addition and subtraction.

Hint 1

An end boundary is not a byte to read.

Hint 2

Compare the specified size with the remaining space after the start.

Compare with the solution

The exclusive end is 28 + 12 = 40. The interval [28, 40) includes position 39, but not 40. The check requires an end less than or equal to the length; equality is therefore correct.

Another route: 40 − 28 = 12 bytes remain available, exactly the specified size. The section fits. This establishes its presence in the file, without interpreting the readings.

Check your reasoning

  • The end 40 and the remaining space 12 are calculated in bytes.
  • The bracket on the right excludes the boundary; no byte at 40 is invented.
  • The result concerns the presence of the bytes, with no conclusion about their content.

Exercise 3 · Diagnosing variants

Stop at the first missing information

Consider the following alterations to the same logbook separately. In the short variant, only 19 bytes remain, but the header is unchanged. In the long variant, the file keeps 40 bytes and the table remains complete; only the specified size of the readings changes to 14 bytes. Where must each reading process stop? Quantify what is missing and explain why a correct signature fixes nothing.

Hint 1

In the short variant, compare the length with the end of the table before decoding the sections.

Hint 2

In the long variant, recalculate the end of the readings and compare it with L.

Compare with the solution

Short variant: the header of 8 bytes fits, but the table requires an end at 20. There is 20 − 19 = 1 byte missing. The last record is incomplete. Stop decoding the specified table as a whole and report the truncation; do not fill in the missing field with an assumption.

Long variant: the table fits, but the readings section ends at 28 + 14 = 42, beyond 40. There are 42 − 40 = 2 bytes missing. You can report what the record specifies; do not declare the section fully present or silently reduce its size.

The signature only identifies a candidate format. It replaces neither the missing bytes of an entry nor those of a section. These variants fail at different stages: the table, then the content it describes.

Check your reasoning

  • The short variant fails at the table, with 1 byte missing.
  • The long variant fails at the section, with 2 bytes missing.
  • You keep what is specified as a specification and report the failure without inventing a complete structure.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What must you read in the header to locate our table and check its bounds?

After recognizing and checking the header, read T, the table start in bytes, N, the number of entries, and E, the bytes per entry. Check the format rules, then compare the exclusive end T + N × E with the available length L.

Recall 2How do you reach the entry with index i, and why does this not yet reach the section?

With an index counted from 0 and less than N, its position is T + i × E. This position reaches a record; the start field within the record indicates where the section is located.

Recall 3When does a section with start o and positive size s fit within a file of length L?

Check 0 ≤ o ≤ L and s ≤ L − o. The exclusive end o + s may equal L. For a nonempty section, the last included byte is at o + s − 1. You must then check the other format rules.

Recall 4What does a fully readable table fail to prove?

It does not prove that the specified sections fit within the file, that their bytes have the expected meaning or that a program is harmless. Each section needs its own check; interpreting the content requires other evidence.
