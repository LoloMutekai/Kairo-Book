Level 2 · C072·M4

Public projection before rendering

Your goalBuild the only record that a public renderer may receive, then check the fields that are copied, replaced and excluded.

Before you start

✿01 See the idea

You are preparing a poster for a bookbinding workshop from an organizing record. The record also contains a contact, a door code and an internal instruction. Placing a rectangle over these details in the poster leaves the sensitive material in the hands of the person producing the file.

Imagine a fresh sheet of paper instead. Copy only the title, topic and duration onto it. In place of the contact, write the fixed word “REMOVED”. Copy neither the code nor the instruction. The person laying out the poster receives only this fresh sheet.

This construction is called a public projection: it transforms the available data into an object explicitly authorized for the public. Rendering then transforms this object into a document. Redaction therefore begins in the data, before the document is produced.

All names, codes and values in this scene are fictional. We are studying a flat record: each field contains plain text or a duration. No field contains a nested record, an image or markup. The copied texts have been approved for publication for this workshop; a field name never suffices to authorize its contents.

The rule to remember

Build a fresh object with authorized fields and values, then render only this object. A new field remains excluded until the policy admits it.

✿02 Follow an example

Worked example

Build the workshop record for publication

Build the projection of the fictional record, count what is transmitted, then explain how to check that rendering no longer depends on the excluded details. The policy is fixed before reading the values.

  1. Define the data and their domain

    Let D denote the source record, a mapping between field names and values. D contains: titre = “Bookbinding workshop”; theme = “paper”; duree_min = 90 min; contact = “Mila”; code_porte = “LINDEN”; note_interne = “call Mila”. The identifiers without accents are the exact field names in our example.

    The field duree_min measures minutes. The other values are texts, with no physical unit. We count fields, rather than characters or bytes. A short code can be as sensitive as a long note.

  2. Write the output policy

    A is the set of names whose values may be copied: titre, theme and duree_min. M contains the name contact, whose value will be replaced. E contains code_porte and note_interne, which will not be emitted. These sets are disjoint: no name receives more than one treatment.

    P denotes the projection operation. It starts with an empty object, copies the fields in A, then writes contact = “REMOVED”. It ignores every other field. It does not modify D. If a required field in A is missing or has an unexpected type, construction stops so the problem can be corrected; it does not pass D along as a fallback.

    This rule authorizes specific names and simple values that have already been checked. Copying an entire object under an authorized name would require a rule for its subfields: our assumption of a flat record is essential.

  3. Build the new record

    P(D), read as “projection of D”, contains exactly: titre = “Bookbinding workshop”; theme = “paper”; duree_min = 90 min; contact = “REMOVED”. The values “Mila”, “LINDEN” and “call Mila” are not copied. The source remains available to the organizers, outside the input to public rendering.

    The replacement is constant text, chosen by the policy. It is neither the real contact blurred out, nor a string of the same length, nor its hash. Those transformations could still reveal information about the removed value.

  4. Calculate the counts and check the partition

    nD is the number of source fields; nA the number of copied values; nM the number of replaced fields; nP the number of output fields; nE the number of excluded fields. All these numbers count fields, with no physical unit. Replacement keeps a slot, while exclusion removes that slot.

    nP=nA+nM=3+1=4 champs

    We subtract the emitted slots to count those that have disappeared: nE = nD − nP = 6 − 4 = 2 fields. Reverse check: 4 + 2 = 6 fields, the initial count. Listing the names identifies code_porte and note_interne, the fields expected to be absent.

    There are 4 fields left, but only 3 original values copied. We expect 0 fields outside the authorized names. The count alone cannot verify confidentiality: mistakenly replacing code_porte instead of contact could keep the same total. The exact names and values must also be compared.

  5. Give the renderer a single input

    R denotes deterministic rendering: given the same input and the same fixed template, it produces the same document. The route is D → P(D) → R(P(D)). Serialization, meaning conversion into text or bytes for the file, also starts from P(D).

    The renderer does not receive D and cannot obtain its values by any other route. Do not pass them to it in embedded data, a hidden attribute or an accessible description. Visually masking real text comes too late: that text is already in the document.

    If a hash is published, calculate it from the public bytes. Let C denote the agreed canonical encoding, H the hash function already studied and hP the public hash: hP = H(C(P(D))). A hash of the removed value could allow guesses to be tested; it does not replace removal.

  6. Check with another source record

    Build D′, read as “D prime”, keeping titre, theme and duree_min, but replacing contact with “Nora”, code_porte with “CHERRY” and note_interne with “call Nora”. The rule does not read any of these values to produce its output: P(D′) = P(D). The projection therefore remains exactly the same, beyond just the field count.

    With C and R fixed, this equality leads to the same public hash and the same rendering. It is justified by the identical public inputs, rather than a promise that hashes are absolutely unique. However, changing the authorized title may change the projection.

    This check establishes that the projection is independent of the removed details in our record. It does not prove that the title or topic is harmless in every context. Examining the final file, its extracted text and its metadata belongs to the next unit.

✿03 Common mistakes

  • “The text is invisible, so it has been removed.”

    Masked text can still be copied or read in the document data. Build P(D) before serialization and give only this projection to the renderer.

    Review the renderer input

  • “I remove the sensitive names I know; the rest can pass through.”

    A field added tomorrow may contain a sensitive detail. Explicit selection emits only authorized names. Work through adding the address again in the second exercise.

    Test the new field

  • “The right field count and a hash are enough.”

    The same count can accompany the wrong values. Compare the exact projection, then vary the removed values. A hash of a secret can help someone guess it; a public hash is used here to identify a version, without certifying its confidentiality.

    Repeat the check with D prime

Exercise 3 · Transfer and objection

What a check allows you to claim

A colleague changes only the contact, code and internal note, then obtains the same projection. They conclude: “The public file cannot reveal anything.” Explain what is demonstrated in our model, then examine the case where theme has been filled with “paper with Mila”. Where should you intervene?

Hint 1

The equality of outputs concerns the removed fields, under a fixed policy.

Hint 2

A sensitive value may appear under an authorized name.

Compare with the solution

Changes to the removed values leave P(D) identical. Under the assumptions of deterministic rendering and the renderer being able to obtain only P(D), they do not change the document either. This reasoning goes beyond checking only the total 4.

It does not establish that every copied value is suitable for publication. If theme contains “paper with Mila”, selecting names transmits this string. This value must be checked or rewritten before constructing the projection, according to explicit authorization; if this check fails, stop production.

Finally, the generated page and its metadata will need their own check. Equal projections and a hash demonstrate neither this final check nor a general absence of reidentification.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1When should a sensitive value be removed?

Before any serialization intended for the public and before rendering: build an authorized object, then transmit only that object.

Recall 2What happens to a field added to the source without a policy change?

It stays excluded because it is not among the explicitly authorized names. Being unknown does not by itself admit it.

Recall 3Why does the contact mask keep a slot without keeping the value?

The name contact is emitted with the constant word “REMOVED”. The renderer receives this constant, without the original value or its length.

Recall 4What check goes beyond simply counting fields?

Compare the exact names and values of the projection, then change the removed values while keeping the authorized values. The output must stay identical under the fixed policy.

Recall 5What does selecting field names fail to guarantee?

It does not guarantee that their values are suitable for publication, or that a final document is free of other sensitive content. Authorized values and final outputs require appropriate checks.
