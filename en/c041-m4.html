Level 2 · C041·M4

Joins and aggregates

Your goalLink jobs to their tasks, calculate a report for each job and detect a sum inflated by a join.

Before you start
c037-m5 : controlled cleaning · c017-m5 : reproduction protocol · c041-m1 : relational model · c041-m2 : keys · c041-m3 : SQL

✿01 See the idea

In a bicycle repair workshop, each job has a quote. Tasks are recorded on separate cards: an adjustment, a test, then perhaps another action. You want a report of the time recorded for each job, including jobs still waiting for their first task.

Imagine placing each task card beside the job with the same identifier. Job A finds 2 cards, so it appears 2 times in the resulting pairs. This does not create any new job. Job C finds no card; you need to decide whether the report should still show it.

A join builds these pairs according to a condition. An aggregate summarizes several rows, for example by counting them or adding their durations. Grouping chooses which rows will be summarized together. Before each operation, ask: “What does a row represent?” This unit of representation is the granularity.

All the data are fictional. The cards are assumed to be complete for the period in question: no card for C means no recorded task here, rather than a known duration for future work. We will join, group and check these same tables; transactions and window functions belong to the next unit.

The rule to remember

Build the pairs, check their repetitions, then group at the required granularity. A sum operates on the rows it receives, even if the join has repeated an amount in them.

✿02 Follow an example

Worked example

Prepare the workshop report without repeating quotes

The 3 jobs and 3 tasks are exactly those in the diagrams. Let us produce a row per job, with the number of tasks and their total duration. We will also check why adding the quotes after a join gives a different result from adding them in their original table.

  1. Specify the tables, units and assumptions

    The dossiers table contains the columns id and devis_eur: (A, 30), (B, 30), (C, 20). The interventions table contains id, dossier_id and minutes: (a, A, 12), (b, A, 18), (c, B, 10). Amounts are in euros and durations in minutes; identifiers have no physical unit.

    dossiers.id is a primary key: no repetition or NULL value. interventions.id is also a primary key; interventions.dossier_id is a non-NULL foreign key that references dossiers.id. Each task therefore belongs to exactly 1 job, while a job can have several tasks or none. Durations are known, non-NULL and positive; each card describes a distinct action. We do not remove any cards that appear identical.

    In the queries, d is the short name for dossiers and i for interventions; the dot refers to a column of that table. The names nb and total_min will be result column names, chosen with AS. Counts are expressed in jobs, tasks or rows depending on what is being counted: these counting units are not interchangeable.

  2. Build the pairs before summarizing them

    The condition i.dossier_id = d.id is the link to test. The following query displays only the pairs that satisfy this link. Each query on this page is read separately, without a final semicolon.

    Query: SELECT d.id, i.id, i.minutes FROM dossiers AS d INNER JOIN interventions AS i ON i.dossier_id = d.id ORDER BY d.id, i.id

    INNER JOIN produces (A, a, 12), (A, b, 18), (B, c, 10): 3 rows. C has no match and disappears. The granularity is the job–task pair, rather than the job.

    To keep all jobs, replace INNER JOIN with LEFT JOIN, a left join. The table on the left is dossiers. The previous pairs remain, and C gives (C, NULL, NULL), making 3 + 1 = 4 rows. NULL represents a missing value, rather than the number 0. For a job with no match, the columns on the right are all NULL.

    The primary key on the dossiers side guarantees here that each task finds at most 1 job. Joining on the quote amount would be a different condition: A and B have the same amount but are different jobs. Column names never choose the condition for you.

  3. Choose what each aggregate counts

    COUNT(*) counts all the rows it receives, including the row kept for C. COUNT(i.id) counts the non-NULL values in that column. Since the identifier of an actual task is always present, this second count measures the number of associated tasks here.

    In group A, both counts give 2. In B, they give 1. In C, COUNT(*) is 1 row, while COUNT(i.id) is 0 tasks. Counting i.minutes would give the same count here as counting i.id because all durations are non-NULL; this equivalence depends on the assumption.

    SUM(i.minutes) adds the non-NULL durations. For A: 12 + 18 = 30 min. For B: 10 min. For C, there is no non-NULL duration: SUM returns NULL, rather than automatically returning 0.

    COALESCE takes the first non-NULL value among its arguments. COALESCE(SUM(i.minutes), 0) therefore replaces this last result with 0 recorded minutes. This choice expresses our reporting convention and the assumption that the cards are complete; it would not allow unknown durations to be turned into measured durations.

  4. Group and write the complete query

    GROUP BY d.id brings together rows with the same job identifier. Aggregates work separately within each group. We obtain a row per job, even though A occupied several rows in the join.

    Query: SELECT d.id, COUNT(i.id) AS nb, COALESCE(SUM(i.minutes), 0) AS total_min FROM dossiers AS d LEFT JOIN interventions AS i ON i.dossier_id = d.id GROUP BY d.id ORDER BY d.id

    The result, in the order (id, nb, total_min), is (A, 2, 30), (B, 1, 10), (C, 0, 0). nb is in tasks and total_min in minutes. GROUP BY chooses the groups; ORDER BY chooses the display order. Grouping alone promises no order.

    A selected column must here be the group key or be summarized by an aggregate. Adding i.id as it stands would be ambiguous for A: should a or b be displayed? To remain explicit and portable, list the selected nonaggregated columns in GROUP BY.

    If the question becomes “Which jobs have a task?”, HAVING COUNT(i.id) > 0, placed after GROUP BY and before ORDER BY, keeps only A and B. HAVING filters the calculated groups; it deliberately changes the population covered by the report.

  5. Check the counts, sum and denominator

    Coverage check: the report has 3 rows, one per identifier in dossiers. Count check: 2 + 1 + 0 = 3 tasks, as in the interventions table. The row kept for C does not inflate this count.

    Minutes check: 30 + 10 + 0 = 40 min. As an alternative check, read the cards directly: 12 + 18 + 10 = 40 min. The sum is preserved because each card was matched exactly once, thanks to the keys and this join condition.

    The average per recorded task is the total minutes divided by the number of tasks. Let M be this total in minutes, N the task count and μ their average duration in minutes per task. N must be strictly greater than 0.

    μ=MN=403=40/3≈13.33 min par intervention

    AVG(i.minutes), the average aggregate, also ignores NULL values and gives this same average over the whole join, without GROUP BY. Dividing by COUNT(*) would give 40 / 4 = 10 min per join row: the denominator would include C, which does not represent any task. Rounding is used only when reading the exact result.

  6. Identify the sum whose meaning changes

    The quote belongs to the job. In the left join, the visible amounts are 30, 30, 30, 20 €. The quote for A accompanies each of its tasks. Its contribution becomes 2 × 30 = 60 €.

    Adding these rows gives 60 + 30 = 90 €, then 90 + 20 = 110 €. Yet the dossiers table gives 30 + 30 = 60 €, then 60 + 20 = 80 €. The difference is 110 − 80 = 30 €, exactly the extra copy of the quote for A.

    To fix the calculation of the “total of quotes”, stay at job granularity. The following query gives 80 €. For a report combining quotes and time, first return to a row per job before summing the amounts.

    Query: SELECT SUM(devis_eur) AS total_eur FROM dossiers

    SUM(DISTINCT d.devis_eur) on the join does not fix the handling of identities. DISTINCT removes repeated numeric values: A and B share 30 €, so this sum keeps only 30 + 20 = 50 €. Equal quotes can belong to distinct jobs. COUNT(DISTINCT d.id), however, would correctly count 3 jobs, since the key is what we want to distinguish.

  7. Place a filter without losing jobs that are waiting

    Now, in the same workshop, let us ask for the number of tasks lasting at least 15 min per job, while keeping every job. Only card b, lasting 18 min, reaches this threshold.

    The condition must restrict which matches are accepted in the join:

    Query: SELECT d.id, COUNT(i.id) AS nb FROM dossiers AS d LEFT JOIN interventions AS i ON i.dossier_id = d.id AND i.minutes >= 15 GROUP BY d.id ORDER BY d.id

    Result: (A, 1), (B, 0), (C, 0). ON chooses the matches. After this choice, LEFT JOIN also keeps jobs that found none.

    If i.minutes >= 15 is placed in WHERE, the filter acts after the join is built: rows with durations that are too short are removed, and the comparison with NULL does not evaluate to true. WHERE keeps only rows where the condition is true. B and C disappear; only (A, 1) remains. A filter after a join does not recreate a job row it has just eliminated.

    The useful logical order is therefore: build matches with FROM, JOIN and ON; filter rows with WHERE; group with GROUP BY; filter groups with HAVING; order with ORDER BY. It describes the meaning of the result, rather than necessarily the physical order chosen by the engine to execute the query.

Explain it in your own words

✿03 Common mistakes

  • “A join necessarily keeps a row per job.”

    Write out all matches before grouping. A appears 2 times because it has 2 tasks. For the total of quotes, start again from the jobs; removing equal amounts with DISTINCT would also remove the legitimate quote for B.

    Review the pairs, then the quote check

  • “COUNT(*) always gives the number of tasks.”

    The left join keeps a row for C. COUNT(*) counts it; COUNT(i.id) excludes it because that identifier is NULL. Choose an identifier guaranteed to be non-NULL to count actual matches.

    Recount the columns in the second diagram

  • “Putting the condition in ON or WHERE amounts to the same thing.”

    With a left join, WHERE can remove the rows kept for jobs with no match. If you want to keep all jobs but restrict the tasks, place the task condition in ON, then count the task identifier.

    Fix the filter in the last exercise

Compare with the solution

The rows are (A, a, 12), (A, b, 18), (B, c, 10), (C, NULL, NULL). The result has 4 rows, but only 3 non-NULL task identifiers.

COUNT(*) = 4; COUNT(i.id) = 3; SUM(i.minutes) = 12 + 18 + 10 = 40 min. AVG(i.minutes) = 40/3 min per task, or approximately 13.33 min per task.

Hint 2

Compare with the solution

The given query returns only (A, 1). The card for B lasts 10 min and is rejected; for C, NULL >= 15 does not evaluate to true and WHERE also rejects its row. The word LEFT does not prevent this later filter.

Query: SELECT d.id, COUNT(i.id) AS nb FROM dossiers AS d LEFT JOIN interventions AS i ON i.dossier_id = d.id AND i.minutes >= 15 GROUP BY d.id ORDER BY d.id

The result is (A, 1), (B, 0), (C, 0). A has an eligible match; B and C have none and are kept with NULL in the i columns. COUNT(i.id) then gives 0. With COUNT(*), the groups for B and C would incorrectly give 1 task each.

The number of jobs returned remains 3. The sum of the counts is 1 eligible task, corresponding to the only card lasting 18 min. These checks verify job coverage and card selection separately.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Why can a job appear several times after a join?

A join produces a row for each pair that satisfies its condition. A has several tasks, so it participates in several pairs. The granularity of the result becomes job–task.

Recall 2What does a left join keep for a job with no match?

A row containing the job, with NULL in the columns on the task side. COUNT(*) counts this row; COUNT(i.id) does not count it as a task.

Recall 3What is the role of GROUP BY d.id, and how do we show no recorded time for C?

GROUP BY forms a group per job identifier. SUM(i.minutes) adds the known durations in the group and returns NULL for C; COALESCE(SUM(i.minutes), 0) displays 0 min according to our reporting convention.

Recall 4Why does SUM(DISTINCT devis_eur) generally fail to correct a sum inflated by a join?

It removes equal amounts, even if they belong to different jobs. We need to preserve a contribution per job identity; for the total of quotes alone, sum the dossiers table directly.

Recall 5Where should a threshold on tasks be placed if all jobs must remain in the report?

In ON of the left join: the threshold restricts the matches. WHERE filters rows after the join and can remove jobs with no match; HAVING then filters groups.
