Level 1 · C018·M1

Interface and contract

Your goalWrite down what a function lets you request and what it guarantees, then check that promise using a loan prediction.

Before you start
c016-m5 : documentation · c015-m5 : diagnosis · c017-m5 : reproduction protocol · c012-m5 : counterexamples

✿01 See the idea

In a community group’s storeroom, 8 lamps are available. You are considering lending out 3 of them and ask a small management tool how many would remain. You want a prediction before deciding: the loan register must stay unchanged. The scene and quantities are fictional.

The name reste_apres_pret, the inputs stock and demande, and the integer form of the result make up the function’s interface here. An interface is the part exposed to whoever uses a component. Here, the component is this piece of program code; the caller is the program that asks it for a result. An interface does not necessarily mean a screen or a button.

The contract specifies the obligations on each side. The caller provides whole numbers of lamps and a request that does not exceed the stock. In return, the function promises the exact remainder, in the same unit, without recording a loan. We also need to know how it signals an invalid request.

A result can have the right form and break the promise. Returning 11 would return an integer, but adding the requested lamps does not calculate the remainder. The interface alone does not say which operation makes the result correct.

The rule to remember

Read the interface to find out how to make a call; read the contract to find out what the inputs mean, what is promised, and how to recognize a refusal.

✿02 Follow an example

Worked example

Predict the remainder without recording the loan

The supplied stock is 8 lamps and the request is 3 lamps. We will write the contract for reste_apres_pret, check the call, calculate its output, and check the meaning of that result.

  1. Write the visible part

    We write the interface as follows: reste_apres_pret(stock, demande) → entier. The parentheses indicate the inputs passed in the call; the arrow states the form of the result. Here, an integer represents a count of whole lamps. The signature names this form of call; it does not yet provide the calculation rule.

    stock is the available quantity stated before the proposed loan; demande is the quantity being considered for lending. The order and role of these parameters matter: swapping them changes the question. The result represents the stock that would remain, rather than the quantity requested.

  2. Define the domain and guarantees

    Let s be the value of stock, d the value of demande, and r the result. All these quantities count lamps, using the same unit. Preconditions are the conditions that must be met before a valid call: s and d are integers, s is nonnegative, and the request satisfies the following bounds.

    0≤d≤s

    Postconditions are the guarantees to check after a valid call: r is an integer count of lamps, r = s − d, and the loan register does not change. The function makes a prediction from the stock it receives; it does not check that this stock still matches what is actually in the storeroom.

    Our contract adds a rule outside this domain: an unsuitable type, a negative count, or an excessive request triggers a request error, with no numeric result and no change to the register. This policy is an explicit choice for our tool, rather than a universal rule for all functions.

  3. Check the inputs before calculating

    The values 8 and 3 are integer counts of lamps. We have 0 ≤ 3 ≤ 8: the call is within the intended domain. We also assume that the same set of lamps is counted without double counting and that no other stock movement is included in this prediction.

    A quantity expressed in boxes would not be suitable, even if it were also an integer: it would first need to be converted into lamps. The type describes a form of data; the unit and meaning are also part of the contract.

  4. Perform the promised operation

    The stock is divided between the lamps to be lent and those that would remain. To isolate the remainder, subtract the request from the stock. This is why subtraction is required.

    r=s−d=8−3=5 lampes

    The expected output is therefore the integer 5, in lamps. This supports the statement “5 lamps would remain with the data supplied.” Saying that the loan has taken place would require another action and suitable evidence.

  5. Check the promise using another operation

    Return to the initial division: the remainder and the request must add up to the stock. Addition provides a check on the result obtained by subtraction.

    r+d=5+3=8=s

    The result also satisfies 0 ≤ 5 ≤ 8 and remains an integer count. These numeric checks do not demonstrate that the register has stayed unchanged: that clause would require comparing its state before and after in an authorized check. No actual loan program is run here.

    A case that meets the contract makes the promise concrete; it does not prove that an implementation keeps it for every possible call. Nor does it prove that another program actually calls this function.

✿03 Common mistakes

  • “If the name and result type are suitable, the contract is satisfied.”

    The result 11 is an integer, but it adds the request to the stock. Return to the meaning of “remainder” and check the relation r + d = s. A correct form does not guarantee a correct value.

    Review the calculation and its check

  • “An integer input is necessarily an allowed input.”

    The request 9 is an integer but exceeds the stock 8. The units, sign, and bounds must also be suitable. Check the domain before interpreting a subtraction as a valid output.

    Study the excessive request

  • “The predicted result is correct, so the loan is recorded.”

    Our function specifically promises to leave the register unchanged. The prediction is a calculation; recording the loan would change other information. That would require a separate action and a check on it.

    Reread the exchanges and the clause about the register

Exercise 1 · Identify the obligations

Form and meaning

A colleague writes only reste_apres_pret(stock, demande) → entier and claims that this is enough. For our lamp storeroom, specify the role of the inputs, their domain, the promised result, and the clause about the register. Which information comes from the signature alone?

Hint 1

Hint 2

Compare with the solution

The signature exposes the name, the parameters stock and demande, and the integer form of the output. On its own, it does not specify the unit, the permitted values, the formula, or the allowed changes.

The contract specifies that s and d are integer counts of lamps, with 0 ≤ d ≤ s. Within this domain, r = s − d and the register stays unchanged. An input outside the domain triggers a request error with no numeric result. These statements make the promise checkable.

Check your reasoning

  • You distinguish the form of the call from the promised behavior.
  • You state the unit and the bounds for the inputs.
  • You specify the result, the error policy, and the absence of loan recording.

Exercise 2 · Apply, then check

Another request, the same contract

The stock remains 8 lamps. Predict the remainder for a request of 2 lamps, then for a request of 8 lamps, and finally for a request of 0 lamps. Check the domain and combine each result with its request. These calls are separate predictions from the same stock, rather than successive loans.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

The endpoints are allowed because the contract uses ≤.

Hint 2

Calculate s − d, then check r + d = s for each prediction.

Compare with the solution

For the request 2, the bounds 0 ≤ 2 ≤ 8 are satisfied. The remainder is 8 − 2 = 6 lamps; the check gives 6 + 2 = 8 lamps.

Requesting all the stock is also allowed: 8 − 8 = 0 lamps remaining. The check 0 + 8 = 8 recovers the stock. A remainder of 0 is therefore a valid possible output.

With a request of 0, 8 − 0 = 8 lamps; 8 + 0 = 8. The function keeps this prediction of the stock and never changes the loan register.

Check your reasoning

  • You validate the inputs, including the bounds.
  • You obtain 6, 0, and 8 lamps and justify each check.
  • You start from the same stock for each call.

Exercise 3 · Diagnose a counterexample

A false remainder of 0

For a stock of 8 lamps, the request becomes 9 lamps. A version of the tool returns 0 whenever the request exceeds the stock, and a colleague concludes that the contract is satisfied because the output is an integer and nonnegative. Respond to this objection and specify the reply our contract requires.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

First check the precondition d ≤ s before judging the result.

Hint 2

Compare this reply with the one for the valid case where exactly all the stock is requested.

Compare with the solution

9 > 8: the call is outside the valid domain. Our policy requires a request error, with no numeric result and no change to the register. Returning 0 does not follow this policy, even though this number is an integer and nonnegative.

The calculation 8 − 9 = -1 lamps is used here to diagnose the excess; it is not an allowed output of the function. Silently replacing this result with 0 hides the refusal.

The output 0 would also mean, for a valid request of 8, that no lamps would remain. Confusing refusal with success prevents the caller from knowing what happened. Another contract could use a structured reply, but it would have to describe it explicitly.

Check your reasoning

  • You identify the violated precondition before evaluating a postcondition for success.
  • You distinguish the arithmetic diagnosis from the allowed reply outside the domain.
  • You explain why a plausible value does not replace a specified error.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does the interface of reste_apres_pret expose in our scene?

The name of the operation, the parameters stock and demande, and the integer form of the result. This is what the caller uses to request the prediction.

Recall 2What does the contract add to this signature?

The meaning and unit of the data, the valid domain, the exact remainder promised, the prohibited changes, and the specified reply for an invalid request.

Recall 3How do you distinguish a precondition from a postcondition in our prediction?

Before a valid call, s and d must be integer counts of lamps and satisfy 0 ≤ d ≤ s. Afterward, the result must satisfy r = s − d and the register must be unchanged. The obligations apply at different times.

Recall 4What does r + d = s check, and what still needs to be checked separately?

The equality checks the calculation of the remainder from the stock and the request. It does not prove that the register is unchanged, that the stated stock matches reality, or that the function is called in a program in use.

Recall 5Why refuse an excessive request instead of returning a remainder of 0?

Our contract requires an error with no number outside the domain. A remainder of 0 can already be a valid output when the request equals the stock; using it for a refusal would make these situations indistinguishable.
