Level 2 · C022·M1

Asset, threat and scope

Your goalDescribe what must remain intact in a local report, build a threat scenario and define the limits of the study before deciding on permissions.

Before you start
c021-m5 : origin, authentication and authorization · c018-m5 : contract tests and test doubles · c012-m5 : counterexamples

✿01 See the idea

You give a colleague a tool to view your workshop report. After they read it, you want your text to be exactly as it was. Yet the same tool can receive a request to “replace the content”. Before asking who is allowed to do what, you need to say what would be lost if this request succeeded.

The scene is fictional, as is its entire inventory of requests. The report is the local file atelier/rapport.txt. It is our asset: a resource that has value and deserves protection. Here, the property to preserve is its integrity, meaning that the expected content is preserved during viewing. The file does not need to contain a secret to deserve this protection.

A threat is a possible cause of harm to this property. Our scenario is specific: a replacement request reaches the tool; the tool passes it on to an operation that opens the file for writing; the original text is overwritten. The request may result from a mistake by the colleague or a deliberate act. Knowing their identity is not enough to rule out the scenario. A threat describes what could happen; it does not prove that an incident has happened.

The scope of the study defines the elements and exchanges we examine: incoming requests, their processing by this tool and interaction with the report. The colleague is outside this scope; their requests cross into it. The frame in the diagram shows what we are studying, without guaranteeing that its interior is safe. A trust boundary is a crossing where we must reassess what we accept: knowing where a request comes from does not guarantee that its operation respects the task.

We study read and replacement requests for this report, including those that fall outside the viewing task. Direct changes by another program and disk failures remain outside this study. Excluding them from the model does not make them impossible; it limits what our conclusion can cover. Permissions, evidence of consent and refusal mechanisms will be studied in the following units.

The rule to remember

Name the asset and the expected property; explain how that property could be harmed; draw the relevant path and the limits of your conclusion.

✿02 Follow an example

Worked example

Prepare the study of the report before making any decision

A fictional inventory contains requests A, B and C in the morning, then D, E and F in the afternoon: all declare “read atelier/rapport.txt”. G and H declare “replace atelier/rapport.txt”. Each letter identifies a distinct request, with no duplicates in the inventory. No execution is observed. Let us find the requests that fall outside the viewing task and the conclusion this count allows.

  1. Define the asset and the observable criterion

    The asset is the original content of atelier/rapport.txt. Our expectation is that after viewing, this content is identical to what it was before. Comparing the content before and after would be a relevant check of the final state for a given trial. It would not trace any intermediate writes. The mere presence of the file or a “viewing complete” message would not check this criterion.

    We must distinguish the objective from evidence that it has been met: here we define the criterion, but we have neither an actual comparison nor an observation of the program.

  2. Define the path and its assumptions

    In this study, a request provides an operation and a target. The operation is “read” or “replace”; the target is the path to the report. We follow its entry into the tool, the processing of these fields and interaction with the file. A replacement request therefore belongs within the scope, even if it contradicts the task.

    For the count, we assume that the inventory is complete over the chosen period, contains no duplicates, and that each request has a single declared operation. To reason about the expected effect, “read” means viewing without changing the content; we would still need to check that the program respects this meaning. We do not assume that a request’s label proves its effect. Direct file operations by other programs and disk failures are excluded from this model.

  3. Describe the threat through to its effect

    G or H enters as a replacement request. If processing turns this request into a write without preserving the report, the original content may be overwritten. This connects the asset, the entry point and the harm to integrity. Simply saying “the colleague is a threat” would specify neither the act nor the possible loss.

    We have not established that this write is possible. The scenario indicates what needs to be examined in the processing and file operations. A dangerous request being received, a weakness in the program and actual damage are distinct facts.

  4. Count requests of the same kind

    L is the set of requests declared as reads: A, B, C, D, E and F. R is the set of requests declared as replacements: G and H. U denotes the entire inventory. The bars | | give the number of elements in a set, with “request” as the unit here. The symbol ∩ denotes the shared elements; ∅ is the empty set. L ∩ R = ∅, so |L ∩ R| = 0: no request is counted in both categories.

    The morning contributes 3 read requests and the afternoon 3. Adding them gives |L| = 3 + 3 = 6 requests. Then |R| = 2 requests. Since the categories are disjoint and cover the inventory, their counts can be added.

    |U|=|L|+|R|=6+2=8 demandes

    To count requests outside the task in this inventory, subtract the reads from the total: 8 − 6 = 2 requests. This subtraction works here because only replacements remain; the categories would need to be reconsidered if other operations appeared.

  5. Check by another method and limit the result

    Without repeating the additions, go through the letters: A, B, C, D, E and F declare a read; only G and H declare a replacement. Direct counting again gives 2 requests outside the task. It confirms the difference, and listing the full inventory again gives 8 requests in total.

    This result says neither how many writes succeeded nor how likely it is that the report will be lost. Even 0 replacements in an inventory would not prove that a future replacement is impossible. Our result is a list of requests to examine against the objective; to draw a conclusion about preservation of the content, we would need to read the relevant execution path and then check its effect in an authorized setting.

Explain it in your own words

Hide the steps. Redraw the path, name the asset and the expected property, then describe the possible overwrite. Why must G and H remain in the study even though they fall outside the task? Recount the requests and state what the result does not prove.

✿03 Common mistakes

  • “It is an ordinary file; there is nothing to protect.”

    Ask what would have value if it disappeared or changed. The report’s original text is useful even without a secret. Name this asset and then the expected property: preserving its content during viewing.

    Identify the asset and its integrity again

  • “The colleague is known, so their request poses no threat.”

    A mistake can be enough. Reconstruct the chain “replacement request, processing, write, overwrite”. Knowing the sender demonstrates neither that the operation is harmless nor how the program behaves.

    Follow the scenario through to its effect again

  • “Replacement is not permitted, so I can remove it from the scope.”

    The scope says what you study; the task says what you want to do. Removing troublesome requests would prevent you from examining exactly how they could reach the asset. Conversely, a failure excluded from the study remains possible.

    Revisit the limits and assumptions of the study

Total: 8 + 1 = 9 requests. Outside the task: 2 + 1 = 3 requests, those named G, H and I. Independent check: 9 − 6 = 3 requests.

No deletion has been observed; these are requests outside the task, not a count of damage.

Exercise 3 · Counterexample and application within the scene

The report changed despite a reassuring check

An account states: “The tool accepted only viewing requests, so the report can no longer be overwritten.” Imagine that the colleague’s text editor can open the same report directly, without going through the tool. Construct a counterexample to this conclusion. Draw the overlooked path and suggest how to limit or extend the study.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

The original scope excluded direct file operations by another program. Where does the editor’s path go?

Hint 2

A conclusion can be too broad even if the reported check is accurate for the path it examines.

Compare with the solution

Counterexample: all requests passing through the tool are reads, but the colleague then replaces the report from their editor. The path “colleague → editor → report” bypasses the tool’s entry point. The stated fact about the tool can be true while the report’s content changes.

We can limit the conclusion to report operations performed through the tool, under the study’s assumptions, keeping direct file operations as an explicit limitation. To also address the overlooked path, we must include the editor and its file operations in the scope, then look for suitable controls and evidence. Enlarging the diagram does not prove that these controls exist. A disk failure would still be a limitation if it were not studied.

Check your reasoning

  • My counterexample preserves the stated fact about the tool’s requests.
  • I draw another path to the same asset and name the missing assumption.
  • I propose a limited conclusion or an extended scope, without claiming verified protection.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1In the scene, what is the asset and what property do you want to preserve?

The original content of atelier/rapport.txt is the asset. Its integrity during viewing means that the expected content remains identical before and after. A secret is not necessary to justify this protection.

Recall 2How can you describe the threat without vaguely accusing a person?

A replacement request enters the tool; if processing passes it on to a write, the original text may be overwritten. A mistake is enough to make the scenario relevant. This possibility proves neither an exploitable weakness nor an actual incident.

Recall 3Why do replacement requests remain within the scope?

They follow the path to the report that is being studied. The scope includes what we examine, including operations that contradict the task. Being in the study grants no permission.

Recall 4What do the 2 requests outside the task in the initial inventory prove?

The ranking of this fictional inventory identifies G and H as replacement requests. It proves neither that any write was executed, nor any probability of an incident, nor any actual preservation of the report.

Recall 5What happens to a threat whose path is outside the scope?

It remains possible. We must state that it is not covered, or extend the study and look for the corresponding evidence. The editor accessing the report directly shows why checking the tool alone does not guarantee protection for every operation on the file.
