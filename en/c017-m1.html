✿01 See the idea

Yesterday, your analysis gave a mean duration of 18 s. Today, it displays 22 s. You corrected a duration, then corrected it again: which version had you actually kept between the two edits? Renaming the file “analyse_finale” does not answer that question.

Git keeps a version history in a repository: the project together with its recorded versions. The working tree contains the files you open and edit. The index, also called the staging area, prepares the next recorded version: it holds the content selected at the moment you stage it. A commit is that lasting record in the local history, with an identifier, a message, and a link to the previous version.

Imagine putting a photocopy in an envelope before filing it away. Changing the original does not change the photocopy already prepared. Similarly, after staging analyse.py, you can still edit the working file: the next commit will keep the staged content unless you stage it again.

Our scene is fictional. A small file, analyse.py, directly contains 3 trial durations in seconds and the calculation of their mean. The durations serve only to track versions; they do not measure any real machine. We study a linear local history, without collaboration or publication.

The rule to remember

Editing changes the working tree; staging copies content into the index; committing keeps the staged state. Check which states you are comparing each time.

✿02 Follow an example

Worked example

Which mean belongs to the commit?

The repository already exists, and analyse.py is tracked by Git. Commit A contains the durations 12 s, 18 s, and 24 s. Initially, the working tree and index match A. We replace the last duration with 30 s, stage the file, then replace it with 36 s before recording B. All the commands described succeed; nothing else changes the project or index, and no other changes are staged. The commands are examples to read, rather than actions executed on your project.

  1. Define what we calculate and what Git keeps

    a, b, and c are the trial durations, in seconds. n is their count, with no physical unit; here n = 3. S is the sum of the durations, in seconds. m is the arithmetic mean, in seconds: we distribute S equally across the trials. All trials have the same weight.

    S=a+b+c;m=Sn

    The file contains the durations and the calculation rule; this example uses no external data. Git keeps the staged content of the file. It does not run the analysis to check the mean. A commit describes a state of the tracked project, not just the number displayed on the screen.

  2. Review the starting point

    In A, the unchanged part is 12 + 18 = 30 s. Including the last duration, S = 30 + 24 = 54 s. The mean is 54 ÷ 3 = 18 s.

    Naming A and describing its durations gives a precise point of comparison. In a real repository, git log --oneline helps you locate commits and their messages. Note the identifier of the version you want; here, A remains a simple teaching label.

  3. Edit, then stage a selected version

    We correct c to 30 s in the working file. S is now 30 + 30 = 60 s; m = 60 ÷ 3 = 20 s. Commit A stays unchanged.

    git diff -- analyse.py compares the working tree with the index. Before staging, it shows the replacement of 24 s with 30 s here. Then git add -- analyse.py puts the current content of this file into the index. This also stages an already tracked file; “add” does not just mean adding a new file.

    git diff --cached -- analyse.py compares the index with the latest commit. It then shows what we intend to record: the change from 24 s to 30 s. The --cached option selects this comparison with the index. The -- separator introduces the filename.

  4. Edit again without updating the index

    We now replace c with 36 s in the working tree. S = 30 + 36 = 66 s, then m = 66 ÷ 3 = 22 s. The index still contains c = 30 s and therefore still corresponds to 20 s.

    git status can list the same file among both staged and unstaged changes. This is consistent: the comparisons concern different states. git diff --cached -- analyse.py still shows 24 → 30; git diff -- analyse.py shows 30 → 36.

    To record the variant at 36 s, you would need to review the change, then call git add -- analyse.py again. In our main sequence, we deliberately keep the earlier staged content.

  5. Commit what was ready

    The command git commit -m "Corrige la durée du dernier essai" creates B from the index. The message means “Correct the duration of the last trial.” -m supplies the message, which describes the intent of the change. We use this simple form, without an option that would automatically add the latest edits.

    B contains 12 s, 18 s, and 30 s: its mean is 20 s. The working tree still contains 12 s, 18 s, and 36 s: its calculation gives 22 s. The commit does not erase this more recent edit or include it automatically.

    B receives its own identifier and points to A as the previous version. Its content remains available for inspection as the working tree changes. The message makes the history easier to read; it does not replace checking the changes.

  6. Check the contents and the numbers

    After B, git show HEAD -- analyse.py shows the change recorded by this latest commit. Here, HEAD refers to the current commit, B. You should find 24 → 30, while git diff -- analyse.py still shows 30 → 36. Since the index now matches B, git diff --cached -- analyse.py shows no staged changes.

    Check the calculation by another route: only the last duration differs between B and the working tree. The difference is 36 − 30 = 6 s. Spread across 3 trials, it changes the mean by 6 ÷ 3 = 2 s. This agrees with 22 − 20 = 2 s.

    These checks connect content to its expected result. The mean displayed by the working tree does not prove that it belongs to B. And a local record alone does not constitute a copy on another machine or evidence that the program was executed.

✿03 Common mistakes

  • “I used add, so all my later edits will be recorded.”

    Staging holds the content as it was at that moment. After the new edit, compare the working tree and index. If you want to keep this edit, review it, then stage the file again; otherwise, the commit will keep the previously staged content.

    Revisit editing after staging

  • “git diff only shows 30 → 36, so nothing else will be recorded.”

    Without --cached, the command compares the working tree with the index. Before B, the already staged changes 24 → 30 appear in git diff --cached. Name the two states being compared before drawing a conclusion.

    Compare the two views of the changes

  • “The commit exists, so the result is correct and backed up elsewhere.”

    A commit keeps content locally. The correctness of the calculation requires its own checks; an independent copy requires separate evidence. In this scene, Git has neither run the analysis nor sent its history to another machine.

    Review the scope of version evidence

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What distinguishes the working tree, the index, and a commit?

The working tree contains editable files. The index prepares the content of the next commit. A commit keeps a state of the tracked project in the local history, with an identifier, a message, and a link to the previous version.

Recall 2Why might an edit made after git add be missing from the next commit?

The index holds the content present at staging time. A later edit changes only the working tree; it must be staged again to be included in a simple commit.

Recall 3What comparisons do git diff and git diff --cached make in our repository?

git diff compares the working tree with the index. git diff --cached compares the index with the latest commit. An empty comparison says nothing about equality with a third state.

Recall 4Why does the result from the open file not prove the result for the current commit?

The working tree may have changed since the commit. You need to identify the version and its content, then distinguish the expected calculation from the output actually observed when running that version. A local commit does not prove the existence of an independent copy either.
