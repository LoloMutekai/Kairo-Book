Level 1 · C019·M2

Threads and race conditions

Your goalFollow threads of execution in shared memory and construct an order of actions that loses an update.

Before you start
c016-m5 : documentation · c007-m5 : execution traces · c012-m5 : counterexamples · c019-m1 : processes and memory space

✿01 See the idea

In a fictional application, a counter shows how many tickets have been recorded. It displays 10 tickets. Threads A and B each finish recording a new ticket, so each must add 1 ticket to the counter. Yet after their updates, the screen may display only 11 tickets. Where did the missing update go?

A thread, or thread of execution, is a sequence of instructions with its own position in the program. In our process, A and B use the same counter in memory. They also keep separate working copies: changing the counter does not automatically overwrite a value that A or B has already read.

The system can let A advance, switch to B, then resume A. These threads are concurrent when their work is in progress during the same period. They do not need to execute their instructions at the same instant: a single core can alternate their actions. Actual simultaneous execution on several cores is parallelism; it is not needed for the fault studied here.

A race condition occurs when the order of accesses to the same shared state can change whether the result is correct. Here, the addition seems correct in each thread; using an old read value can lose an update. The values and traces are fictional. We will work through an explicit model, without claiming to reproduce the instructions of a particular language or interpreter.

The rule to remember

To look for a race condition, distinguish the shared value from the local copies, then interleave the actions while preserving the order within each thread.

✿02 Follow an example

Worked example

The tickets are recorded, but the counter loses an update

The shared counter starts at 10 tickets. The 2 threads A and B must each add 1 ticket. Let us break each update into 3 actions: read the counter, calculate the increased value, write that value to the counter.

  1. Name the state and define the model

    C denotes the shared counter. n denotes its initial value, 10 tickets; u is the amount each thread is asked to add, 1 ticket. m is the number of requested updates, here 2. A and B are thread labels. For a thread named T, r with subscript T is its copy of the value read, and v with that subscript is its calculated value. C, n, u, r and v are expressed in tickets; m counts updates.

    The arrow ← means “receives the value of”. L, K and E stand for read, calculate and write, respectively; they are action names with no unit. An update always follows this order within each thread:

    L:rT←C;K:vT←rT+u;E:C←vT

    We assume that each read and each write of an integer is indivisible: no thread reads part of a number. The actions form a common order visible to the threads, and each thread retains its L, K, E order. Each action executes exactly once, with no failure or other writer; integers do not overflow. The system can switch threads between these actions. These assumptions define the model studied here; they are not a guarantee for every language or every piece of hardware.

  2. Calculate the result that would meet the requirement

    Each new ticket must contribute u to the counter. Multiplying m by u gives the total contribution; adding it to n gives the expected result, written as C with subscript attendu, meaning “expected”.

    Cattendu=n+mu=10+2×1=12 tickets

    This calculation expresses what the updates must accomplish. It does not yet describe the order in which the threads will act.

  3. Have the threads read before any write

    A reads C and keeps r with subscript A = 10 tickets. B then reads C: no write has occurred, so r with subscript B = 10 tickets. The shared counter still holds 10 tickets. The local copies are separate, but their values are equal.

    A calculates v with subscript A = 10 + 1 = 11 tickets. B calculates v with subscript B = 10 + 1 = 11 tickets. Each addition is correct. These calculations change the local values, but do not yet change counter C.

  4. Write the results and measure the shortfall

    A writes its calculated value: C receives 11 tickets. B then writes its own: C receives 11 tickets. Writing means replacing C with the prepared value; B does not read again when writing. Its write therefore does not add 1 to the new counter value written by A.

    Let C with subscript final denote the counter after all the actions, and d the shortfall from the expected result. These quantities are expressed in tickets. Subtracting the obtained result from the expected one measures the lost update:

    d=Cattendu−Cfinal=12−11=1 ticket

    Check by counting: the 2 writes have taken place, but the counter has increased by only 11 − 10 = 1 ticket. The fault requires neither an incorrect addition nor a torn number; the threads started from the same old value.

  5. Change only the order of actions

    Start again from the same n. Let A complete L, K, E before B reads: A writes 11 tickets. B then reads r with subscript B = 11 tickets, calculates 11 + 1 = 12 tickets and writes 12 tickets. The shortfall becomes 12 − 12 = 0 ticket.

    Independent check: counting the new tickets gives 10 + 1 + 1 = 12 tickets, matching this sequential order. We kept the data and instructions of each thread; only the interleaving changed. An interleaving mixes actions while respecting the internal order of each thread. The one that loses an update is enough to refute the guarantee “the counter is always correct” in our model.

  6. Describe what a fix must guarantee

    The boundary to protect covers the entire read, calculate, write sequence on C. If A has read a value and is preparing its replacement, letting B prepare its own replacement from the same old value allows the fault. A future protection mechanism must prevent this situation or detect the change and recalculate correctly.

    This unit establishes the need; the next will study locks and semaphores. A randomly chosen delay does not enforce the required order. Seeing a correct result in a trial also does not demonstrate that all permitted interleavings are correct. This model describes a possible lost update without estimating its frequency in a real program.

Explain it in your own words

✿03 Common mistakes

  • “There cannot be a race condition on a single core.”

    Switching from A to B between the read and the write is enough. Replay the diagram line by line, with no simultaneous execution; the value read by B remains old when A writes.

    Review the successive actions in the diagram

  • “Adding to the counter fits on a single line, so everything happens as one block.”

    The written length of the program does not prove that its effect is indivisible. In our model, the update has 3 separate actions. Look for a guarantee covering the complete sequence; do not infer it from the write of an integer alone.

    Review the assumptions and the L, K, E breakdown

  • “I got the correct total, so the race condition is fixed.”

    The total can be correct when A finishes before B reads. That still allows the order in which all threads read the initial value. Produce that adverse order before drawing a conclusion; a delay with no guarantee does not rule it out.

    Test the claimed guarantee

Exercise 1 · Identify and explain

The counter changes while the copy waits

Start again from 10 tickets. A reads, then B reads. A calculates and writes its update. B has not yet calculated or written. Give C and the copy r held by B at this point; then predict the value B will write.

Hint 1

Draw separate boxes for the shared counter and the value B has already read and kept.

Hint 2

The write by A replaces C. No action refreshes the copy held by B.

Compare with the solution

A has written 10 + 1 = 11 tickets: C therefore holds 11 tickets. B read before this write; its copy remains 10 tickets.

B will calculate 10 + 1 = 11 tickets and write that value. The final counter will hold 11 tickets. The calculation does not start from 11, since B does not read C again.

Check your reasoning

  • Give C and r of B separately, using tickets as the unit.
  • Justify the old copy by the position of the read.
  • Predict the write from the copy, without inventing another read.

Exercise 2 · Reconstruct a counterexample

The same actions, different results

Starting from 10 tickets, write a trace in which B completes its update before A reads. Then write a trace in which B reads, A reads, B calculates and writes, then A calculates and writes. Calculate the final counter values and explain what changed.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Each thread must keep its own read, calculate, write order.

Hint 2

For each read, note the most recently written C, or the initial value if no thread has written yet.

Compare with the solution

Sequential trace: B reads 10, calculates 11, writes 11; A then reads 11, calculates 12, writes 12 tickets. The threads have switched roles compared with the example, but the total increase remains 2 tickets.

Interleaved trace: B reads 10, A reads 10, B calculates 11 and writes 11, A calculates 11 and writes 11. The final counter holds 11 tickets. The 2 threads have executed their actions; the last write uses a stale read value.

The requirement and additions are identical. The position of the read by A relative to the write by B changes the total from 12 to 11 tickets. This trace is enough to show that a race condition is possible; it does not give a frequency of occurrence.

Check your reasoning

  • Write all the actions of each thread in their internal order.
  • Obtain 12 tickets, then 11 tickets, justifying the reads.
  • Explain the difference through interleaving, without assuming simultaneous execution.

Exercise 3 · Transfer and critique

Is an indivisible integer write a sufficient guarantee?

The same fictional counter now starts at 20 tickets. A colleague guarantees that each read and each write of an integer is indivisible, then concludes that the 2 updates will necessarily produce the correct total. Each thread still adds 1 ticket. Refute or justify this conclusion with a complete trace, a shortfall calculation and the boundary that a fix must cover.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

The assumptions in the example already guaranteed indivisible reads and writes.

Hint 2

Have the threads read the counter before any write. Does the stated guarantee forbid this order?

Compare with the solution

The expected result is 20 + 2 × 1 = 22 tickets. Permitted trace: A reads 20, B reads 20, A calculates 21, B calculates 21, A writes 21, B writes 21 tickets.

Each read and each write was indeed indivisible. Yet the result is 21 tickets and the shortfall is 22 − 21 = 1 ticket. The stated guarantee still permits the faulty interleaving.

The fix must address the relationship between reading and writing: prevent concurrent updates from replacing C using the same old value, or detect this situation and repeat the calculation. Making only the last write indivisible does not cover the read, calculate, write sequence. The mechanisms that ensure this property will be studied in the next unit.

Check your reasoning

  • Preserve the stated assumptions in the counterexample.
  • Detail the expected result, the final result and the shortfall, with their units.
  • Locate the need for protection across the complete update.
  • Do not treat a result obtained with a hint as an achieved level; repeat the reasoning without support on another day.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What do A and B share, and what do they keep separately?

They use the same counter within the same process. Each thread has its position in its instructions and its working copies; writing to the counter does not refresh a value already read and kept.

Recall 2How can a race condition occur without simultaneous execution?

By alternating actions: A reads, B reads, each calculates from that old read value, then each writes. This interleaving respects the order of each thread and is enough to lose an update on a single core.

Recall 3Why does an indivisible write not make the update indivisible?

The update also includes the read and the calculation. The counter can change between the read value being kept and its replacement being written, even if no write can be split.

Recall 4What do a faulty order and a trial with a correct result prove?

A permitted faulty order refutes the guarantee of correctness in the model. A correct trial establishes only its result for the order actually followed; it does not rule out other interleavings. Neither alone measures a real frequency.

Reconstruct the reasoning

Without looking at the diagrams, reconstruct the process, the shared counter and the local copies. State the assumptions, then describe a trace that preserves the updates and a trace that loses one. Recalculate the expected result and the shortfall; finish with the boundary to protect and the proof that a successful trial does not provide.
