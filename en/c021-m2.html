HTTP request and JSON schema

Your goalBreak down a reservation request and check its JSON body before calculating what it allows you to reserve.

Before you start
c019-m5 : clocks and persistence · c018-m5 : contract tests and test doubles · c021-m1 : client, server and port

✿01 See the idea

The walking club has 8 water bottles available. On its page, you ask to reserve 3 of them under the group name “marche”. As with a paper form, you need to know which desk should receive the request and what to write in its boxes.

The HTTP request is the message the client sends to the server with its query. Its method states the requested operation; its path identifies the target resource; its headers provide information about the message; its body carries the reservation data here. The server returns a response with a status and, in our scenario, a JSON body.

JSON is a way of writing data. An object groups named fields; a string represents text; a number represents a quantity. A JSON schema describes the accepted forms: required fields, types and bounds. Text can be perfectly readable JSON while failing to meet this contract.

The scenario, stock and reservation service are fictional. We assume that the correct server has already been reached and examine an isolated request. Continuous transport, delays and permissions belong to the following units. Before continuing, predict why the number 3 and the text "3" might receive different verdicts.

The rule to remember

Read the HTTP destination and operation separately, then the body format, then its contract. Being able to decode data is not enough to accept it.

✿02 Follow an example

Worked example

Reserve water bottles for the marche group

The fictional service receives a request to create a reservation. Its contract limits each request to between 1 and 6 water bottles. The available stock S is 8 water bottles; the requested quantity q is 3 water bottles. No other stock movement occurs during processing.

  1. Build the HTTP envelope

    We choose the POST method to ask the service to create a reservation in the collection identified by the path /reservations. Our service defines the precise meaning of this route. Writing only the path does not specify the operation; writing only POST does not specify the resource.

    The Content-Type header receives the value application/json: this declares that the body of this request uses JSON format. This format name describes neither the required fields nor the quantity limits. The response will declare the format of its own body separately.

  2. Read the body as typed data

    The body is an object whose fields are nom and quantite. The nom field contains the string "marche"; the quantite field contains the number 3. In JSON notation, braces delimit the object, names are in double quotation marks, colons connect each name to its value and a comma separates the fields.

    The quotation marks around "marche" indicate text. Adding quotation marks around 3 would produce the string "3": the decoder could still read it, but it would no longer be a number. We provide no automatic conversion from text to a number.

    The quantite field contract defines the unit as a water bottle. The unit is not added to its numeric value: the text "3 gourdes" would also fail to meet the integer type.

  3. Set out the schema before calculating

    Our contract requires an object containing exactly nom and quantite, both required. nom must be a nonempty string. quantite must be an integer between m = 1 and M = 6, inclusive, in water bottles. No other field is accepted.

    In JSON Schema terminology, type sets the type and properties describes the fields. required lists the required names; describing a field in properties does not make it required. Setting additionalProperties to false, meaning false as a logical value, disallows fields that are not described here. For nom, string specifies a string and minLength sets a minimum length of 1 character; for quantite, integer specifies an integer, while minimum and maximum set its bounds.

    Decoding first checks that the text is readable JSON. Schema validation then checks the names, presence, types and constraints. The order of fields does not matter in this contract. The schema alone does not check the club’s current stock.

  4. Apply the checks to the request

    nom is present and contains the nonempty text marche. quantite is present, numeric and an integer. There is no additional field. We still need to compare its value with the bounds, without removing or ignoring any constraint.

    m≤q≤M:1≤3≤6

    The body therefore meets the schema. The service must still check availability: q ≤ S, or 3 ≤ 8 water bottles. This check consults the club’s state; it is separate from the form of the message. We can proceed under the stated assumptions.

  5. Calculate the remainder and check it another way

    R denotes the number of water bottles still available after this isolated request is accepted. S, q and R are integer counts in water bottles. Subtracting q from S removes exactly the water bottles allocated to the group; the upper bound M limits the request but does not replace the stock S.

    R=S−q=8−3=5 gourdes

    Inverse check: 5 + 3 = 8 water bottles, recovering the initial stock. Another way to see it: draw 8 boxes and allocate the first 3 to the group; you count 5 free boxes. The result also satisfies 0 ≤ R ≤ S. This arithmetic predicts the remainder under our assumptions; it observes no write to a server.

  6. Interpret the response within its stated scope

    In the fictional service, successful creation returns the HTTP status 201, meaning “created”, and a JSON body reporting the reserved quantity 3 and the remainder 5. Under the contract chosen here, a body that does not meet the schema receives the status 400 with an explanation of the rejection. This choice of response to schema errors belongs to our service.

    The status describes the outcome reported by the server; the body gives the specified details. They must be read together. The fact that a response can be decoded as JSON does not make it a success. Establishing that a real reservation has been recorded would also require an appropriate check of that record; our calculation on paper does not provide one.

✿03 Common mistakes

  • “I set application/json, so the fields must be correct.”

    Content-Type declares the body format. Then read the schema: nom and quantite are required, types must be correct, bounds must be met and there must be no additional field. The decoder and validator answer different questions.

    Revisit the envelope, then the schema

  • “The text "3" and the number 3 are the same.”

    Quotation marks make the value a string. The contract requires a numeric integer for quantite. Correct the type when preparing the body; assume no silent conversion by the server.

    Review the type diagram

  • “There is enough stock, so this quantity is allowed.”

    The stock S and the upper bound M have different roles. A request can leave a positive remainder and exceed the limit per reservation. First check all body constraints, then its compatibility with the club’s state.

    Examine the excess in the last exercise

Exercise 1 · Identification and repair

A readable request that is rejected

The client uses POST, the path /reservations and Content-Type with the value application/json. The object body contains nom equal to the string "marche" and quantite equal to the string "3". Identify the role of each element, locate the contract failure and propose the smallest correction.

Hint 1

Compare the quotation marks around the quantity with those around the group name.

Hint 2

Ask whether the fault concerns the HTTP method, JSON readability or the type of a field.

Compare with the solution

POST is the method; /reservations is the path; Content-Type is a header whose value declares JSON. The body contains the data. An object with these strings can be valid JSON: the failure occurs during validation of the quantite field.

Replace its text value "3" with the number 3, keeping nom as text. The bounds 1 and 6 are then met. Changing only the header would not correct the type; adding the unit to the string would not correct it either.

Check your reasoning

  • You assign the method, path, header and body their respective roles.
  • You distinguish readable JSON from an object that meets the schema.
  • You correct quantite without removing the quotation marks required around the text marche.

Exercise 3 · Diagnosis and objection

Enough stock, but the contract does not allow it

The same request, but quantite is the number 7. Someone says: “The JSON is readable and there are water bottles left after subtraction; we can accept it.” Respond by calculating how far the quantity exceeds the upper bound. Locate the failure, give the response specified by our contract and state whether the stock should decrease in this rejected trial.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Being an integer is not the entire rule: reread maximum.

Hint 2

Compare 7 separately with the upper bound 6 and the stock 8.

Compare with the solution

The quantity is numeric and an integer, but it exceeds the upper bound: 7 − 6 = 1 water bottle beyond the limit. The failure is a schema constraint, even though the JSON is readable and the available stock would be sufficient.

The subtraction 8 − 7 would give 1 water bottle; this positive remainder does not fix the violation. Our contract specifies the status 400 with an explanation about quantite. In this trial, rejected before creation, the stock remains 8 water bottles: the hypothetical subtraction result must not be applied.

One possible repair is to prepare a new request within the bounds, then repeat the checks. Removing the upper bound from the reasoning would change the contract instead of correcting the request.

Check your reasoning

  • You refute the positive remainder argument without claiming that the JSON is unreadable.
  • You keep the initial stock for the rejected request and connect 400 to the fictional contract.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1How do you break down the reservation request before reading its values?

POST is the method; /reservations is the path; Content-Type declares application/json here; the body contains the data. The client targets a server that has already been identified. The path alone does not specify the operation.

Recall 2Why do application/json and successful decoding not prove compliance?

The header declares a format and decoding reads its notation. The schema checks something else: required fields, types, bounds and additional fields. Our service must still check its current availability.

Recall 3What do quotation marks change in the quantite field?

3 is an integer; "3" is a string. JSON allows these values, but our schema requires the integer for quantite and provides no automatic conversion. The unit water bottle belongs to the contract.

Recall 4Does describing a field in properties make it required?

No. properties describes the values if the field is present; required lists the required names. Our contract requires nom and quantite, then rejects additional names by setting additionalProperties to false.

Recall 5What distinctions must you make after calculating the remainder?

The calculation predicts a remainder under assumptions. An HTTP response reports an outcome according to the service contract; it must be read with its body. Checking a real record requires appropriate evidence, which the calculation on paper does not provide.

Reconstruct the reasoning

Reconstruct without looking: name the operation, resource and format; describe the fields and their types; separate decoding, schema validation and availability; calculate the remainder with its units; check the calculation; interpret the status and body without attributing additional evidence to them.
