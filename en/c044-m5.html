Tool calls, limits and evaluation

Your goalFollow a calculation delegated to a tool, limit its invocations and evaluate the answer from the trace rather than its wording alone.

✿01 See the idea

At a workshop, you ask an assistant: “We have 3 boxes of 18 notebooks and 7 notebooks reserved. How many can we hand out? Check the calculation with the calculator.” It can write a convincing answer. To find out whether it used the calculator, you need to follow more than that sentence.

A tool call is a structured request produced by the model: a tool name and arguments, meaning the data to send to it. A program outside the model, which we will call the orchestrator, checks this request and decides whether to execute it. The tool then returns a result or an error. The model can receive this return in its context and write its final answer.

The calculator in our scene is called calculer. It accepts multiplication or subtraction of integers. It does not move any notebooks or check the actual stock. A correct calculation therefore guarantees neither that the model chose the right arguments nor that the stated inventory is accurate.

The scene, quantities and test traces are entirely fictional. We will check them by hand. This example reports no execution of a real model or tool.

The rule to remember

The tool request proposes; the orchestrator authorizes and limits; the tool returns; the final answer must remain faithful to that return.

✿02 Follow an example

Worked example

Check the notebooks while distinguishing calculation from inventory

The stated stock contains 3 boxes of 18 notebooks; 7 notebooks are reserved. The tool calculer is authorized for this calculation without affecting the stock, with a limit of 2 invocations per request. We require a trace that links each return to its call and a final answer that distinguishes the calculated quantity from stock actually observed.

  1. Set the contract before requesting the calculation

    The contract specifies the accepted inputs and what the output means. Our tool request includes a call identifier, the name calculer, an operation and its arguments a and b. These arguments are numbers; for multiplication, a counts boxes and b counts notebooks per box. For subtraction, both count notebooks. The unit is part of our interpretation of the calculation.

    The orchestrator checks the name against its list of authorized tools, the operation, the integer type of the arguments and the remaining budget. An invented name or invalid arguments cause rejection before execution. A correctly spelled name does not by itself grant authorization. The contract for this scene prohibits changing the stock.

    An accepted return contains the identifier of the same call, a success or error status and, only on success, an integer value. A return from an earlier call or a missing value field does not confirm the current calculation. We assume full boxes, the same number of notebooks in each box, no deliveries or distribution between calculations, and reservations that do not exceed the total.

  2. Establish an independent reference with pencil and paper

    Let c be the number of boxes, in boxes; q the contents, in notebooks per box; t the total, in notebooks; a the reserved notebooks; and r the available notebooks. Multiply c by q to count all the notebooks, then subtract a because the reservations are already part of that total.

    t=c×q=3×18=54 carnets
    r=t−a=54−7=47 carnets

    Reverse check: 47 available + 7 reserved = 54 notebooks. This recovers the total; r is between 0 and 54 notebooks. This check verifies our arithmetic reference without reading the model’s future answer. It does not check whether the notebooks are physically present.

  3. Approve the multiplication and receive its result

    The model proposes the call identified as lot: name calculer, operation multiplication, a = 3, b = 18. A sentence such as “I will calculate” does not replace this request that the program can process. The program checks its fields and approves it.

    Before this start, n = 0 invocations have begun. After approval, n = 1. The fictional return from lot reports success and a value of 54. We check its identifier and structure, then add it to the model’s context as a tool return. The trace thus distinguishes the request, the invocation and the received return.

    There is 2 − 1 = 1 slot left. The result 54 still includes the reservations: answering the availability question now would overlook part of the request.

  4. Subtract the reservations, then conclude

    The model proposes the call identified as reste: name calculer, operation subtraction, a = 54, b = 7. The orchestrator uses the value received from lot and checks the budget before starting. The return from reste reports success and a value of 47; it too enters the context.

    The counter reaches 2 invocations. The permitted final answer is: “According to the stated quantities, 47 notebooks remain to hand out: 3 × 18 − 7. The calculation returns from lot and reste agree with this result. The physical stock has not been checked.”

    Writing this final answer does not require another invocation of calculer. The tool return adds to the context of this request; it is neither model training nor a guarantee of lasting memory.

  5. Define the limit and error handling

    L denotes the limit on tool invocations per request, n the approved invocations already started, and b the remaining slots. All are counts of invocations, with no physical unit. Our rule approves a new call only if n is strictly less than L, then increases n by 1 before launch.

    b=L−n=2−2=0 place restante

    Call number 3 is therefore blocked before execution. If a result is still missing, we report a stop without a confirmed calculation. If the result has already been received, we can present it without calling the tool again. The limit bounds invocations, not the running time of a tool that gets stuck: a time limit and a budget for model calls require additional rules.

    If lot returns an error, its slot remains used and it has no value. Replacing the error with 0 notebooks or reusing an earlier return is prohibited. Under our contract, we then stop the calculation and state that the tool did not confirm availability. A partial result does not become a complete result.

  6. Evaluate traces specified in advance

    Evaluation compares behavior against criteria written before reading the answer. Here, the nominal case requires the reference value, its correct unit, authorized calls within the budget and an accurate account of where the result came from. Error and limit cases require an honest stop; they do not require producing a quantity at any cost. The following traces are fictional exercise material, not observed model trials.

    Nominal trace: lot receives 54, reste receives 47, and the 2 returns are successes linked to their calls; the final answer reports 47 notebooks according to the stated stock. Verdict: compliant with the contract on this trace, since calculation, budget and justification agree.

    Error trace: the only invocation, lot, returns an error; the answer says “calculation result unavailable, stock unconfirmed”. Verdict: compliant stop. The counting task remains unfinished, even though the error handling is correct.

    Limit trace: after 2 invocations ending in errors, a new request appears; it is blocked and the answer reports the limit, with no confirmed quantity. The budget barrier works in this trace. Verdict on the entire chain: noncompliant, because our policy required stopping at the first error. A successful local check is not enough to validate the whole contract.

    False evidence trace: 0 invocations are executed, but the answer says “calculer confirmed 47 notebooks”. The value is right; the claimed source is false. Verdict: noncompliant. Repair requires removing this attribution or producing a new authorized trace with its actual returns, without rewriting the old one.

    The set contains 2 traces focused on stopping and 2 on a reported quantity, making 4 traces. It helps distinguish the criteria; it measures neither an actual success rate nor an improvement in the model. For a real evaluation, keep the requests, criteria, system version and resulting traces; also include an unknown tool and invalid arguments, then broaden the cases before making any generalization.

✿03 Common mistakes

  • “The model writes a call, so the tool has run.”

    A request may be rejected, never reach the executor or fail. Look for approval and then the return linked to the correct identifier, with its status and any value. Claiming that a tool ran requires an execution trace; claiming that it succeeded also requires its result.

    Follow the roles in the first diagram

  • “An error does not count against the budget.”

    Our counter increases when the approved invocation starts. Waiting for success before counting it would allow an endless repetition of failing calls. Distinguish this counter from proposals rejected before launch, and also provide a limit for model turns.

    Review the counter rule and stopping conditions

  • “The answer is the right number, so the whole chain is validated.”

    The False evidence trace has the right value but invents tool use. Check the arithmetic, arguments, budget, error handling and faithfulness of the answer separately. A calculation based on the stated stock does not prove the physical stock either.

    Compare the verdicts on the evaluation traces

The right result hides a prohibited repeat

For the same request, a system obtains 54 then 47 with the authorized calls, runs calculer again to check, then correctly answers 47 notebooks. Write the criterion this trace violates and an evaluation case that catches the fault. Add the expected behavior if the first invocation returns an error.

Hint 1

A criterion about the final answer alone does not see how many invocations have started.

Hint 2

Compare with the solution

The quantity is correct, but the new invocation brings the count to 3, beyond the limit of 2. The criterion must concern the trace: no invocation starts when n reaches L. Saying “the final answer is right” does not test this rule.

Case to prepare: after the returns from lot and reste, the model proposes calculer again. The expected result is rejection before launch; the answer may retain 47 notebooks, linking them only to returns already received. The counter must stay at 2. A test double can supply this proposal without calling a real model.

Additional error case: make lot return an error. The invocation is counted, the return contains no usable value and our policy stops the calculation with an explanation. Displaying 0 notebooks as the result or claiming 47 confirmed notebooks violates this contract.

To establish the system’s behavior, you would then need to run these cases on the candidate system and keep their traces. Describing them on paper prepares the evaluation; it does not establish that it was run.

  • Your case requires rejection before invocation number 3, with the counter remaining at 2.
  • You define the expected output on error without inventing a numerical value.
  • You distinguish a designed evaluation from one that has been run and recorded.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Which steps separate a tool request from a result the model can use?

The model proposes a name and arguments; the orchestrator checks and approves the request; the tool runs; a return linked to that call reports success or error; this return can enter the context. A request alone proves none of these subsequent steps.

Recall 2When does our counter increase, and what does its limit guarantee?

It increases before each approved invocation, even if it fails. The limit bounds this number of invocations. It does not by itself limit a tool’s running time or calls to the model. Once it is reached, no new invocation starts.

Recall 3The return from lot is an error. Can we continue with a 0 value?

No. A missing value is not a 0 quantity. Under our contract, we keep the error and the used slot, then stop and state that availability has not been confirmed by the calculation.

Recall 4Why is an answer of 47 notebooks insufficient to validate the chain?

The value may be correct despite a false attribution to the tool or an invocation beyond the limit. You must check the calculation, units, approved calls, budget, errors and faithfulness of the answer to the returns. This still does not check the physical stock.

Recall 5Does adding a tool return to the context mean that the model has been trained or that the result will be remembered over time?

No. This return supplies information to the current inference. Changing the parameters or keeping information over time requires a separate mechanism and its own evidence.
