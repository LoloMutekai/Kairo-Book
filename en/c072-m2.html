Level 2 · C072·M2

Hash chains and their limits

Your goalRecalculate the links in a logbook, identify a break and specify which reference can detect a rewritten history.

Before you start

✿01 See the idea

In a workshop, a logbook records a visual inspection, lubrication and the closing of a machine casing, in that order. For each entry, a hash is calculated from its content and the previous hash. The next entry therefore carries a dependency on what came before it.

Imagine someone replacing “lubrication completed” with “lubrication postponed”. If they keep the recorded hashes, recalculation no longer matches the hash on that row. If they also recalculate the subsequent hashes, the logbook can become consistent again. To recognize the earlier history, a reference must have been kept beyond their reach.

The reference in our scene is a closing record, kept separately, which this person cannot replace. It identifies the logbook, the calculation rule, the starting value, the number of entries and the expected final hash. This protection is an explicit assumption of the exercise, rather than a property created by hashing.

All events and codes are fictional. To work through the calculations with a pencil, we will use a toy hash that is deliberately easy to fool. The diagrams and numerical results concern this toy model; they do not measure the security of a real cryptographic method.

The rule to remember

Checking the links establishes internal consistency. Then comparing against a protected closing record ties this consistency to a specific version, under the assumptions of the hashing method used.

✿02 Follow an example

Worked example

Recalculate the logbook, then modify it

The fictional logbook contains 3 entries in this order: visual inspection, code 12; lubrication completed, code 25; casing closed, code 9. These codes identify labels; they do not measure a duration or an amount of oil. The starting value is 7. The closing record expects this length and final hash 78.

  1. Define a link and what is checked

    i is the position of an entry, from 1 to n; n is the number of entries. eᵢ denotes the full content of the entry at that position. hᵢ is the hash after that entry; h at position 0 is the agreed starting value. E transforms an ordered pair into a sequence of bytes using canonical encoding: the same values produce the same bytes, and field boundaries are unambiguous. H is the deterministic hash function applied to these bytes. Hashes are identifiers with no physical unit; positions are counts.

    hi=H(E(hi−1,ei))

    A row stores its content, its predecessor’s hash and its own hash. To verify it, start from the expected starting value; compare the recorded predecessor with the previous verified hash, then recalculate the row’s hash and compare it with the recorded hash. Stop at the first mismatch. After checking the links, compare the length and final hash with the closing record.

    For a real cryptographic hash, we assume that it is impractical to construct a different encoded history that preserves the expected hash. This assumption and protection of the record are necessary. The public starting value makes the calculations reproducible; by itself, it does not prove which history was preserved.

  2. Set up the toy model for calculation

    In the toy model, p is the previous hash and x is the event code. T(p, x) is the remainder when 3p + x is divided by 101 using integer division. “Remainder” means subtracting the largest multiple of 101 that does not exceed this sum. The result is an integer between 0 inclusive and 101 exclusive. p, x and the result have no physical unit.

    T(p,x)=(3p+x)mod101

    The symbol mod asks for this remainder, rather than the quotient. T replaces the calculation H(E(p, e)) only for our demonstration. Here, the stated codes represent all the fictional content; in a real logbook, leaving an editable field out of the hash calculation would leave that field unchecked. T does not have the cryptographic resistance assumed for H.

  3. Process the visual inspection

    The first entry receives the starting value 7 and the code 12. Multiplying the predecessor by 3 and then adding the code makes the result depend on both inputs: 3 × 7 = 21, then 21 + 12 = 33. This sum is less than 101, so its remainder is already 33.

    Store the predecessor 7 and the hash 33 with this entry. The next calculation will use 33, rather than the starting value again.

    T(7,12)=33

  4. Incorporate the lubrication and reduce the sum

    The lubrication receives 33 as its predecessor. Calculate 3 × 33 = 99, then 99 + 25 = 124. This sum contains 1 times 101; subtract it: 124 − 101 = 23. The result is indeed between 0 inclusive and 101 exclusive.

    Check by reconstructing the division: 101 × 1 + 23 = 124. The entry therefore stores the predecessor 33 and the hash 23.

    T(33,25)=124−101=23

  5. Close the logbook and check the expected version

    The casing closure receives 23. We obtain 3 × 23 = 69, then 69 + 9 = 78. This sum is less than 101, so the final hash is 78. The recorded predecessors must be, in order, 7, 33 and 23; the recalculated hashes must be 33, 23 and 78.

    The intact chain has 3 entries and final hash 78, matching the record. This checks this representation of the logbook using our toy model. Even with a robust hash, this agreement would not prove that lubrication actually took place: a statement that was false when first entered can be linked into a perfectly consistent chain.

    T(23,9)=78

  6. Modify an entry, with or without recalculation

    Replace lubrication completed, code 25, with lubrication postponed, code 26. Leaving the recorded hash 23 creates a break: recalculation gives 99 + 26 = 125, then 125 − 101 = 24, which differs from 23.

    If the person now records 24, they must also change the predecessor of the casing closure and its own hash. The calculation gives 3 × 24 = 72, then 72 + 9 = 81. The rewritten chain is consistent, but the protected record expects 78, rather than 81.

    Another check: the code increased by 1; here, without crossing the next multiple of 101, the final hash increases by 3 × 1 = 3, as confirmed by 81 − 78 = 3. Recalculation is public: rebuilding a chain with a new final hash requires no secret. If the record could be replaced along with the logbook, this check would no longer identify the earlier version.

  7. State the limits without promising the impossible

    Deleting the last entry leaves a consistent prefix: inspection followed by lubrication, with 2 entries and final hash 23. A verifier that examines only the remaining links may accept it. The closing record, however, expects 3 entries and final hash 78. The same precaution applies when an earlier valid version is presented in place of the expected version.

    The toy model has an additional weakness. Code 126 represents “bearing replacement” in our fictional logbook. It differs from 25 by 101. At the same position, 99 + 126 = 225, and 225 − 202 = 23, with 202 = 2 × 101. Closing the casing again gives 69 + 9 = 78. The content changes, but the length and final hash stay the same: this is a collision, where different inputs give the same hash. Our toy model therefore cannot guarantee integrity even with a protected record.

    Cryptographic hashing aims to make such constructions impractical; it does not make collisions mathematically impossible. It does not block writing to the logbook, identify the author by itself or hide the entries. Here we are learning to check the dependency between rows and to limit our conclusion; mechanisms for signatures, secrecy and provenance require their own evidence.

✿03 Common mistakes

  • “A hash chain prevents any modification of the logbook.”

    The calculation removes no write permissions. Changing only the lubrication code produces 24 on recalculation, compared with the recorded 23; rebuilding all the links produces a consistent chain with final hash 81. Specify what the person can replace and where the reference is protected.

    Revisit the modification, with and without recalculation

  • “All the remaining links agree: the logbook is complete.”

    A prefix can retain correct links after the end is deleted. Compare its length and final hash with the expected closing record for the relevant logbook; a known starting value does not provide the expected length.

    Examine the shortened logbook in the last exercise

  • “The same final hash always proves the same history.”

    Our toy model produces 23 with either code 25 or code 126, then the same final hash 78. A conclusion about integrity requires a hash resistant to deliberate collision construction, unambiguous encoding and a reliable reference. It still proves neither the author’s identity nor that lubrication actually happened.

Compare with the solution

The inspection still gives 33. The recorded lubrication predecessor, 33, is therefore correct. Its recalculated hash is 99 + 26 − 101 = 24, compared with the recorded 23: this is the first mismatch encountered. This location indicates the first check that fails, without identifying the author or the time of the alteration by itself.

To rebuild, replace the lubrication hash with 24, the predecessor of the casing closure with 24 and its hash with 81, because 3 × 24 + 9 = 72 + 9 = 81. The links then agree. The record still expects 3 entries and final hash 78: the length matches, but the final hash differs.

The independent check 81 − 78 = 3 recovers the effect of the code increase propagated by the factor 3. Rejection comes from the reference that remained intact; it does not come from any impossibility of recalculation.

Exercise 3 · Critical transfer within the same logbook

Can a shorter logbook pass the check?

The casing closure disappears. The original inspection and lubrication remain. Someone announces “no break, so the logbook is complete and lubrication really happened”. The remaining links agree: starting value 7, inspection 33, lubrication 23. The internal check can therefore be green. However, the closing check compares 2 entries and final hash 23 with the expected 3 entries and final hash 78; it rejects this shortened logbook.

If the person can also replace the record with length 2 and final hash 23, agreement with this new record no longer distinguishes the prefix from the previously expected version. A reliable reference tied to the correct logbook and closing record must be found. A record copied alongside the file under the same control does not satisfy our protection assumption.

Finally, even a complete logbook matching a reliable reference attests to entries under the stated assumptions. It does not demonstrate the physical act of lubrication. The conclusion must distinguish consistency, agreement with the expected version and evidence of the action. ✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What information goes into calculating a chained hash?

The entry’s content and the predecessor’s hash, encoded together canonically. Their order and boundaries must be unambiguous.

Recall 2How do you check a row before moving to the next one?

Compare its recorded predecessor with the previous verified hash, recalculate its hash using its content, then compare it with the recorded hash. Begin with the expected starting value and stop at the first mismatch.

Recall 3Why can a fully recalculated chain pass the link check?

The calculation is public and the person can rebuild all the links. A reliable closing record kept beyond their reach and tied to the correct logbook allows comparison of the length and final hash with those of the expected version.

Recall 4Why does a consistent prefix fail to prove that a logbook is complete?

Deleting the end does not change the remaining links. A reference specifying the expected closing record is needed; the starting value alone does not determine it.

Recall 5Which limits must be recalled before drawing conclusions from hashes?

Integrity depends on the hashing method, encoding and reference; our toy model allows easy collisions. Chaining alone proves neither the author’s identity nor the stated action, and it does not make the content secret.
