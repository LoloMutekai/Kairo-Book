Level 1 · C021·M3

WebSocket and events

Your goalFollow a WebSocket channel and explain how a received message does, or does not, become an update to the order board.

Before you start
c019-m5 : clocks and persistence · c018-m5 : contract tests and test doubles · c021-m1 : client, server and port · c021-m2 : HTTP request (query) and JSON schema

✿01 See the idea

At a juice counter, a tablet displays 4 pending orders. The kitchen prepares the drinks behind a partition. How can it announce a change without the tablet constantly asking, “What about now?” Imagine a phone line left open: when the queue changes, the kitchen can speak over that same line.

The tablet acts as the client; the kitchen program acts as the server. WebSocket is a protocol that establishes a persistent communication channel between them. Once it opens, either side can send messages while the channel remains available, without a new HTTP request (query) for each message. In the standard mechanism, an HTTP handshake first requests a switch to the WebSocket protocol; here we follow what happens after the channel opens.

An event is a notification that the program receives: for example, “the channel is open” or “a message has arrived”. A handler is the part of the program called in response. The message handler still has to read the content, recognize its meaning and decide what to change. An open channel does not fill in the board by itself.

The scene and all its quantities are fictional. On this page, the server sends the full number of orders still pending, never a number to add. The first diagram shows the channel; the second follows the work needed after reception. No response time or actual benefit is measured.

The rule to remember

The channel carries data; the event notifies the program; the handler interprets the message contract and updates the local state.

✿02 Follow an example

Worked example

The same queue, from the kitchen to the tablet

The board and the kitchen start with 4 pending orders. The kitchen then accepts 2 new orders and serves 3 orders. It sends a complete state after each of these changes. Between these states, a message of type “presence”, defined by the application, arrives without any count. Let us follow the connection, the content and the displayed result.

  1. Separate channel activity from order activity

    In the browser’s WebSocket programming interface, open signals opening; message signals the arrival of a message; error signals a communication error; close signals closure. These English names are the technical event identifiers. A handler is associated with each one. Opening allows data to be exchanged; it does not say that an order has been served.

    The message handler receives data. In our contract, these are text messages representing JSON; WebSocket also supports binary messages. The protocol does not require JSON. The application type “file” will be a field in this content: it is distinct from the event name message.

  2. State the contract and assumptions

    Let A be the number of orders pending at the start, E the number of incoming orders and S the number of orders served during the period. All these quantities are counts, measured in orders. There are no other additions, servings or cancellations; the orders served belong to the queue. N denotes the final count in the kitchen. D denotes the count displayed on the tablet; C denotes the count carried by an accepted message.

    The expected content is a JSON object: the type field has the value “file” and the en_attente field has the value 6 here. The type field selects the action; en_attente carries C, an integer greater than or equal to 0, measured in orders. The handler decodes the JSON text, checks these fields and replaces D with C. The arrow ← is read as “receives the value”: it assigns a value to the display. The handler does not turn invalid content into a count of 0. The type “presence” is recognized but does not change D.

    In this worked example, the channel stays open, and states sent over this same connection are received in the order they were sent. Each handler then finishes processing before the next one. We assume that the content is checked and the display actually updated. We do not assume that a message sent during a disconnection is recovered.

    N=A+E−S;D←C

  3. Calculate the first state to send

    The kitchen has A = 4 orders and accepts E = 2. We add because these orders join the same queue: 4 + 2 = 6 pending orders. The server sends content of type “file” with en_attente equal to 6.

    The message event triggers the tablet’s handler. The text is decoded, the type and integer are checked, and D then takes the value C = 6 orders. Adding this count to the old count would give 10 orders: that would count the orders already present a second time.

  4. Receive another type without changing the count

    The next message carries the type field with the value “presence”. This is still a browser message event. But its content calls for a different response: in this scene, recording that the server has sent a presence notification. D stays at 6 orders.

    This message promises neither the current state of the queue nor that an order has been served. An application that only displayed “message received” without reading type could not distinguish these meanings.

  5. Calculate and apply the new complete state

    The kitchen serves S = 3 orders. We subtract the orders leaving the queue: 6 − 3 = 3 pending orders. The server sends a JSON object whose type is “file” and whose en_attente is 3. This content announces the new complete state, not an additional quantity to serve.

    The handler applies the same contract: D takes the value 3 orders. It calculates neither 6 + 3 nor a difference between messages. The kitchen calculates its queue; here the client copies the accepted count. Other applications choose change messages whose values must be added: their contract must then specify this.

    N=4+2−3=3 commandes

  6. Check the counts and the scope of the evidence

    Check by conservation: the 3 remaining orders and the 3 served orders represent 6 orders. This is indeed the total of the 4 initial orders and the 2 incoming orders. We recover the result without simply repeating the same subtraction.

    Check the handler: 3 message events were received; 2 carry queue states and cause 2 replacements. The presence notification does not change this count. The expected trace of D is 4, then 6, then 6 again, then 3 orders.

    To verify the display in a real application, we would need to observe reception, the accepted content and the resulting board. Our fictional trace explains what would need checking; it does not demonstrate any real communication. Finally, a count sent by the server does not by itself prove that the drinks were physically handed over.

Explain it in your own words

Without looking at the text, draw the channel, then describe the chain event → decoding → contract → replacement. Why does the presence message leave the count unchanged? Then justify the final count by conservation and name the evidence that opening a channel does not provide.

✿03 Common mistakes

  • “The channel is open: the board must be up to date.”

    Opening establishes the possibility of communication. Next, look for a message containing the expected state, its handler, the result of the check and the display produced. Without these steps, you know the state of the channel, not the state of the board.

    Review the diagram of reception and processing

  • “All message events mean the same thing.”

    message names the arrival of data. The type field in the content carries its meaning for the application. The “presence” notification and the “file” state arrive through the same event but do not trigger the same change.

    Revisit the passage about the presence message

  • “Every number received is added to the displayed number.”

    Read the contract again: the number is a complete state. Adding the states to the old count would produce 10, then 13 orders, instead of 3. The last calculation exercise asks you to identify these 10 orders counted in excess.

    Compare replacement and addition in the exercises

Exercise 1 · Recognize and explain

The event name is not enough

The tablet displays 4 orders. It receives open, then message with an object whose type is “presence”, then message with an object whose type is “file” and whose en_attente is 6. All content satisfies the contract. Give the count after each event and the number of replacements. Explain what the type field does.

Assisted answer: try this exercise without help later.

Hint 1

Opening changes the state of the channel. It does not contain an order count.

Hint 2

Among the received contents, look for the one that carries a queue state.

Compare with the solution

After open: 4 orders, the initial count is kept. After the “presence” message: still 4 orders. After the “file” message: 6 orders. There is 1 replacement, requested by the only content of type “file”.

The browser announces arrival through message. The handler then reads type to choose the intended response. The same reception event can therefore lead to different processing depending on the content.

  • I give 1 replacement and link it to the “file” content.
  • I distinguish the name message from the type field.

Exercise 2 · Calculation and diagnosis on paper

Why the incorrect board count grows

Start again with 4 displayed orders and the full sequence from the example. A faulty handler ignores “presence” but adds each “file” count to the previous count. Calculate its result, compare it with the correct result and check the conservation of orders. Finally, if the server sends the complete state 3 again without any change to the queue, what should the correct handler display?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

The faulty handler starts with 4 + 6. The correct handler replaces the count.

Hint 2

To check the kitchen, add the remaining and served orders; compare this with the total of initial and incoming orders.

Compare with the solution

The faulty processing gives 4 + 6 = 10, then 10 + 3 = 13 orders. The correct result is 3 orders; the difference is 13 − 3 = 10 orders. The error comes from the meaning assigned to the content, even though the messages arrive correctly.

Conservation requires 3 + 3 = 6 orders, just as 4 + 2. The faulty count does not match this history of the queue. Transport and the application rule must therefore be checked separately.

Receiving C = 3 orders again still calls for D ← C. The display stays at 3 orders. Repeating a complete state does not mean adding a new quantity. This check uses only the stated contract; it does not assume that WebSocket eliminates repeated messages.

Check your reasoning

  • I work through both faulty additions to 13 orders.
  • I justify 3 by conservation, using orders as the unit.
  • I keep 3 orders after the new identical state and explain why.

Exercise 3 · Transfer and limits of evidence

What do we know after closure?

After the last valid state 3, the browser signals close. The kitchen keeps working behind the partition. Later, another channel opens, but no queue state has been received yet. One person wants to display 0 orders; another wants to present 3 as the confirmed current count. What information can be displayed honestly, and what observation is missing?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Closure does not describe any operation on the order queue.

Hint 2

Separate the last value received from what is known now. Opening still does not contain any count.

Compare with the solution

The last known value is 3 orders. The current count is unknown, because the kitchen may have accepted or served orders since then. We can keep 3 with the label “last state received, freshness unconfirmed”; neither close nor the new opening justifies 0 orders or a confirmed current count.

What is missing is a new valid queue state and a check that it has been applied to the board. The new connection does not prove that changes made during the interruption have been recovered. Choosing timeouts and the recovery method belongs to the next unit; here we determine what can be concluded from the observed events.

Check your reasoning

  • I keep 3 as the last value received, with an explicit qualification about its freshness.
  • I do not turn closure into an empty queue.
  • I ask for a valid state and its application, without attributing a history to the new opening.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does a WebSocket channel provide after it opens?

A persistent channel over which the client and server can each send messages during the connection, without a new HTTP request for each message. The server can send an update without waiting for a new request.

Recall 2What is the difference between the message event and the type field in our JSON?

message notifies the program that data has arrived. The type field describes what the content means for the application; the handler reads it to choose the processing. WebSocket does not require this content to be JSON.

Recall 3What steps connect reception to the displayed count?

The handler is called, decodes the JSON text, checks the type and the nonnegative integer count, then replaces the displayed state if the contract is satisfied. Invalid content must be reported without inventing a count of 0.

Recall 4Why does receiving 3 orders again not increase the displayed queue?

The contract carries the full current count: the display is replaced with 3 orders. Addition would only be appropriate for a different contract defining a change to apply.

Recall 5What does opening a channel prove, and what is still needed to announce an up-to-date board?

Opening establishes the possibility of exchanging data at that moment. A valid state still has to be received, and its processing and the resulting display checked. Opening proves neither the recovery of a history nor the physical serving of a drink.
