React components and state

Your goalPlace a shared quantity in the right component, follow its update, and recalculate the displays that depend on it.

Before you start

✿01 See the idea

In a fictional workshop, you choose how many equipment kits to request. The batch allows you to request 5. The selector shows 2 kits requested, and a summary shows 3 still available. You press Add: both displays must describe the same request.

Imagine a central record that the selector and the summary each read a part of. If each keeps its own editable copy of the quantity, they can contradict each other. With a shared quantity, the summary can always recalculate the subtraction.

React is a library that builds interfaces from components. Here, a component is a function that describes a piece of the interface from what it receives and what it remembers. Atelier contains the Commande and Bilan components: these names refer to functions, not predefined HTML elements.

A property, called a prop in React code, is an input supplied by the parent to the child. State is memory that React keeps for a component instance between renders. A render is the calculation of the interface description; React then uses this description to update the DOM, the tree of elements on the page.

Here, capacity is a fixed value for the batch. The requested quantity is the state that changes. The number still available is calculated from these values. Everything is local and fictional: clicking changes a displayed request without preparing or shipping a kit.

The rule to remember

Keep the quantity in the shared parent; pass down the values and an action function; recalculate the summary from that same quantity on every render.

✿02 Follow an example

Worked example

Add a kit to the workshop request

The fictional capacity is 5 kits; the requested quantity starts at 2 kits. A click must add 1 kit to this quantity, then update the selector and summary. Follow the relevant data and instructions without running an application.

  1. Define the contract and units

    Let q be the requested quantity, C the capacity, and r the number still available for this request. These quantities are whole-number counts of kits. The step p is the quantity increment for an accepted Add action; it is 1 kit and is also expressed in kits. Capacity stays fixed during the calculation; no other action changes the quantity.

    We keep the same instance of Atelier in the same position in the interface. Local state is not saved storage: closing and recreating this instance, or reloading the page without a saving mechanism, can reset the quantity to its initial value.

    0≤q≤C;r=C−q

    The relation r = C − q is enough to define the summary. Initially: 5 − 2 = 3 kits available. We do not need to store r separately.

  2. Give the shared state an owner

    Commande must display the quantity and request changes to it; Bilan must read the same quantity. Their shared parent Atelier therefore keeps this state. This placement avoids having to synchronize copies in the children.

    The statement const [quantite, setQuantite] = useState(2) goes at the start of the Atelier function, outside any condition or loop. useState is the function provided by React that declares this memory. quantite is the value for the current render; setQuantite is the function that requests its update. The square brackets give names to the elements of the returned pair.

    The argument 2 initializes this memory when the instance is created. It does not automatically reset the quantity to 2 on every new render. By contrast, a simple local variable initialized to 2 would be recreated on every call to the function.

  3. Pass down values and an action

    Atelier supplies quantite and ajouter to Commande. The JSX expression <Commande quantite={quantite} onAjouter={ajouter} /> describes this child; JSX is a notation for describing the interface in JavaScript code. Curly braces insert the value of an expression. The names quantite and onAjouter are the properties chosen for this component.

    Commande uses the received quantity in its text and places onClick={onAjouter} on its Add button. onAjouter refers to the function received from the parent; the curly braces pass the function without calling it during the render. When the click happens, React calls this event handler.

    Bilan receives quantite and capacite, then calculates const reste = capacite - quantite during its render. A child reads its properties; to request a change to the parent's state, it calls the function passed down to it. It does not rewrite the received property.

  4. Describe what Add means

    The parent defines ajouter with an update based on the previous quantity: setQuantite(precedente => precedente + 1). The => symbol describes a function: it receives a value named precedente and returns that value increased by 1. React will use the pending value when it processes this function.

    This statement describes the case where adding is still possible. To respect the contract across the full range, we can write setQuantite(precedente => precedente < capacite ? precedente + 1 : precedente). Here, the step is exactly 1 kit and the quantity is an integer: if it is below the integer capacity, this step will not exceed it. The form condition ? resultatSiVrai : resultatSiFaux returns resultatSiVrai when condition is true, otherwise resultatSiFaux.

    The updater function only calculates the next state. It does not order any equipment or send any message: React may call it again to check its purity during development. Its result must stay the same for the same input.

  5. Calculate the next state and read the right moment

    The click starts from a render where quantite is 2. The guard allows the addition because 2 is less than 5. We must add the step to this quantity:

    qsuivant=q+p=2+1=3 trousses demandées

    The subscript word “suivant” means “next” and denotes the next value, with no additional unit. Calling setQuantite requests this change; it does not replace the quantite variable in the handler already running. Reading quantite just after this call, in the same handler, still gives 2. The next render will receive 3.

    This delay is explained by a snapshot: the handler was created with the values from its render. An update request does not rewrite this snapshot. We must distinguish the value read during the click from the value used in the next render.

  6. Recalculate the displays and check the total

    On the new render, Atelier passes 3 to Commande and Bilan. Commande displays 3 kits requested. Bilan subtracts this quantity from the fixed capacity: 5 − 3 = 2 kits still available.

    q+r=3+2=5=C

    This check correctly recovers the batch capacity in kits. Another check follows the change: the request gains 1 kit and the available count loses the same amount, from 3 to 2. These calculations measure neither the number of renders nor how long a display lasts.

    A new render does not imply recreating the entire DOM. React compares the calculated description with what was displayed and applies the necessary changes. The expected result here is a consistent pair of numbers; our static reading does not constitute an observation of this result in a browser.

  7. Follow a sequence of updates in the same handler

    Start again from 2 kits. Suppose the same handler makes 2 calls to setQuantite(quantite + 1), with no new render between calls. Each expression reads the same snapshot 2 and requests replacing the state with 3. Replacing it with 3, then again with 3, leaves 3 kits requested.

    With 2 calls to setQuantite(precedente => precedente + 1), React processes successive transformations. The first receives 2 and returns 3; the next receives 3 and returns 4. The summary becomes 5 − 4 = 1 kit available, and 4 + 1 = 5 kits.

    The results differ by 1 kit. This comparison concerns calls placed in the same handler. It does not say that separate clicks necessarily lose an addition: they can be processed with separate renders.

✿03 Common mistakes

  • “Each component can remember its own quantity; they will eventually agree.”

    Separate states evolve separately. Place the quantity in Atelier, their shared parent, then supply it to the children. Recalculate the available count in Bilan instead of keeping an initial copy there.

    Review the diagram of the shared owner

  • “After setQuantite, quantite has already changed in my handler.”

    The handler keeps the values from the render that created it. Distinguish this snapshot from the pending state; to chain changes based on the previous value, pass an updater function.

    Review the steps on the snapshot and the sequence of updates

  • “I can call ajouter during the render; it simplifies the button.”

    onClick={ajouter} passes a handler. onClick={ajouter()} calls the function while building the interface; if it changes state during the render, it can cause repeated renders. Reserve this call for the click and keep the render calculation free of external actions.

Exercise 3 · Diagnosis and repair

A stale summary and a limit reached

After the addition in the example, Commande displays 3 requested. Bilan still keeps 3 available because it stored the initial result. Explain the inconsistency, repair the design, and propose a check. Then, in this same workshop, the request reaches 5 kits: what must Add do to respect capacity?

Hint 1

Add the displayed numbers and compare the total with capacity.

Hint 2

The available count can be recalculated. At capacity, compare a proposed addition with the limit before keeping it.

Compare with the solution

The displays report 3 + 3 = 6 kits, whereas the batch allows 5. This disagreement reveals a stale derived value; it does not demonstrate a problem with the physical batch.

Remove the separate state for the available count. On every render, Bilan calculates reste = capacite - quantite: 5 − 3 = 2 kits. The check recovers 3 + 2 = 5. Repeating an action and then reading the quantity and available count together distinguishes this repair from simply changing the initial text.

At 5 requested, 0 kit remains available. Adding without a guard would propose 6 kits, beyond 5. The bounded function keeps precedente when precedente is no longer less than capacite; the quantity therefore stays at 5. Checking this rule in the application would be separate from our calculation on paper.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does a React component calculate in the workshop?

A description of its piece of the interface from its properties and state. React uses this description to update the DOM; calculating the render does not prepare any kit.

Recall 2What is the difference between a received property and local state?

A property is an input supplied by the parent. State is memory that React associates with a component instance between renders. The child requests a change from the parent through a function passed down to it; it does not rewrite its property.

Recall 3Why does the available count not need its own state?

It follows entirely from the capacity and requested quantity. Recalculating it on every render avoids a stale copy and makes it possible to check that quantity plus available count equals capacity.

Recall 4Why can reading quantite just after setQuantite still give the old value?

The handler reads the snapshot of the render that created it. setQuantite requests state for a future render; it does not rewrite the variable in this handler.

Recall 5When is the function precedente => precedente + pas useful?

When the next state depends on the previous state, particularly when chaining transformations in the same handler. Each function receives the pending state produced by the previous one; it must only calculate its result, with no external action.
