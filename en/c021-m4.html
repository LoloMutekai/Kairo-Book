Level 1 · C021·M4

Timeouts and retries

Your goalSet a time limit for a locker availability check, decide when to retry it, and distinguish a missing response from an action that did not take place.

Before you start
c019-m5 : clocks and persistence · c018-m5 : contract tests and test doubles · c021-m1 : client, server, and port · c021-m2 : HTTP request and JSON schema · c021-m3 : WebSocket and events

✿01 See the idea

At a parcel locker, you tap “Check locker”. The kiosk sends an availability query to the server, then waits for its response. The screen stays on “searching”. Should it wait indefinitely, try again immediately, or display that the locker is unavailable? Silence alone supports none of these conclusions.

A timeout sets how long the kiosk is willing to wait for an attempt. When it expires, the kiosk knows only that it did not receive the expected response in time. The server may have received nothing, may still be working, or may have responded without the response reaching the kiosk. The diagram shows this last possibility; it does not diagnose a failure.

A retry sends a new attempt. A pause before this retry spaces out the requests; an overall deadline limits the entire check, including pauses. These limits answer different questions: how much time for this call, how many calls, and how much time for the whole process?

The entire scene and all its durations are fictional. Here, the check is a read operation: it neither reserves nor opens the locker. We explicitly assume that repeating it does not change the server state. Availability can still change between responses; a new read does not guarantee the same content.

The rule to remember

Before each retry, check whether the operation may be repeated, the number of attempts, and the time remaining. A timeout describes the client’s wait; it does not determine the result on the server.

✿02 Follow an example

Worked example

Check the locker before the deadline

The kiosk’s HTTP availability check receives no usable response during calls A and B. At most 3 attempts are allowed, with a timeout of 1.50 s per attempt. The overall budget is 5 s, the first pause is 0.50 s, and the next pause doubles. In this fictional trace, the response to call C arrives 0.25 s after it is sent and meets the expected JSON contract.

  1. Define the limits before sending

    We use t for the time elapsed since the first request was sent, in seconds; it starts at 0 s. B = 5 s is the overall budget: here, the deadline is reached when t = B. Time is measured with a monotonic clock, which measures durations without following adjustments to civil time.

    τ, the Greek letter tau, denotes the maximum timeout for an attempt, in seconds: τ = 3/2 s = 1.50 s. N = 3 is the maximum number of attempts, with no unit. The initial request counts: N therefore allows at most 2 retries. The letters A, B, and C name the calls; the letter B on its own in formulas still means the budget.

    p denotes a pause, in seconds. The chosen pauses are 0.50 s, then 2 × 0.50 s = 1.00 s. This increasing interval gives the server more time to recover between requests. It guarantees neither recovery nor an optimal duration; this setting is chosen for the exercise.

    We assume a timer that covers the entire call, including connection and reception, and a check of the overall deadline. The local time spent on calculation and validation is ignored here. In a program, these tasks also take time: the clock must be read again before making decisions. A simple read timeout that restarts with each chunk received is not this overall limit.

  2. Choose an allowed retry

    The contract for this check allows availability to be read again without making a reservation. After a timeout, we allow another attempt at this read. A JSON contract error or an explicit refusal would not be fixed by blindly repeating the request: the response would need to be understood and the request corrected if necessary.

    The algorithm follows a simple rule: stop as soon as a usable response arrives; after a failure that permits a retry, check the counter, then check that the pause will leave time for a new call. It sends nothing if the attempt limit has been reached or if the pause would use all the remaining time. Attempts run one after another on the client; earlier processing may still continue on the server.

  3. Advance the clock to the second request

    Call A starts at 0 s. Since no usable response arrives before its limit, the wait ends at 0 + 1.50 = 1.50 s. The kiosk records a timeout; it does not conclude that the server did nothing.

    The pause starts now, after this wait. The next request is therefore sent at 1.50 + 0.50 = 2.00 s. Adding only the pause to the time of the first request would make the waits overlap on the client.

  4. Calculate what remains for the last call

    Call B starts at 2.00 s and ends its wait at 2.00 + 1.50 = 3.50 s. There is 1 allowed attempt left. The new pause is 1.00 s; call C can therefore start at 3.50 + 1.00 = 4.50 s.

    r denotes the time remaining when a request is sent, in seconds. We subtract the time already used from the budget, because the pauses have not reset the clock. For C:

    r=B−t=5−4.50=0.50 s

    d denotes the maximum wait actually allowed for this new call, in seconds. It must respect both τ and r: we take their smaller value. For the last call, the remaining budget is smaller:

    d=min(τ,r)=min(1.50,0.50)=0.50 s

    Without a response, C would be stopped at 4.50 + 0.50 = 5.00 s. Giving C the full timeout again would exceed the deadline. Our rule gives priority to the deadline if a response arrives at exactly that time: a usable response must arrive before this limit.

  5. Accept the response and stop retrying

    The response from C arrives after 1/4 s, a wait of 0.25 s. This duration is shorter than the 0.50 s allowed. The reception time is 4.50 + 0.25 = 4.75 s. The response is received before the deadline, then found to meet the contract under our timing assumptions.

    The remaining margin is 5 − 4.75 = 0.25 s. We stop immediately: the timeout is an upper limit, not a duration to fill. The result says that availability was checked; it proves neither a reservation nor an opening of the locker.

  6. Check the total time, including pauses

    Let us check the case where no call responds in another way. The waits total 1.50 + 1.50 + 0.50 = 3.50 s. The pauses total 0.50 + 1.00 = 1.50 s. Together: 3.50 + 1.50 = 5.00 s, exactly the budget.

    With a full timeout for every call, the waits alone would take 3 × 1.50 = 4.50 s. Adding the pauses would give 6.00 s, which is 1 s too much. The maximum number of attempts therefore does not, by itself, keep the total time within the intended limit.

    The response accepted in our fictional trace arrives at 4.75 s, before this upper limit. At the deadline without a response, an accurate screen would say “availability check unconfirmed” and offer an explicit next step; it would not invent an availability status. A read response arriving after the check has been abandoned must not silently replace a more recent check.

  7. Use the same caution if the button makes a reservation

    Now suppose that the button for the same locker requests a reservation. If the response is lost after the reservation is recorded, repeating the request may create another reservation when the server does not protect against duplicates. The HTTP method name or the absence of a response is not enough to establish that repeating the request is safe.

    An operation is called idempotent when repeating it has the same intended effect on state as executing it once. Our read satisfies the assumption that it does not change that state. For a reservation, an automatic retry would require a verified contract that prevents the effect from being repeated, for example a request reference that the server remembers durably. Without this, the result must remain unknown and a way to check this request must be provided. The timer does not cancel a reservation already made. Restoring a WebSocket connection does not resolve this uncertainty either.

Without looking at the timeline, reconstruct when C starts and how long it is allowed to wait. Explain why the last wait is shortened, then why the same timer does not allow a reservation to be blindly replayed.

✿03 Common mistakes

  • “The timeout has expired, so the server did nothing.”

    The timer describes only the client’s waiting limit. The server may have processed the request and the response may have been lost. For the locker reservation, keep the result unknown until suitable evidence determines it.

    Review the response lost between the server and the kiosk

  • “With 3 attempts, I will always stay within 5 s.”

    Add the calls and the pauses. Here, giving every call its full timeout would lead to 6.00 s. A shared deadline requires recalculating the time remaining before each call and shortening C.

    Repeat the check of the total time

  • “A network failure allows any request to be sent again.”

    Look at the request’s effect. Reading availability again is allowed by the contract in this scene; making a reservation may repeat an effect that has already occurred. Without a verified guarantee against duplicates, avoid automatic replay and check the outcome of the initial request.

    Handle the uncertain reservation in the last exercise

Exercise 3 · Transfer and objection

The reservation with no response

The button for the same locker now sends a reservation request. The server can create a new record each time it receives one and states no protection against duplicates. The kiosk reaches its timeout without receiving a response. Someone suggests retrying as with the availability check. Respond to this suggestion and specify what evidence to seek before deciding to send again.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Construct a case in which the server recorded the reservation but the response was lost.

Hint 2

Separate checking the initial result from making a new request that could repeat the effect.

Compare with the solution

The server may have created the reservation before the response was lost. Replaying without protection may create another one. A timeout therefore proves neither the absence of a reservation nor the safety of sending again.

The kiosk keeps the status “reservation unconfirmed” and does not replay automatically. There must be a defined way to check the outcome of the initial request: for example, a known reference and a server state that can be queried to determine its result. Simply reading “locker occupied” does not say who reserved it and is not enough.

If a contract prevents duplicates for the same request reference, you must still verify that the server enforces this contract, including after a restart, before relying on it. The kiosk cannot invent this guarantee. A time budget and a reconnection govern waiting and transport; they do not demonstrate this property of the operation.

Check your reasoning

  • You describe the case of a response lost after an effect has already occurred.
  • You distinguish an unknown result from a confirmed failure.
  • You reject automatic resending under the given assumptions and require evidence tied to the initial request.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does a timeout prove for the kiosk?

It did not receive the expected response in time. This does not say whether the server received nothing, is still working, or processed the request without a response being received.

Recall 2Which limits must be distinguished, and do pauses use the budget?

The timeout per attempt, the maximum number of attempts including the initial request, and the overall deadline. Pauses use the overall budget. A usable response stops the check before these limits.

Recall 3How do you find the allowed wait for a new call?

Measure the elapsed time t, subtract it from the budget B, and take the smaller value between this remainder and the timeout per call. If the attempt count is exhausted or the pause leaves no time, do not send a new call.

Recall 4Why should a reservation not be retried automatically like a locker read?

A reservation may already exist despite the lost response. Repeating it may repeat the effect. You must check the initial outcome or have an enforced contract that prevents duplicates; a timer does not provide this evidence.

Recall 5Without rereading, reconstruct C’s start time and its limit with the example’s settings.

The waits for A and B each take 1.50 s, separated by 0.50 s. After B, the pause is 1.00 s. C therefore starts at 4.50 s; out of 5 s in total, only 0.50 s remain. Its limit is 5.00 s.

Reconstruct the reasoning

Reconstruct the rule using the kiosk: name the read operation and its effect, set the timeout, counter, and deadline, place pauses after waits, recalculate the time remaining, and stop on a usable response or a limit. Finish with the lost response case: an ended wait does not prove the absence of a reservation.
