Level 2 · C072·M1

Digest and canonical encoding

Your goalConstruct the canonical bytes of a record, then explain what comparing their digests actually allows us to conclude.

Before you start
c022-m5 : untrusted inputs and injection · c070-m5 : minimum spanning tree · c017-m5 : reproduction protocol · c041-m5 : transactions and windows

✿01 See the idea

You are archiving a storage record: cabinet a = 1, box b = 2. One person writes the box first; another starts with the cabinet. The information is the same, but the recorded characters are in a different order. The scene and its values are fictional.

A digest is a summary calculated from a sequence of bytes, the small units that make up a file. Hashing is the operation that produces this summary. It examines the bytes supplied: it cannot infer either the meaning of the record or the differences in presentation that we want to ignore.

We therefore need to choose what “the same record” means. Here, we allow variations in field order and in spacing around punctuation. A canonical encoding imposes a unique representation for these equivalent presentations. Changing the box, however, changes the data and must remain visible in the bytes.

The first diagram separates this formatting from hashing. The second shows a poor way to summarize bytes: simply adding them. We will calculate this sum by hand to understand its weakness, without treating it as a cryptographic digest.

The rule to remember

Define which data are equivalent, specify their canonical bytes, then always apply the same hashing algorithm. A digest does not choose what “identical” means.

✿02 Follow an example

Worked example

Archive the storage record while distinguishing content from presentation

Copy A writes b before a and leaves a space after the comma; copy B writes a before b and leaves no spaces. Both specify cabinet 1 and box 2. Let us produce the same sequence of bytes, count them and calculate a checksum for which we can check every term.

  1. Define exactly which records are accepted

    The record d is an association between field names and their values. Field a identifies the cabinet, field b the box; these identifiers have no physical unit. In this small contract, the fields are exactly a and b, each appearing once, with an integer between 1 and 3. Every other case is rejected before encoding.

    Here, JSON is a way of writing this association: braces surround the record, quotation marks delimit the names, colons separate each name from its value, and the comma separates the fields. Field order has no meaning for this record. The strings below reproduce the characters in the copies exactly. Copy A leaves a space after its comma:

    {"b":2, "a":1}

    Copy B contains no spaces:

    {"a":1,"b":2}

  2. Write the canonical contract, then apply it

    C converts d to bytes: it writes a then b, keeps the names in double quotation marks, writes the integers in decimal digits with no leading 0 and adds no spaces. It encodes this text in UTF‑8, with no initial byte order mark or final newline. UTF‑8 is a rule for converting characters to bytes; every character in our domain occupies 1 byte here.

    Let us read the values in A and B again, then rewrite them according to this contract. In both cases, the text to encode is exactly:

    {"a":1,"b":2}

    This contract is limited to our record. Sorting the keys alone does not handle every case involving decimal numbers, accented text or repeated field names. We do not accept these cases here and do not claim to define a universal canonical format.

  3. Convert characters to bytes

    Here is the table we need, in decimal values: opening brace → 123, closing brace → 125, quotation mark → 34, comma → 44, colon → 58, letter a → 97, letter b → 98, digit 1 → 49, digit 2 → 50. A space, if present, has the value 32.

    Follow the characters from left to right. Each number below is the value of a byte; the semicolons only make the list easier to read and are not bytes added to the record.

    123 ; 34 ; 97 ; 34 ; 58 ; 49 ; 44
    34 ; 98 ; 34 ; 58 ; 50 ; 125

    The numeric value 1 therefore becomes the character “1”, encoded by the byte with value 49. We must not directly put a byte with value 1 in this position. The choice of written representation is part of the contract.

  4. Count what the hashing algorithm will receive

    A name in quotation marks occupies 2 + 1 = 3 bytes. The colon and the digit of its value add 1 + 1 = 2 bytes. Each field therefore occupies 3 + 2 = 5 bytes, and the fields together occupy 2 × 5 = 10 bytes.

    The braces and the comma occupy 2 + 1 = 3 bytes. The length n of C(d) is therefore:

    n=10+3=13 octets

    A byte contains 8 bits, each bit being 0 or 1. The input therefore represents 13 × 8 = 104 bits. Before canonicalization, A contains 13 + 1 = 14 bytes because of its space. Hashing A and B directly does not mean hashing the same bytes.

  5. Calculate a small sum, then understand its significance

    To work through a whole calculation with a pencil, define S as the sum of the byte values of C(d). S is an integer with no physical unit, expressed here in “sum units”. This checksum is used for teaching; it is not SHA and offers no cryptographic resistance.

    Start with the outer punctuation: 123 + 125 = 248, then 248 + 44 = 292 sum units.

    The names contain 4 quotation marks: 4 × 34 = 136. The letters give 97 + 98 = 195. Together: 136 + 195 = 331 sum units.

    The colons give 2 × 58 = 116; the digits give 49 + 50 = 99. Together: 116 + 99 = 215 sum units.

    S=292+331+215=623+215=838

    We can check the result by directly adding the list of bytes from the previous step. For A before canonicalization, changing the order does not change the sum; the single additional space would raise it to 838 + 32 = 870 units.

  6. Explain the role of the cryptographic digest

    For a cryptographic digest, choose H = SHA‑256. H is a deterministic function: the same bytes always give the same result h. Here it summarizes the input of 104 bits with an output of 256 bits. It is neither compression that allows us to recover the record nor encryption that would keep it secret.

    h=H(C(d))

    The output contains 256 ÷ 8 = 32 bytes. In hexadecimal, a notation that represents 4 bits per character, it occupies 256 ÷ 4 = 64 characters. These lengths are properties of the output format, not a measure of reliability.

    We do not work through the internal operations of SHA: h remains its symbolic result, without inventing a value. The preceding numerical calculation is entirely that of S. One aim of a cryptographic function is to make it difficult to construct distinct inputs with the same digest; it does not make collisions mathematically impossible. A collision is precisely this equality of outputs for different inputs.

  7. Check the encoding and limit the conclusion

    Count the list again in another way: 2 braces + 4 quotation marks + 2 letters + 2 colons + 2 digits + 1 comma = 13 bytes. Reading the fields of this text again does give a = 1, b = 2. This check distinguishes a counting error from a loss of content.

    A and B produce exactly C(d), so their canonical digests are equal. If we change only the box to 3, its digit is encoded by 51: the difference is 51 − 50 = 1. The sum becomes 838 + 1 = 839 units, but the length remains 13 bytes. Identical length therefore does not guarantee identical content.

    With H fixed and the calculations correct, different digests imply different inputs. Equal digests are not absolute proof of equality, because collisions exist. To use a digest to check for changes, we also need a reference kept through a trusted channel: replacing the record and its reference together would fool the comparison. The digest alone proves neither who wrote the record nor whether the storage information is true.

Explain it in your own words

Hide the lists. Reconstruct the canonical text from the record, justify every character and distinguish n, S and h. Why is changing the field order allowed, whereas swapping their values changes the data?

✿03 Common mistakes

  • “The text looks identical, so its bytes and digest must be identical too.”

    Start again from the characters actually encoded: the space in A adds 1 byte. First state which variations have no effect on the record, then apply C to both copies before H. The chosen equality of meaning comes from the contract.

    Review the contract and the byte count

  • “Sorting the keys is enough to obtain a canonical encoding everywhere.”

    The contract also specifies the domain, the form of integers, spaces, character encoding and the final newline. The rules for our record reject cases they do not define. Another application must state its own rules instead of adopting only the sorting rule.

    Reread the domain and all the rules of C

  • “The sum is the same: nobody could have changed the record.”

    Swap the values of a and b: the bytes change position but their sum remains 838. This example disproves the guarantee for S; it does not provide a collision for SHA. Even a cryptographic digest must be compared with a trustworthy reference.

    Construct the collision and discuss the reference

Exercise 3 · Critical transfer · defend a conclusion

Same checksum, different storage location

Compare the initial record a = 1, b = 2 with the record a = 2, b = 1. Show that they have the same S without adding everything again. A colleague then proposes replacing S with H and storing the record and its digest in the same editable folder. Can they conclude that the record is authentic and protected against any substitution?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

List the bytes removed and then added when the values swap places.

Hint 2

Distinguish the collision you have just constructed for S from a collision for H. Also ask who can replace the reference digest.

Compare with the solution

The digits swap positions. The punctuation and letters stay the same, and 49 + 50 = 99 in both cases. The sum therefore remains 838 units even though the storage location has changed: this is an explicit collision for S.

This collision proves nothing similar for H, which processes byte order according to its own algorithm. A cryptographic digest meets requirements that S does not, but it does not identify the author on its own. If someone can replace the record and recalculate the reference stored alongside it, their agreement does not reveal this substitution.

The remedy is to specify the intended property, keep a trusted reference beyond the reach of this replacement and state the encoding contract as well as H. The mechanism for authenticating the author requires separate proof; we do not construct it in this unit.

  • Identify a collision for S without claiming to have found one for H.
  • Describe how the record and its reference can be replaced together, then explain the limitation on identifying the author.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What does H receive, and what does its determinism guarantee?

H receives a sequence of bytes. With the same algorithm and the same bytes, it gives the same digest; it does not interpret the meaning of the record.

Recall 2How can you reconstruct C for our record without looking at the example?

Accept exactly a and b, with no repeats, and integers from 1 to 3; write a then b, names in quotation marks, integers with no leading 0, no spaces and no final newline; encode in UTF‑8 with no initial byte order mark. These rules are specific to this domain.

Recall 3Why is n = 13 bytes not enough to identify the record?

Replacing box 2 with 3 replaces one digit with another: the length remains 13 bytes while the content changes. Size checks length; it is not proof of identity.

Recall 4Which collision can you construct here, and what does it fail to prove?

Swapping a = 1, b = 2 to a = 2, b = 1 leaves S = 838 despite the different bytes. This is a collision for the sum S, not a collision calculated for SHA.

Recall 5What can you conclude from two different digests? And why does equality not identify the author?

With the same H correctly calculated, different digests imply different inputs. Equality remains compatible with a collision or with substitution of the data and its reference. Hashing alone does not attest to who produced the record.

Reconstruct the reasoning

Without rereading, reconstruct the path record → equivalence rules → canonical text → bytes → digest. Then explain why length, the sum S and the digest H do not provide the same evidence. Finish with the condition that the reference must be trusted, then give the counterexample with swapped values yourself.
