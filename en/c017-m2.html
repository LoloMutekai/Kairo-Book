Dependencies

Your goalIdentify the libraries needed for an analysis, including those used indirectly, and distinguish a list of versions from a verified reproduction.

Before you start
c016-m5 : documentation · c007-m5 : execution traces · c017-m1 : Git

✿01 See the idea

You share a small analysis of mass readings: the file pesees.csv, the script bilan.py and its Git history. On your machine, the script displays a mean mass and plots the readings. On the recipient’s machine, it stops: a library is missing. The same script does not necessarily find the same tools on another machine.

A library brings together reusable code. In this scenario, each library is distributed in its own package: a unit to install. A software dependency is something the program needs for the requested task. Here, bilan.py directly uses Table to read the file and calculate the mean, then Plot to draw the plot. Table and Plot in turn use Core: this library is an indirect dependency of the script, even though the script does not name it.

The mass readings, the Table, Plot and Core libraries, their versions A, B and C, and their relationships are fictional. These letters identify specific versions in our scenario; they indicate neither a quality ranking nor a compatibility rule. The diagram represents the declared requirements of these versions for this analysis.

The execution environment brings together what allows the script to run: in particular, the Python interpreter, which executes its instructions, and the libraries available to that interpreter. A version is an identified edition of a piece of software. Keeping code in Git does not automatically record the versions of the installed libraries.

The rule to remember

Start from the script, follow every requirement to the end and record the versions. Then compare this list with the environment actually used; the list alone does not prove that the analysis has been rerun.

✿02 Follow an example

Worked example

Sharing the bag analysis

The fictional file contains 3 masses: 98 g, 100 g and 102 g. The script must display their mean and produce a plot. Its reference environment contains Table version A, Plot version B and Core version C. We prepare the list of requirements and the expected result, without installing or running these imaginary libraries.

  1. Define what the script must be able to do

    We want the mean and the plot: all the requirements of these operations matter. The script uses Table to read and calculate; it uses Plot to draw the plot. These are 2 direct dependencies. The local modules of bilan.py are part of the shared code; here, we count only distinct external libraries.

    We assume that all masses are read in grams, with no missing rows or change in the calculation. The interpreter must also be identified in the reproduction record, but it is not included in this library count. Tools supplied with Python follow its version; they are not each an external package to add.

  2. Follow indirect requirements

    The path through Table lists Table, then Core: 2 library mentions. The path through Plot lists Plot, then Core: another 2 mentions. We therefore have 2 × 2 = 4 mentions, but Core appears on each path.

    This repetition adds 2 − 1 = 1 extra mention when counting distinct packages. Subtract it: 4 − 1 = 3 libraries. Check by another route: 2 direct + 1 indirect = 3 libraries. The script and data files are excluded from this count.

  3. Match names to versions

    The expected inventory is Table version A; Plot version B; Core version C. It covers the 3 libraries in the diagram. In this scenario, Table A and Plot B both require Core C: their requirements agree.

    A list containing only Table and Plot leaves out the indirect dependency. A list without versions leaves the edition used unspecified. A dependency file can declare exact versions or allowed versions; a lock file can preserve the selected versions, including indirect ones, depending on the tool used. You need to read what it actually contains. We limit ourselves here to the inventory, without learning an installation command.

  4. Prepare a check value

    Adding the masses gives the total mass of the bags. The partial sum is 98 + 100 = 198 g; then 198 + 102 = 300 g. We divide by 3 because each mass reading counts equally in this mean.

    m=Sn=3003=100.00 g

    S denotes the sum of the masses, in grams; n the number of mass readings, a count with no physical unit; m the mean mass, in grams. The fraction means division. Independent check: the lower mass is 2 g below 100 g and the upper mass is 2 g above it; these differences cancel out, and the central mass does not shift the mean. We obtain 100.00 g again.

  5. Compare the inventory instead of guessing

    The recipient of the analysis has Table A and Plot B, but Core is absent from their inventory. They have 2 of the 3 expected libraries: 3 − 2 = 1 library is missing, Core C. The count alerts us; comparing names and versions identifies what is missing.

    The intended environment must be completed, then checked to ensure that it is the environment actually used to launch bilan.py. In a Python project, a virtual environment serves in particular to separate one project’s packages from those of another. It does not by itself supply the required libraries or check their compatibility.

  6. Separate preparation from evidence

    Our arithmetic check gives an expected value, not an execution log. A future reproduction will need to record the interpreter and versions actually used, rerun the analysis with the same inputs, then compare the mean and check that the requested plot has been produced.

    If the displayed mean is 100.00 g, its difference from the expected result is 100.00 − 100.00 = 0.00 g. This is a useful check of this output. It certifies neither every operation in the script nor reproduction on every machine. Identified dependencies make verification easier; they do not replace that verification.

✿03 Common mistakes

  • “I sent the Git repository, so the other person has my environment.”

    The repository shares the files tracked in it. Separately record the interpreter and the libraries available to the person who will run the script, with their versions; then check that environment.

    Review the role of the environment

  • “The script does not name Core, so I can leave it out.”

    Follow the arrows beyond the script’s calls: Table and Plot use Core. The inventory must include this indirect dependency, while counting the same shared version only once.

    Revisit the library count

  • “The package count is right and so is the mean: everything has been reproduced.”

    Compare names and versions, not just their count. Then check the requested outputs: a correct mean does not prove that the plot is present. The diagnostic exercise asks you to specify what the check establishes.

For the same analysis, someone proposes replacing Plot B with Plot D. Compare with the solution

Selecting Core D satisfies the declared requirement of Plot D, but contradicts that of Table A. Selecting C would do the reverse. Under the assumptions in this question, these requirements cannot be satisfied simultaneously in the same environment. The number of distinct names can remain 3: counting does not detect this version conflict.

To restore the reference, you can return to Plot B with Table A and Core C. This choice restores the declared consistency in the scenario; execution still needs to be checked. To change the combination, you would need to consult the requirements of the versions being considered and test a compatible combination. We have no evidence here that would justify an update to Table.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Why is sharing bilan.py and its history not enough to share its environment?

Code files do not automatically supply the interpreter and libraries that will be used. You need to identify them with their versions and check that they are present in the execution environment.

Recall 2Why is Core a dependency of bilan.py even though the script does not call it directly?

Table and Plot need it. The dependency is indirect in relation to the script; you discover it by following the requirements of the direct libraries.

Recall 3Why does counting paths not necessarily give the number of distinct libraries?

The same library with the same version can be used on several paths. Here, Core C is shared: we subtract its extra mention to form the distinct inventory.

Recall 4What is missing from a list that gives the correct names without their versions?

It does not specify the editions used and does not allow a complete comparison of the requirements. Libraries with the same names may require incompatible versions of a shared dependency.

Recall 5What does our mean calculated by hand prove, and what still needs to be established?

It provides an expected value for these mass readings. The environment used and the execution of the script still need to be checked, with the requested outputs, including the plot. The dependency list alone is not that evidence.

Reconstruct the reasoning

Reconstruct the requirements of bilan.py without support: direct calls, indirect requirements, versions and the sharing of Core. Explain how to compare the inventory with the environment used, then why an expected value and a consistent list still leave an execution to be checked.
