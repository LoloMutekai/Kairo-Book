Level 1 · C018·M5

Contract tests and test doubles

Your goalWrite booking checks that can be used with several components, then state exactly what a test double lets you check.

Before you start

✿01 See the idea

You are preparing the booking desk for a drawing workshop. A person requests 2 places; the desk must confirm or reject the request. To check the display without opening bookings, you can replace the booking register with a test substitute. But a prepared "accepted" response does not tell you whether the real register would have deducted the places.

The register is the component that provides the booking; the desk consumes its response. Their interface names the available operations. Their contract specifies what an operation must accept, return and change. A contract test compares observations with these commitments, without depending on how the register organizes its data.

A test double is a replacement component used during a test. A stub returns prepared responses: it helps test how the desk reacts. A fake computes simplified behavior, for example by keeping the places in memory. A double can also record calls: this spy role lets you check what the desk asked it to do.

The entire scene and its numbers are fictional. We follow workshop bookings one after another, without cancellations, payments or external failures. We do not cover concurrent use or storage on disk here. Before looking at the results, ask yourself: which component is actually being tested in each diagram?

The rule to remember

To test the provider, keep the contract expectations and change the component under test. To test the consumer in isolation, replace its provider with a controlled double. In each case, state the boundary of the evidence.

✿02 Follow an example

Worked example

A booking sequence with independent expectations

The workshop has 6 places. We will request 2 places, then 5 places, then all the places still available. Each case observes the response and the availability after the call. The final case requests 0 places. Prepare the expectations on paper before expanding the steps.

  1. Write the observable contract

    Let C be the initial capacity, s the number of places available before the call, q the quantity requested and s′ the number of places available after the call. The prime means "after". These quantities are integer counts of places. Initially, C = s = 6 places. The state must always satisfy 0 ≤ s ≤ C.

    The operation reserve(q) returns a result containing a status and the number of places remaining. The operation availability() reads the current count without changing it. For 1 ≤ q ≤ s, the status is "accepted", the new state is s − q and the result reports this new state. For q > s and q ≥ 1, the status is "rejected"; the count stays at s. For q < 1, the status is "invalid" and the count also stays at s. Inputs of other types are outside the contract studied here.

    A rejection or an invalid input takes no places, even partially. A result already returned stays unchanged after subsequent calls. The tests use these public operations: they require neither a particular internal variable name nor a particular representation of the register.

    1≤q≤s⇒s′=s−q

  2. Prepare the test and calculate acceptance

    A test follows a reproducible procedure: prepare a known state, call the operation, then assert what must be observed. An assertion is a check that reports a failure if its statement is false. The expectation comes from the contract; it is also called the test oracle. Asking the component under test for this expectation would make the check circular.

    The requested quantity of 2 places is a positive integer below the count of 6 places. We therefore deduct it from the count: 6 − 2 = 4 places. We expect all of the following: the status "accepted", 4 places in the result and 4 places in availability(). Checking only the status would let a register pass if it confirmed without deducting the places.

    Conservation check: 2 allocated places + 4 available places = 6 places, the starting capacity. We also keep this first result to check later that it has not changed.

    6−2=4 places

  3. Test rejection for hidden deductions

    The next request is for 5 places, but only 4 remain. The difference 5 − 4 = 1 place shows why the request exceeds availability. This difference must not be deducted from the register: the contract rejects the entire request.

    We expect "rejected", 4 places reported and 4 places still available. The change in the count is 0 places. Checking the state after rejection detects an error that the word "rejected" alone does not reveal: a component could subtract the places before deciding.

    This case follows the previous acceptance: we do not reset the count to 6 between these calls. However, when we restart the entire suite on another component, we do recreate a workshop with no bookings.

  4. Test the boundary and invalid input

    Let us request exactly the 4 places still available. Equality is allowed: 4 − 4 = 0 places remaining, with status "accepted". A component that requires q to be strictly less than s would fail here, even if it passed the first request.

    In total, 2 + 4 = 6 places have been allocated; 6 + 0 = 6 places checks conservation again. The first result must still report 4 places: it describes its own call, rather than the current state, which is now 0.

    Next, let us request 0 places. This is not a valid booking: the status must be "invalid", with 0 places remaining and no change. The rule for invalid inputs is explicit; the test does not invent an exception or a status absent from the contract.

  5. Choose what the double must let you observe

    To test the booking desk, prepare a stub that responds "accepted, 4 places remaining". Inject it in place of the register. Submit a request for 2 places to the desk. Check that the desk displays a confirmation and that the call log contains exactly 1 call to reserve, with q = 2. Also prepare "rejected" and "invalid" responses to check that the desk does not turn them into confirmations.

    This stub does not deduct any places. Its call recording acts as a spy. A confirmation on screen is therefore not enough to prove a booking: it can only show that the desk handles the injected response correctly. The number of calls matters here because the desk is required to forward each request without repetition.

    To reuse the contract suite, you need a fake that maintains a count and calculates statuses. In an isolated test setup, the same suite must be able to test either this fake or the register implementation under test. Only their setup changes; the expectations and assertions stay identical. Passing on the fake alone tells you only about the fake and the cases written.

  6. Find a check that can actually contradict the component

    Independent check of the first calculation: draw 6 empty boxes and cross out the 2 allocated boxes. The number of boxes not crossed out is 4. The next request does not fit in these boxes; do not cross out any. Then cross out the 4 remaining boxes: none remain. This count uses individual places rather than the subtraction performed by the program.

    Imagine a stub that always responds "accepted, 0 places remaining". The word sounds favorable, but from the first request the difference from the contract is 4 − 0 = 4 places. Our expectation detects this faulty substitute. A double does not conform just because it has the correct method name.

    Even a suite that passes on several components checks only its cases. To find out which register the desk actually uses, you then need an integration test that keeps the real components concerned and observes their exchange. To establish actual use, you also need evidence at the point of use. The calculations on this page form a fictional test setup; they do not claim to provide any of this external evidence.

✿03 Common mistakes

  • “The double has the same methods, so it respects the contract.”

    The name reserve guarantees neither the correct count nor rejection without an effect. Apply the acceptance, excess and equality cases to the component concerned, checking its response and availability. The stub that always reports success contradicts the first calculation.

    Return to the faulty stub and the box check

  • “I calculate the expectation by asking the register what it should return.”

    An error can then appear on both sides of the comparison. First write the result using the contract and a small known state. In our workshop, drawing the boxes and checking conservation verify the expectation without consulting the register algorithm.

    Review how to prepare the oracle

  • “The desk passes with the double: the real register received the booking.”

    The double’s call recording shows the calls the double itself received. The real register is absent from the setup. Prepare its contract test and its integration test with the desk separately; keep the verdict within the components observed.

    Compare the boundaries of the test setups

Exercise 2 · Diagnosis · response and calls

A confirmation that hides repetition

The stub is set to respond "accepted, 4 places remaining" to every call. You submit 1 request for 2 places to the desk. The display is correct, but the call log contains 2 calls to reserve(2). Does the desk test pass? What would happen to the count if a conforming register starting with 6 places received this repetition?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

Compare the call log with the requirement for forwarding the request.

Hint 2

A prepared response stays identical. A working register recalculates from its state after the first call.

Compare with the solution

The test fails: we expect 1 call with q = 2, but observe 2. The display alone does not detect the repetition. Here the spy role of the double reveals the defect in the desk.

With a conforming register, the first booking would leave 6 − 2 = 4 places. The repetition would leave 4 − 2 = 2 places. The calls would be accepted: our contract provides no rule for recognizing and merging repeated requests. The stub with a fixed response hides this change; the reasoning does not prove that a real register received these calls.

Check your reasoning

  • You make the test fail because of the call log, even with the correct display.
  • You recalculate the second state from the first.
  • You keep the observed defect in the desk separate from the hypothetical effects on the register.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1Where does the expectation in a contract test come from?

From the behavior promised by the contract, applied to a known initial state. The expectation is prepared independently of the result returned by the component under test.

Recall 2In the workshop, what do the stub, the fake and call recording let you do?

The stub supplies chosen responses to the desk. The fake maintains a count and simulates the booking rules. Recording acts as a spy: it reveals the requests actually received by the double.

Recall 3Why check availability() after a rejection?

The word "rejected" can hide an incorrect deduction. The contract requires an unchanged count; checking the result and the state read can reveal this defect.

Recall 4What stays the same when you apply the suite to the fake and then to another implementation?

The cases, expectations and assertions stay the same. You change the component setup, restoring the initial state at the start of each suite. You do not reset the state between the successive calls planned within that suite.

Recall 5What is still missing after the desk passes with its double?

The real register’s contract and its integration with the desk still need testing. The double’s call log proves only what it received during the test; it demonstrates neither the connections in actual use nor an actual booking.
