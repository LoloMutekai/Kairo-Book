Interfaces

Your goalDescribe a function’s interface and decide whether a call or a change respects its contract.

Before you start
c013-m5 : recursion · c015-m5 : diagnostics · c016-m1 : modules

✿01 See the idea

At a workshop counter, you are preparing to serve juice. The stock sheet states 1800 mL; the planned request is for 650 mL. You want to know how much would remain before pouring. The quantities and the program in this scene are fictional: we are not observing any actual stock.

In this imagined small program, the commande module asks the reserve module to perform this calculation. Here, a module is a file that groups functions together. To call the function we need, commande must know its name, what information to supply and what the returned value means. This agreement forms its interface.

Imagine a form with fields labelled “stock in millilitres” and “request in millilitres”, followed by a field labelled “predicted remainder”. Changing how the subtraction is performed behind this form may have no effect on the person filling it in. Changing a field’s unit, even while keeping its name, can make their answer wrong.

The program that uses the function is its caller. The implementation is the function’s body: the instructions that perform the calculation. We will define the boundary between them: input names and types, units, accepted conditions, output and permitted effects. Here, the function predicts a volume; it pours nothing and records no new stock.

The rule to remember

An interface lets the caller know what to supply and what to expect. Its signature names the parameters; its contract also specifies units, rejected inputs and effects.

✿02 Follow an example

Worked example

Predict the remainder without changing the supply

The commande module prepares a request for 650 mL from a declared supply of 1800 mL. Let us describe the agreement with reserve.reste_apres, then follow the call through to its result and checks.

  1. Name exactly what crosses the boundary

    The signature is reste_apres(stock_ml, demande_ml). The name reste_apres identifies the function; stock_ml and demande_ml name its parameters. A parameter is a slot in the definition; an argument is the value supplied in a call. Here, the arguments are 1800 and 650.

    Each input must have type int, Python’s integer type. The contract excludes text, floating-point numbers and true/false values. The inputs count whole millilitres. The output will be an integer number of millilitres, or the marker None if the call is rejected. The suffix _ml is a reminder of the unit; Python does not check this unit from the name.

    The call is written reserve.reste_apres(stock_ml=1800, demande_ml=650). The dot identifies the function within the reserve module; the names before the = signs explicitly associate each argument with its parameter. Here, these signs indicate an association in the call.

  2. State the conditions before calculating

    To keep the relations short, s denotes the supplied stock, q the request and r the predicted remainder; all are in mL. The input conditions, called preconditions, require non-negative stock and a request between 0 volume and that stock.

    s≥0;0≤q≤s

    The agreed behaviour is explicit: check the types, then these inequalities; if a check fails, return None; otherwise calculate r. None means “no usable result”, and the caller must handle this case before any numerical use. The preconditions define the inputs to which the numerical promise applies; the interface also describes rejection outside this domain.

    Here, 1800 mL is non-negative and 0 ≤ 650 ≤ 1800. The call is valid. We assume the declared stock matches the volume available at the time of the prediction; this function does not measure the supply.

  3. Subtract to produce the promised output

    The output promise, called a postcondition, is r = s − q for an accepted call. We subtract because q is the volume planned for serving, while r is what would remain. The quantities use the same unit, and the model assumes that serving causes no loss.

    r=s−q=1800−650=1150 mL

    The returned value is therefore the integer 1150, which the contract says to read as 1150 mL. The function must not replace this number with text such as “1150 mL”: the caller expects a quantity it can use in further calculations. The display can add the unit afterwards.

  4. Check the result and the boundaries

    Check using the inverse operation: the remainder and the request must add up to the stock. 1150 + 650 = 1800 mL. We recover the supplied stock. The result also satisfies 0 ≤ 1150 ≤ 1800.

    At the boundaries, requesting 0 mL leaves 1800 mL; requesting the entire stock leaves 0 mL. These results are valid. A request for 1900 mL exceeds the supply by 100 mL: it must give None. A negative request, such as -1 mL, must also be rejected.

    These cases check different promises: conservation of volume, accepted boundaries and the distinction between rejection and an empty supply. The numerical example alone does not prove the behaviour for every input.

  5. Say what has changed after the call

    The call has produced a prediction. The original stock_ml data keeps its value 1800 in the calling program until that program replaces it; this function performs no pouring or recording. A change outside the returned result would be an effect of the call. Our contract excludes these effects.

    Given the same arguments, the function must return the same answer. The caller can use 1150 mL as hypothetical stock for the rest of its plan. To report stock that actually remains, it will need to check the serving and the supply by another means.

  6. Separate the internal method from the public agreement

    Another implementation could count the remaining millilitres instead of writing the subtraction directly. It would be compatible with this caller if it preserved the usable parameters, types, units, promised values, rejected inputs and absence of effects. Here, compatible means that the caller can continue using the function under the same agreement.

    The signature alone is therefore insufficient. A function can keep its name and parameters while returning litres or changing recorded stock. Before replacing it, compare the full contract and check the behaviour. We have made no promise about response time here.

Explain it in your own words

Hide the example. Present the interface to the person writing the commande module: arguments, types, units, conditions, output and effects. Why can the answer 0 be used as a volume while None must be handled separately?

✿03 Common mistakes

  • “The name and parameters are enough to define the interface.”

    Add what the caller needs to understand without opening the body: types, millilitres, conditions, rejection with None and the absence of effects. Keeping the name does not guarantee that these promises are preserved.

    Reconstruct the full contract of reste_apres

  • “650 mL or 0.65 L is the same volume, so I can pass either.”

    The physical volume is the same, but the interface expects an integer that counts millilitres. Supply 650. A floating-point number would be rejected by our contract; even an integer expressed in another unit would be misinterpreted. Type and unit need separate checks.

    Reread the argument types and units

  • “If the call is invalid, I will return 0 and let the caller work it out.”

    0 mL is already the correct answer when the entire supply is requested. For an excessive request, returning that same number would make a rejection look like a valid prediction. Our interface reserves None for the absence of a result; the caller must distinguish it before calculating.

Compare with the solution

The call gives stock_ml = 650 and demande_ml = 1800. The request exceeds this stock: the agreed answer is None. The function cannot guess that the arguments have been reversed.

The fixed call is reste_apres(stock_ml=1800, demande_ml=650). It returns 1150, meaning 1150 mL. Naming the arguments makes their roles visible; you still need to supply the correct quantities.

Check your reasoning

  • You associate the arguments with the parameters before subtracting.
  • You justify None by identifying the violated condition.
  • You write the fixed call and distinguish its integer value from its unit.

Exercise 2 · Chain calls

Plan an additional request

After the request for 650 mL, you plan another 250 mL. What stock do you pass to the function for this new call in your plan? Calculate the returned value and check the total volume. What can you state about the actual supply?

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

In this plan, the previous request has already consumed part of the hypothetical supply.

Hint 2

Add the final remainder and the volumes of all planned requests.

Compare with the solution

The hypothetical stock becomes 1150 mL. The call is reste_apres(stock_ml=1150, demande_ml=250). It is valid and returns 1150 − 250 = 900 mL.

Local check: 900 + 250 = 1150 mL. Check of the entire plan: 900 + 250 + 650 = 1800 mL. Reusing 1800 as the stock for the new call would overlook the first request.

The result is a prediction under the assumptions of accurate stock and serving without loss. It does not establish that any pouring took place. The actual supply still needs checking; the calculation has not changed any recorded stock.

Check your reasoning

  • You use the previous returned value as the stock in the plan.
  • You obtain 900 mL and reconstruct the initial volume.
  • You distinguish predicted values from observed serving and stock.

Exercise 3 · Diagnose a change

The same name can hide a broken contract

A new version keeps the parameters of reste_apres and still receives whole millilitres. It calculates in litres and returns its result directly in litres. It also replaces None with 0 when the request exceeds the stock. Can the caller use it without changes? Show the problems with the usual request and the excessive request, then propose a fix.

Rate your confidence before comparing

Assisted answer: try this exercise without help later.

Hint 1

A litre contains 1000 mL. Compare the unit and type of the promised return with those of the new result.

Hint 2

For an invalid request, what does a remainder of 0 mL normally mean to the caller?

Compare with the solution

For the usual request, the inputs correspond to 1.80 L and 0.65 L. The new returned value is 1.15 L. This volume does correspond to 1150 mL, but the caller expects the integer 1150 in millilitres: the unit and representation of the return have changed. Keeping the same parameters does not preserve the output promise.

For a request of 1900 mL, the return 0 would be read as a valid prediction of an empty supply. The original contract requires None because the request exceeds the supply by 100 mL. This change removes the rejection signal.

Fix: keep the public interface in whole millilitres, retain None for rejected inputs and produce no external effects. An internal calculation in litres can be retained if it restores exactly the expected integer number of millilitres; for these whole volumes, direct subtraction avoids an unnecessary conversion. Recheck the usual call, a request for the entire stock and the excessive request before any replacement.

Check your reasoning

  • You compare the output promises beyond the parameter names.
  • You relate 1.15 L to 1150 mL without confusing their numerical values.
  • You restore rejection with None and the effects specified by the contract.

✿05 Recall from memory

Close the lesson, answer each question, then reveal the answer. Explain any missing steps in your own words.

Recall 1What do you need to know to use reste_apres without reading its body?

Its name, its parameters and their association with arguments, the expected types and units, the accepted conditions, the promised output, rejection with None and the absence of external effects.

Recall 2Why is the type int insufficient to describe stock_ml?

int specifies an integer representation; it does not say what it counts. The contract specifies millilitres, a non-negative volume and the relation to the request. The name’s suffix is a reminder of the unit without checking it.

Recall 3Why are None and 0 not interchangeable in this interface?

0 mL is a valid remainder after a request equal to the stock. None indicates that the call was rejected and that no remainder should be used in a calculation.

Recall 4Does the return 1150 prove that the supply contains this volume?

It gives a predicted remainder in millilitres under the stated assumptions. The function does not dispense juice, measure the supply or record new stock. The serving and the actual volume need a separate check.

Recall 5Under what condition can the function’s body change without changing its caller?

The usable parameters and all promises about types, units, results, rejected inputs and effects must be preserved. Under this contract, the calculation method can change; the meaning of the returned value must stay the same.
